# 결 (gyeol) 설계

회사에서 PPT로 하던 발표를 HTML로 만드는 빌더. 팀장, 본부장께 결정을 받는 보고(사업 제안, 고객 제안 계획, 개선 제안, 계획)만이 아니라 주간 업무 보고, 결과·장애 보고, 프로젝트 착수, 지식 공유, 팀 소개처럼 동료나 다른 부서 앞에서 하는 발표도 다룬다. 사용자는 대부분 비개발자다. 개인 PC에서 localhost로만 띄운다.

## 1. 원칙

1. **AI(또는 규칙)는 모양만, 사람은 내용만.** 발표 형태를 받아 골격(장 구성, 레이아웃, 칸마다 작성 안내)을 만들고, 내용은 사람이 채운다.
2. **내용은 이 PC 밖으로 나가지 않는다.** 서버 저장 없음, 외부 전송 없음. 덱은 브라우저(IndexedDB), 사용자가 고른 보관 폴더, 사용자가 내보낸 파일에만 있다. AI(MCP)에도 내용은 주지 않는다(11장).
5. **결론부터.** 듣는 사람은 바쁘다. 표지에 결정 요청(결정받을 것이 없는 발표는 부제), 둘째 장에 결론(한 장 요약, 오늘의 한 줄), 마지막 장에 받을 결정이나 부탁. 처음 두 장만 봐도 무엇에 관한 발표이고 무엇을 해 주면 되는지 알게 한다.
3. **자유도를 줄여서 디자인을 지킨다.** 글상자를 마음대로 옮기는 기능은 없다. 사용자는 레이아웃을 고르고 빈칸을 채운다. 배치, 서체, 여백은 시스템이 정한다.
4. **처음 보는 사람도 설명 없이 쓴다.** 익숙한 구조(왼쪽 슬라이드 목록, 가운데 슬라이드, 아래 발표자 노트), 모든 선택지에 기본값, 모든 빈칸에 안내 문구.

## 2. 사용 흐름

```
홈(내 발표) ─ 새 발표 만들기 ─▶ 마법사 3단계 ─▶ 편집기 ─▶ 발표 / 내보내기
                                  1. 발표 종류   어떤 발표인가요?            세 묶음 13가지 + 고른 종류로 만들어지는 장 네 장의 그림
                                  2. 발표 상황   누구에게, 얼마나 발표하나요? (듣는 사람, 시간, 방식) + 구성 미리보기
                                  3. 표지       표지를 채워 주세요           (제목, 결정받고 싶은 것 또는 부제, 소속, 발표자, 테마) + 표지와 이어질 장
```

- 마법사는 모든 항목에 기본값이 있어서 "다음"만 눌러도 끝난다.
- 1단계는 종류 열셋을 회사에서 PPT를 만드는 자리 셋으로 묶어 세로 칸으로 나란히 둔다(`DECK_GROUPS`: 제안하고 결정받기, 진행과 결과 보고하기, 알리고 나누기). 단추에는 이름과 한 줄 설명만. 오른쪽 카드는 글로 된 흐름 대신 그 종류의 이야기 흐름마다 실제로 만들어지는 장(`Blueprint.showcase`)을 2×2로 작게 그린다. 칸에는 안내 예시가 진하게 들어가서 어떤 장인지 알아볼 수 있다. 두 번 누르면 바로 다음 단계. 빈 발표는 아래 줄 왼쪽의 다른 길이다.
- 2단계의 고르는 줄에는 이름만 두고, 고른 것이 무엇을 바꾸는지는 그 아래 한 줄로. 선택을 바꾸면 "10장으로 만들어요"와 장 그림이 즉시 바뀐다(새로 들어온 장만 살짝 나타난다). 발표 형태가 모양을 바꾼다는 걸 눈으로 보여준다.
- 3단계는 적는 대로 오른쪽의 큰 표지가 바뀐다. 결정을 받는 종류(`examples.ask`가 있는 것, `asksDecision`)만 '결정받고 싶은 것'을 묻고, 주간 업무 보고, 프로젝트 착수, 지식 공유, 팀 소개는 부제를 묻는다. 이런 발표의 표지는 결정 요청 칸이 없고 아래 띠 모양으로 만든다(옆 면은 위쪽이 결정 요청 자리라 비워 두면 짙은 면의 위가 빈다). 표지 아래에 이어질 장을 작게 넷(낮은 화면은 셋, 넘치면 마지막 칸에 남은 장 수) 그려서 오른쪽 칸 아래가 비지 않게 한다. 테마는 견본과 이름으로 고른다.
- 설명 글을 화면에 늘어놓지 않는다. 꼭 필요한 설명만 옆에 (i)를 두고 마우스를 올리면 툴팁으로 보인다(`Info`). 홈의 보관 폴더 안내도 같다.
- 화면 비율: 묻는 말은 두 칸 위에 걸치고, 왼쪽(고르는 것)과 오른쪽 카드는 같은 줄에서 시작해 높이가 비슷하게 칸 너비를 단계마다 잡는다. 틀 전체는 머리줄과 아래 줄 사이 가운데에 둔다(위에 붙이면 큰 화면에서 아래만 크게 빈다). 1920×1080에서는 틀을 1480까지 넓히고 단추와 그림을 키운다.
- 1280×600(윈도우 노트북 150%), 1366×650, 1536×730에서 세 단계 모두 스크롤 없이 한 화면에 들어가고 가로 스크롤은 없다. 장이 많은 구성(30분)은 2단계 오른쪽 카드 안에서만 스크롤한다.

## 3. 골격 생성 규칙

발표 형태가 바꾸는 세 가지:

| 입력 | 바뀌는 것 |
|---|---|
| 종류 (13가지, 아래 표) | 이야기 순서와 장 구성 (blueprint) |
| 듣는 사람 (본부장·임원, 팀장, 팀 동료, 다른 부서, 여러 분이 함께) | 장마다 무엇을 챙기는 장인지(`focus`: 숫자 numbers, 자세한 실행 detail, 배경 context) 달아 두고, 듣는 사람이 더 챙기는 장(`up`)은 우선순위 3을 2로, 덜 챙기는 장(`down`)은 2를 3으로 바꿔 장 수를 맞춘다. 본부장·임원: 숫자를 챙기고 세부를 덜어 내며 목차가 없다. 팀장, 팀 동료: 실행 계획과 세부까지. 다른 부서: 배경을 먼저 푼다. 여러 분이 함께: 구성 그대로 |
| 시간 (5, 10, 20, 30분+) | 목표 장 수 5, 7, 11, 15. 보고는 질문과 토론이 길어서 한 장에 2분 남짓. 우선순위 낮은 장부터 뺀다 |
| 방식 (회의실 발표, 화상 회의, 보고서로 보내기) | 글 밀도와 작성 안내. 보고서로 보내면 혼자 읽어도 이해되게 설명을 더 넣도록 안내 |

- 어느 종류든 표지 → 결론(한 장 요약, 지식 공유는 오늘의 한 줄) → … → 마지막 한 장(받을 결정이나 부탁)의 뼈대는 같고, 마지막 장은 한 번만 나온다(`generate.test.ts`). 한 장 요약은 줄 이름(배경, 제안, 기대 효과, 요청 사항)을 미리 넣고 줄마다 다른 안내를 단다(`hints['items.N.body']`).
- 위험과 대응, 안 비교(A안/B안/C안, 추천안 강조), 필요한 자원(예산/인력/기간) 같은 보고용 장은 이름표를 미리 채운다(`prefill`). 이름표는 구조라서 미리 넣어도 되지만 내용은 넣지 않는다.

- 유형별 blueprint는 사람이 설계한 장 목록이다. 각 장은 레이아웃, 역할 이름, 우선순위(1~3), 대상 청중, 챙기는 것(focus), 칸별 안내 문구를 가진다. 장의 안내(`guide`)는 짧은 한 문장으로 쓴다.
- 장 수 맞추기: 우선순위 1은 절대 빼지 않는다. 3부터, 같은 우선순위면 뒤쪽부터 뺀다. 섹션 구분 장들은 묶음으로 넣거나 뺀다(일부만 있으면 어색하다).
- 규칙 기반이라 AI 없이도 돈다. AI는 MCP로 구성과 모양만 손볼 수 있다(11장).

종류는 회사에서 PPT를 만드는 자리를 공개된 보고서 작성 안내(업무 보고를 계획·현황·결과 보고로 나누는 글, 품의서와 주간 업무 보고, 장애 보고 양식의 항목)에서 모아 셋으로 묶었다. 종류 id는 저장 파일에 남으니 바꾸지 않는다. 예전 버전은 모르는 종류를 빈 발표처럼 다룬다(이름이 비고, AI에게는 `blank`로 보인다).

| 묶음 | 종류 | 마지막 장 |
|---|---|---|
| 제안하고 결정받기 | 사업 제안, 개선 제안, 검토 보고(여러 안 비교), 고객 제안 계획, 연간·반기 계획 | 결정 요청 (우선순위 1) |
| 진행과 결과 보고하기 | 주간·월간 업무 보고, 실적 보고, 결과 보고, 문제·장애 보고 | 요청 사항 (실적 보고만 1, 나머지는 2라 짧은 발표에서는 빠진다) |
| 알리고 나누기 | 프로젝트 착수, 조사·분석 보고, 지식 공유·교육, 팀·업무 소개 | 함께 정할 것, 다음에 할 일, 정리, 이럴 때 찾아 주세요 |

## 4. 데이터 모델

```ts
Deck  { id, title, meta: { type, audience, duration, method, org, presenter, date, contact, logo },
        theme: { id, accent? }, logo, slides: Slide[] }
Slide { id, layout, purpose, section, fields: {title, lead, body, ...}, items: Item[],
        hints, guide, notes, options, hidden }
Item  { id, title, body, value, meta, image }
```

- 레이아웃이 달라도 칸 이름(title, lead, body, items[].title/body/value/meta)을 공유한다. 그래서 레이아웃을 바꿔도 내용이 유지된다.
- 레이아웃의 최대 항목 수보다 많은 항목은 지우지 않고 숨긴다. 다시 바꾸면 돌아온다.
- 소속, 발표자, 날짜, 연락처, 로고는 덱 단위 값이다. 표지에서 고치면 마지막 장에도 반영된다. 결정 요청 한 줄은 표지의 칸(`fields.ask`)이다. 결정을 받지 않는 발표는 편집할 때도 이 칸을 그리지 않는다(적어 둔 것이 있으면 그대로 보인다).

## 5. 레이아웃 (26개 + 부품 장)

표지(결정 요청 포함), 섹션 구분, 목차, 한 장 요약, 한 문장 메시지, 핵심 숫자, 목표 대비 실적, 두 값 비교, 증감 요인, 추이, 진행 현황, 구성비, 단계 흐름, 깔때기, 표, 핵심 포인트, 비교(지금과 바뀐 뒤, 위험과 대응), 2×2 우선순위, 위치 비교, 일정, 사례, 안 비교, 이미지와 설명, 로고 모음, 막대 비교, 결정 요청.

- **모양(variant):** 한 레이아웃 안에서 같은 칸을 다르게 놓은 것. 칸은 늘거나 줄지 않아서 바꿔도 내용이 그대로다. 목차(목록/나란히), 한 장 요약(줄/칸), 핵심 숫자(나란히/하나 크게/카드), 핵심 포인트(줄/세로 칸/타일), 비교(두 면/표), 일정(가로/세로), 안 비교(카드/표), 막대 비교(가로 막대/세로 막대), 추이(선/면), 구성비(띠/도넛), 단계 흐름(선으로 잇기/칸), 두 값 비교(묶은 막대/두 선/점 두 개), 섹션과 결정 요청(바탕/색 면), 표지(옆 면/아래 띠/색 면).
- **목표 대비 실적:** 목표와 실적을 같은 단위로 적으면 달성률은 저절로 계산한다. 막대는 실적만큼 채우고 목표 자리에 세로 줄. 목표를 넘은 만큼은 진하게, 모자란 만큼은 빗금으로 목표 줄에 붙여 칠한다. 좋고 나쁨을 색으로 판정하지 않는다(낮을수록 좋은 지표가 있어서). 눈여겨볼 지표 하나만 강조색.
- **두 값 비교:** 항목마다 앞 값(작년, 계획)과 뒤 값(올해, 실적). 두 값의 이름은 칸으로 바꾼다. 묶은 막대는 0부터, 두 선은 추이처럼 바닥을 올려 그린다. '점 두 개'는 항목마다 한 줄에 앞 값과 뒤 값의 점을 찍고 사이를 잇는다(덤벨): 항목이 많아도 줄이 가지런하고, 움직일 때 뒤 값의 점이 앞 값에서 출발해 미끄러진다. 앞 값은 옅은 회색, 뒤 값은 강조색. 항목 이름 아래에 앞 값에서 몇 % 바뀌었는지(▲▼) 계산해 붙이되, 늘어난 것이 좋은지는 장마다 달라서 색으로 가르지 않는다.
- **증감 요인(폭포):** 처음 값(예: 목표)과 요인마다 더하고 뺀 값을 적으면 끝 값(예: 실적)은 계산한다. 따로 적으면 서로 안 맞을 수 있어서다. +, ▲는 더하기, -, −, △, ▼는 빼기로 읽는다(`src/slides/numbers.ts`). 더한 요인은 강조색, 뺀 요인은 옅은 회색, 처음과 끝은 글자색. 처음과 끝이 증감보다 훨씬 크면 바닥을 올리고 막대 아래를 비스듬히 끊어 잘렸음을 보인다.
- **추이:** 시기마다 숫자를 적으면 점을 찍어 선으로 잇는다. 모두 0보다 크고 폭이 좁으면 0부터 그리지 않는다(흐름을 보는 장이라 납작해지지 않게). 0을 지나면 0 줄을 긋는다. 목표선은 적었을 때만, 강조 점은 기본이 마지막(`highlight.fallback: 'last'`). 값 이름표는 점 위, 양옆보다 낮은 점은 점 아래. 숫자가 빈 시기는 발표할 때 점을 찍지 않는다. 무너지기 쉬운 값은 갤러리 `set=edge`로 본다.
- **진행 현황:** 과제마다 진행률 막대와 상태. 상태 글(완료, 진행 중, 지연, 예정 등)을 읽어 색을 정하고, 비우면 발표할 때 진행률로 짐작한다(100%는 완료, 0%는 예정, `statusOf`). 읽을 수 없는 글('검토 중')은 색 없이 그 글 그대로. 머리줄 오른쪽에 상태별 과제 수를 모아 지연이 먼저 보이게. 상태는 늘 글자와 함께 색을 쓴다.
- **구성비:** 값을 더한 전체에서 각 항목의 비중. 모두 %로 적었으면 적은 그대로, 금액이나 건수면 비중을 계산해 크게 보이고 적은 값과 합계는 작게. 강조할 조각만 강조색, 나머지는 큰 조각부터 진한 회색 단계. 강조가 없으면 강조색의 농담. 숫자와 단위는 붙여 쓴다('131억 원').
- **단계 흐름:** 날짜 없는 순서(업무 절차, 바뀌는 절차). 기본 모양은 단계마다 위에 굵은 선을 긋고 그 아래 가는 번호, 이름, 설명을 두는 줄이다. 선이 이어져 순서의 띠로 읽힌다. 번호를 동그라미에 넣어 점 사이를 잇는 꼴과 칸 사이 꺾쇠는 흔한 서식처럼 보여 뺐다(목차, 마지막 장과 같은 말). 움직일 때 단계마다 선이 왼쪽부터 그어지고 다음 단계의 선이 이어서 그어진다. 일정(날짜가 있는 순서)과 나눠 쓴다. 강조할 단계 하나는 선을 두 배 굵기의 강조색으로, 번호도 강조색으로(강조색 바탕에서는 강조가 글자색이라 굵기로 알아본다).
- **위치 비교(포지셔닝 맵):** 두 기준(가로, 세로)의 점수로 회사나 안을 점으로 찍는다. 점수가 모두 0~10이면 0~10 눈금, 아니면 가장 큰 값까지. 가운데 점선 십자는 두 기준의 중간. 강조할 점(보통 우리)만 강조색으로 크게, 나머지는 회색. 이름표는 점 옆에 붙이되, 이웃한 이름표나 점과 겹치면 반대쪽이나 위아래로 비킨다: 그리기 전에 글 길이로 어림하고(`labelSides`), 그린 뒤에 실제 크기로 다시 고른다(`fitBlocks.ts`의 `labels`, 내보낸 파일도 같다). 점수는 편집할 때만 이름 아래에 보인다.
- **깔때기:** 단계마다 한 줄에 이름, 숫자, 막대. 막대는 왼쪽 끝을 맞춰 남은 만큼(첫 단계 대비 길이)을 세고, 그 단계에서 빠진 만큼(앞 단계 길이에서 이 길이까지)을 막대 뒤에 옅게 이어 위에서 아래로 계단이 진다. 앞 단계에서 넘어온 비율은 막대의 시작 위에, 처음부터 끝까지의 비율은 이름과 숫자 칸에 맞춘 맨 아래 줄에. 비율은 계산한다. 막대는 회색, 강조할 단계(기본은 마지막)만 강조색. 단계는 순서가 있는 항목이라 가로 막대로 둔다(ONS 차트 지침: 항목은 가로 막대, 세로 막대는 시간 순서에). 예전의 가운데 맞춘 막대는 단계마다 짙어지는 강조색과 막대 끝에 붙은 숫자 때문에 숫자 줄이 들쭉날쭉하고 흔한 깔때기 그림처럼 보였다.
- **표:** 칸은 넷까지(머리말 h1~h4, 항목의 title, meta, value, body). 발표할 때는 머리말도 칸도 비운 칸이 빠진다. 금액, 비율, 건수만 든 칸은 오른쪽에 맞춘다('11월' 같은 날짜는 글로 본다). 강조할 줄 하나.
- **일정:** 시기 아래 가는 선 위에 작은 꽉 찬 점을 찍는다. 굵은 테두리의 큰 동그라미에 둘레까지 두른 점은 흔한 서식처럼 보였다. 장 한 장을 다 쓸 때 시기는 일정의 답이라 가장 크게 둔다(넷까지 62, 다섯·여섯은 44). 지금 단계를 고르면 지나온 구간의 선과 점은 강조색, 지금 점은 바탕 틈을 둔 가는 고리, 남은 점은 옅게. 세로 목록 모양은 단계마다 한 줄에 시기, 점, 할 일, 설명을 두고(칸은 모든 줄이 같이) 점을 잇는 세로 선 하나만 긋는다. 시기는 가장 긴 시기만큼만 넓게 잡아 점 옆에 붙이고, 설명은 본문 가운데(12칸 격자의 7번째 칸)에서 시작해 왼쪽 반과 오른쪽 반이 맞선다. 예전에는 줄마다 가로 선까지 그어 선이 세 겹이었고, 할 일과 설명을 위아래로 쌓아 오른쪽 절반이 비었다.
- **안 비교:** 안이 하나면 고를 것이 없으니 장을 다 쓰는 판 하나로 그린다: 왼쪽에 이름과 비용(이 장의 답이라 크게), 오른쪽에 내용. 판 하나를 왼쪽 760px에 두던 때는 장의 오른쪽 절반이 통째로 비었다.
- **로고 모음:** 다섯까지는 한 줄에 모두, 그보다 많으면 두 줄로 나눠 윗줄에 하나 더(7개는 4·3, 9개는 5·4, `logoColumns`). 덜 찬 마지막 줄은 가운데에 둔다(칸을 반 칸으로 나눠 반 칸만큼 민다). 한 줄에 넷을 두던 때는 5개가 4·1로 마지막 줄에 하나만 남았다.
- **숫자 장의 출처:** 핵심 숫자, 막대 비교, 목표 대비 실적에는 출처·기준 시점 칸이 있다(선택).
- 숫자를 넣기 전에는 편집 화면에서 예시 막대를 흐리게 보여 줘서 어떤 장인지 알아보게 한다. 발표와 내보낸 파일에는 나오지 않는다.

- 모든 슬라이드는 1920×1080 고정 캔버스에 디자인하고 화면에 맞춰 축소·확대한다. 어디서 열어도 같은 모양이다.
- 긴 글: 칸마다 글자 수 단계에 따라 글씨를 줄인다(내보낸 파일에서도 같은 결과가 나오도록 측정이 아니라 길이 기준). 그래도 넘치면 편집기에서 경고한다.
- 항목 수에 따라 배치가 바뀐다(2~4열 등).

## 5-1. 부품 장: 부품을 골라 끌어다 놓기

레이아웃이 맞지 않는 장은 부품을 골라 직접 꾸민다. 그래도 글상자를 아무 데나 두지 않는다. **정해진 줄과 칸에만 들어가서** 대충 놓아도 반듯하다.

- **부품(`src/deck/blocks/`):** 부품 장만의 부품 32가지(핵심 한 줄, 제목과 글, 점 목록, 인용, 강조 상자, 큰 숫자, 전과 후, 목표 대비, 비율 원, 몇 중 몇, 숫자와 흐름, 개요, 걱정과 대책, 강점과 약점, 예상 질문, 준비 상황, 추진 일정, 맡은 사람, 이미지, 평가표, 시장 규모, 원인 순위, 기간별 달성, 항목별 증감, 쌓은 막대, 색 표, 지표 흐름표, 흐름, 연결도, 나누기, 모으기, 칸 조립)와 레이아웃을 그대로 쓰는 부품 19가지(한 장 요약, 핵심 숫자, 추이, 증감 요인, 표 등). 레이아웃 부품은 그 레이아웃의 그리기, 칸, 안내, 움직임을 그대로 쓰고 장의 머리(제목, 부제, 출처)만 뺀다. 그래서 장을 부품 장으로 바꿔도 생김새가 같다.
- **맡은 사람의 체계도:** 맨 앞 사람(이끄는 사람)을 위 가운데에, 나머지를 아래에 나란히 두고 선으로 잇는다(추진 체계). 동그라미는 빼고 글을 가운데로 둔다: 동그라미와 글을 옆으로 두면 세로 선이 둘 사이에 떨어져 글에 꽂혀 보였다. 선은 칸의 가짜 요소라 움직일 때는 칸이 아니라 글을 올리고, 선은 이끄는 사람 아래에서 내려와 가운데에서 양옆으로 퍼진 뒤 사람마다 내려온다.
- **움직이는 컴포넌트(묶음 ‘움직임’):** 발표할 때 데이터가 오가고 나뉘고 모이는 모습을 보이는 부품. 움직임이 주인공이지만 편집할 때, PDF, 축소 목록의 다 보인 모습만으로도 한 장의 그림으로 읽혀야 한다(움직임은 시작 모습만 정하고 끝 모습은 CSS 그대로). 강조색은 답(흐름이 닿는 곳)에만, 선과 화살표는 이음표처럼 글자색을 옅게 한 색이다. 흐름은 단계(시스템)를 옅은 면의 상자로 나란히 두고 사이를 화살표 끝의 선으로 잇는다. 오가는 양은 상자 아래 끝에 숫자로 두어 나란한 단계끼리 한 줄에 서고, 강조할 단계(기본은 마지막)만 옅은 강조 면과 테두리, 강조색 숫자다. 단계 상자가 210px 남짓보다 좁아지면(단계 수마다 문턱이 다르다) 상자를 세로로 쌓고 이름과 설명을 한 줄에, 양을 오른쪽 끝에 둔다: 나란히 두면 단계 이름이 두세 글자마다 꺾였고, 쌓을 때 이름과 설명을 위아래로 두면 상자 하나가 두 줄 높이라 넷만 쌓아도 칸을 넘쳤다. 가장 좁은 너비는 4칸이다(3칸에 다섯 단계를 쌓으면 860px로도 모자랐다). 칸에 면은 깔지 않는다: 단계 상자가 이미 면이라 상자 안에 상자가 된다(`rules.ts`의 `FLAT`, 연결도도 같다). 연결도는 가운데(짙은 면)를 사이에 두고 이어진 것(옅은 면)을 양옆에 나눠 두고(앞의 반, 홀수면 하나 더가 왼쪽), 상자마다 가운데 쪽으로 나온 선이 줄기에서 둥글게 꺾여 가운데 상자에 닿는다. 한쪽 단의 상자는 모두 2줄씩 차지하는 같은 높이의 칸이라(오른쪽이 하나 적으면 한 줄 내려 엇갈린다) 선의 세로 길이를 '상자 높이 + 사이'의 배수로 CSS만으로 그린다. 선은 모두 테두리로 그린다: 줄여 그린 장에서 배경으로 그린 선과 테두리로 그린 선은 픽셀에 맞춰지는 자리가 달라 이음매가 1px 어긋났다. 칸이 720px보다 좁으면 가운데를 위에 한 줄로, 이어진 것을 아래에 들여 쌓고 왼쪽 줄기에서 가지를 뻗는다(이름과 설명은 한 줄에. 위아래로 두면 여섯을 쌓아 860px로도 모자랐다). 나누기는 전체 하나를 몇 조각으로 나눈 몫이다: 무엇의 합계인지와 합계(큰 숫자, 글자색. 비우면 조각을 더한 값)를 위에, 그 아래 굵은 막대 하나를 조각의 몫대로 나눈다(사이는 8px 바탕 틈, 색은 구성비와 같은 강조색의 농담, 강조할 조각을 고르면 그것만 강조색이고 나머지는 회색 농담). 조각의 이름과 값은 그 조각 바로 아래, 막대와 같은 몫의 칸에서 조각 색의 짧은 세로선 옆에 선다: 범례를 따로 두면 색을 맞춰 보며 눈을 옮겨야 했다. 조각마다 이름과 값이 들어갈 너비를 글자 수로 어림해(`splitNeed`) 그 너비가 몫이 되는 칸 너비를 문턱으로 고르고, 칸 안쪽(면의 여백을 뺀 너비)이 그보다 좁으면 막대 아래 목록(조각 색 네모, 이름, 값과 몫)으로 바꾼다. 넓은 칸의 목록은 여러 단으로 흘린다(한 단이면 다섯 줄이 칸 높이를 다 가져갔다). 숫자는 `seriesIn`으로 한 기준에 맞춰 더하고, 단위가 섞여 더할 수 없으면 막대를 비우고 몫을 보이지 않는다. 모으기는 여러 값을 더한 합계다: 값마다 한 줄(이름, 값, 조각)을 두고 맨 아래 합계 줄을 셈의 합계 선(`--rule`, 옅은 글자색)으로 나눈다. 합계 줄은 무엇의 합계인지, 합계(강조색, 이 부품의 답), 합계 막대. 줄의 조각은 합계 막대에서 그 값이 들어갈 자리에 그대로 놓여(앞 조각들이 끝난 곳부터) 줄마다 한 칸씩 오른쪽으로 내려가는 계단이 된다: 따로 그린 작은 막대를 늘어놓으면 합계 막대의 어느 조각이 어느 값인지 색으로만 맞춰야 했다. 막대와 조각은 같은 식(몫과 앞의 틈 수)으로 자리를 잡아 조각이 막대의 제 조각 바로 위에 선다. 칸 안쪽이 960px보다 넓으면 이름, 값, 조각이 세 칸(모든 줄이 함께 쓰는 subgrid, 값은 합계까지 오른쪽 끝을 맞춘다), 좁으면 이름과 값 한 줄 아래 조각을 둔다(세 칸이면 합계가 값 칸을 넓혀 조각 자리가 300px도 남지 않았다). 칸 조립은 비율을 작은 네모 칸의 판으로 보인다: 큰 숫자(강조색) 옆(좁으면 위)에, 사이를 칸 한 변의 16%로 좁힌 판을 둔다. 전체가 100까지의 정수면 칸 하나가 하나(60명 중 47명이면 6줄 10칸), 아니면 100칸으로 백분율이다. 전체 칸은 비우면 100이라 열어야 보이는 칸이다(편집할 때 늘 보이면 낮은 줄에서 판 자리를 먹어 글자가 0.7까지 줄었다). 줄 수는 √n 부근에서 빈자리가 가장 적은 것으로 고른다(`tileGrid`). 채운 칸은 왼쪽 단부터 단마다 아래에서 위로 쌓여 단 하나가 전체의 열에 하나다. 상자가 납작하면 줄을 반으로 줄여 옆으로 눕히고, 넓은 칸에서는 판을 칸의 오른쪽 끝에 붙인다(숫자는 왼쪽 끝). 판의 칸은 눕혀도 한 변 20px 밑으로 줄지 않는다. 몇 중 몇(`ratio`)과 같은 '전체 가운데 몇'이지만 몇 중 몇은 셀 수 있는 것을 점(사람이면 사람 모양)으로 20개까지 하나씩 세는 조용한 부품이고, 칸 조립은 100칸까지 하나씩 세고 판 전체를 한 덩어리로 보이며 발표할 때 칸이 날아와 맞춰지는 부품이다.
- **계산하는 부품:** 사람이 적은 글은 그대로 보이고, 모양만 글에서 읽는다. 비율 원은 비율만큼 둘레를 채운다(반원 게이지 모양은 손잡이가 호의 끝을 따라간다). 낮은 칸에서는 원을 왼쪽에, 이름과 덧붙임을 오른쪽에 둔다: 위아래로 쌓으면 글이 높이를 먼저 가져가 원이 지름 50px대로 줄었다. 그림은 칸에 맞춰 줄어들 뿐 넘치지 않아서, 잘리지 않는 높이를 잴 때 그림의 가장 작은 크기(원 지름 120, 반원 너비 160, 목표 대비 막대 16)도 본다(`measureBlocks.ts`의 `FIGURE_MIN`). 몇 중 몇은 전체가 20개까지면 점 하나가 하나, 더 많으면 점 100개로 백분율을 보이고, 단위가 '명'이면 점 대신 사람 모양. 점은 숫자 바로 아래나 옆에 한 덩어리로 둔다(점 칸이 남는 높이를 다 가져가면 점이 칸 아래에 붙어 숫자와 한참 떨어졌다). 한 줄로 늘어놓을지 줄을 늘릴지는 점이 더 커지는 쪽이고, 그 갈림의 칸 비율은 점 수마다 다르다(열 개면 5.5:1, 다섯 개면 2.7:1). 둘 다 가장 큰 크기(72px)면 한 줄로: 줄을 늘린 배치는 넓은 칸의 반도 쓰지 않는다. 숫자와 흐름은 흐름 칸의 숫자(쉼표나 띄어쓰기로 나눔, '1,200'은 한 숫자)로 작은 선을 그린다. 준비 상황은 상태 글(완료, 진행 중, 지연, 예정)을 진행 현황과 같은 규칙(`statusOf`)으로 읽어 표시를 고른다. 추진 일정은 기간 칸 이름을 할 일의 기간 글에서 찾아 처음 칸부터 끝 칸까지 막대를 긋고(`spanIn`, '1월'을 '11월' 안에서 잡지 않는다), 기간 칸 이름은 쉼표나 줄바꿈이 있으면 그것으로만 나누고(`colsOf`, 이름 안의 띄어쓰기는 그대로), 띄어쓰기로만 적었으면 큰 기간 뒤의 작은 기간과 때를 앞말과 한 칸으로 묶는다('10월 1주 10월 2주', '3월 상순', '1분기 말'. 예전에는 '10월', '1주'가 따로 칸이 됐다). '10월 1주 2주 3주'처럼 앞 칸의 큰 기간을 빼고 적으면 이어받고, 기간 글도 그렇게 읽는다('10월 2주~3주'는 10월 3주까지, '11월'은 11월의 칸 모두). 이름이 칸보다 길면 글자를 줄이지 않고 띄어쓰기에서 두 줄로 쌓는다. 안내 문구는 쉼표로 나눈 꼴('11월, 12월, 1월')을 보인다(편집할 때의 예시 칸이기도 해서 설명을 적지 않는다), 지금 칸을 적으면 지난 일은 흐리게, 하는 일은 강조색, 할 일은 옅은 강조색으로 칠한다. 막대가 기간을 보여 주므로 기간 글은 칸 이름보다 더 적은 것이 있을 때만 보인다. 맡은 사람은 이름 첫 글자를 동그라미에 넣고 사진은 받지 않는다(사람 사진을 발표 파일에 담지 않게). 평가표는 기준마다 평가 글을 안 차례로 나눠(띄어 쓰기나 쉼표) 좋음, 보통, 나쁨(상 중 하, ○ △ ×도)을 꽉 찬 원, 반 찬 원, 빈 원으로 그리고(`gradeOf`), 읽지 못한 글('1.9억' 같은)은 그대로 보인다. 추천하는 안을 적으면 그 안에만 옅은 띠와 강조색을 쓴다. 시장 규모는 원을 바닥에 맞춰 겹치되 크기를 규모에 비례시키지 않는다(전체 시장이 목표의 백 배가 넘기 일쑤라 비례하면 목표가 점이 된다). 규모는 옆 목록의 큰 숫자로 읽고, 강조색은 마지막(목표)에만. 원인 순위(파레토)는 막대가 전체에서 그 원인의 몫, 선이 앞에서부터 더한 몫(누적 비율)이고 둘이 같은 눈금이라 눈금이 하나다(눈금 둘을 겹치지 않는다). 누적 비율이 80%에 닿기까지의 원인만 강조색이고, 위에 '상위 3개가 전체의 88%'처럼 요점을 계산해 적는다. 원인은 적은 차례 그대로 둔다(장 위에서 순서를 바꾼 대로 보여야 해서 저절로 줄 세우지 않고, 안내에 '많은 것부터'). 기간별 달성은 실적 막대와 목표 줄(막대보다 조금 넓은 가로 줄)을 겹치고, 목표를 넘은 기간만 강조색, 못 미친 기간은 회색이다. 이름 아래에 달성률, 위에 'N번 중 M번 달성'. 목표 숫자는 편집할 때만 막대 위에 칸으로 보이고 발표할 때는 목표 줄과 달성률로 읽는다. 항목별 증감은 0을 세로 선으로 두고 늘어난 것은 오른쪽, 줄어든 것은 왼쪽으로 뻗는다. 0의 자리는 양쪽 가장 큰 값의 비율이라 모두 늘었으면 왼쪽 끝이다. 늘어난 것이 좋은지(매출) 나쁜지(비용)는 장마다 달라서 강조할 쪽을 모양으로 고른다(늘어난 쪽 강조, 줄어든 쪽 강조). 쌓은 막대는 나눈 것 이름(쉼표로 나눔, 이름 안의 띄어쓰기는 그대로)과 기간마다의 값(쉼표로 나눔)으로 쌓고, 맨 아래 칸이 강조색, 위로 갈수록 옅다. 값 그대로와 100%로 두 모양이고, 칸 안 숫자는 칸이 숫자보다 높을 때만 보인다(칸마다 크기 상자의 컨테이너 쿼리). 세 세로 막대 차트는 낮은 칸에서 소제목과 표시 줄을 한 줄에 놓아 막대 높이를 지킨다. 막대 너비는 항목 칸의 반 남짓(56%)이고 가장 넓어도 160px이다(120px까지였을 때는 한 줄을 다 쓰는 막대 넷 사이가 막대의 두 배 넘게 비었다). 색 표(히트맵)는 줄마다의 값(쉼표로 나눔, '-'는 빈 칸)을 강조색 하나의 진하기로 칠하고(가장 낮은 값이 가장 옅고 가장 높은 값이 강조색 그대로), 칸마다 숫자를 그대로 둔다. 숫자 색은 칸의 진하기가 문턱을 넘으면 강조색 위의 글자색으로 바꾸는데, 문턱은 강조색 아홉, 두 테마, 카드에서 3:1 밑으로 내려가지 않게 셈한 값이다(검은 바탕은 더 늦게, 강조색 바탕은 짙은 면까지 칠한다). 표 전체에서 견주면 가장 높은 칸과 낮은 칸에 고리를 두르고 위에 어디인지 적고, 줄마다 견주면(줄마다 단위가 다를 때) 고리 없이 줄마다 제 눈금이다. 지표 흐름표는 지표마다 흐름 칸으로 작은 선을 긋고 지금 값(마지막)과 바로 앞 또는 처음보다 바뀐 만큼을 나란히 둔다. 선은 지표마다 제 눈금이라 단위가 다른 지표를 한 표에 두고, 강조색은 지금(선 끝 점과 지금 값)에만, 바뀐 만큼은 오른 것이 좋은지가 지표마다 달라 색 없이 ▲▼로 적는다(단위가 %면 %p).
- **자리:** 줄은 셋까지, 한 줄에 칸은 셋까지, 부품은 여섯까지. 칸 너비는 12칸 격자의 정해진 비율만(12 / 6·6, 8·4, 4·8 / 4·4·4, 6·3·3, 3·6·3, 3·3·6). 부품마다 가장 좁은 너비(`minSpan`)와 보기 좋은 너비(`prefSpan`)가 있다. 줄 높이는 CSS 격자가 나누되 부품이 잘리지 않을 높이를 지킨다. 높이를 받으면 커지는 부품(차트, 표, 그림, 일정 막대, 2×2·위치 판, 로고: `stretchRows`)이 든 줄이 있으면 남는 높이는 그 줄끼리 똑같이 나누고(`minmax(잘리지 않을 높이, 1fr)`), 글과 숫자의 줄은 잘리지 않을 높이 그대로 둔다. 모든 줄에 똑같이 나누면 차트 위의 핵심 한 줄도 차트만큼 높아져서, 칸이 내용보다 훨씬 크게 잡히고 칸 안 위아래가 비었다. 그런 줄이 없으면(글과 숫자뿐이면) 모든 줄에 똑같이 나눠 더한다(두 줄이면 위아래 1:1). 그 높이를 지키려고 한 줄이 더 가져가면 나머지 줄이 남은 높이를 다시 나눈다. 예전에 부품마다 비중을 두었을 때는 예상 질문 같은 글 목록에도 높이가 몰려 아래 줄만 장 끝까지 늘어나 보였다. 지금은 높이를 받아 실제로 커지는 부품만 나눠 가진다. 사람이 줄 사이를 끌어 높이를 정하면(`BlockRow.grow`, 1~100의 비중, 모든 줄에 있을 때만) 그 비중으로 나눈다(`minmax(잘리지 않을 높이, 비중fr)`). 비중대로면 잘리는 줄은 격자가 잘리지 않을 높이로 묶고 남은 줄끼리 다시 나눈다. 줄을 더하거나 옮겨 새 줄이 생기면 비중이 없는 줄이 생겨 다시 똑같이 나눈다. 그 높이는 부품, 모양, 바탕(그대로 / 카드와 강조색 면), 항목 수, 칸 너비마다 갤러리에서 고를 수 있는 글꼴 짝마다 잰 표(`deck/blockHeights.ts`, 높은 쪽)에 차트처럼 너무 납작하면 보기 나쁜 부품의 바닥 높이를 더한 것이다. 선 차트(추이, 두 값 비교의 선)는 한 줄을 다 쓰면 바닥 높이를 80px 낮춘다: 납작해 보이는 것은 높이가 아니라 너비와 높이의 비율이라서. 그래서 핵심 숫자 한 줄 아래에 추이 한 줄이 들어간다. 막대 차트는 낮추지 않는다. 막대 위 숫자, 아래 이름과 증감의 자리는 너비와 상관없어서 낮춘 만큼 막대만 눌린다(두 값 비교 아래 증감을 쌓으면 막대가 20px가 됐다). 높이를 가늠하는 본문 상자는 편집 화면과 발표 화면이 같아야 한다. 편집할 때만 보이는 빈 부제의 안내는 자리를 밀지 않게 제목 아래 여백 위에 겹쳐 둔다(예전에는 그 줄 81px만큼 편집 화면에서만 본문이 낮아, 발표 화면에는 들어가는 조합을 막았다). 그 높이를 지킬 수 없는 자리는 놓을 자리로 고르지 않고, 항목 추가와 모양 바꾸기도 막는다. 다만 다른 줄의 칸 너비만 다시 나누면 들어가는 자리는 연다(`insertAt`에 본문 높이를 주면 줄이는 폭이 큰 줄부터 하나씩 가장 낮아지는 비율로 바꾸고, 들어가는 순간 멈춘다). 좁으면 위아래로 쌓여 높아지는 부품(전과 후, 숫자)은 넓은 칸에서 낮아져서, 짧은 글 옆 4칸의 전과 후를 8칸으로 넓히면 아래에 차트 한 줄이 들어간다. 예전에는 장이 반쯤 비어 보여도 차트를 모두 막았다. 끄는 동안 보이는 모습과 놓은 뒤, AI의 제안이 같은 높이로 같은 계산을 한다. 막을 때는 까닭(`NoRoom`: 부품 수, 줄 수, 줄의 칸 수, 칸 너비, 높이)을 끄는 동안 놓을 자리 아래에, 부품 고르기 카드에('이 장엔 자리가 없어요', 눌러서 까닭. 어느 부품도 못 넣으면 카드마다 붙이지 않고 위에 한 번), 도구 단추에 보인다. 그래도 글을 길게 쓰거나 파일에서 읽어 넘치면 `slides/fitBlocks.ts`가 줄 높이를 같은 비율로 낮추고(`--bk-sq`), 넘치는 칸의 글자를 단계로 줄인다(`--bk-fit`). 줄 높이는 1:1을 지키려고 글자를 먼저 늘 줄여도 되는 데까지(보통 크기는 줄이지 않고, 크게는 한 단계. 크게의 한 단계는 1/1.2라서 줄이면 꼭 보통 크기다) 줄이고, 그래도 넘치는 줄만 다른 줄이 잘리지 않을 높이까지 남는 높이를 가져온다(`--bk-r1..`, 줄마다의 잘리지 않을 높이는 본문 상자의 `data-mins`). 잰 높이는 보통 글자 크기라 크게나 명조에서 딱 그 높이면 모자랄 수 있다. 한 줄을 다 쓰지 않는 칸은 한쪽에 이음표가 선 너비(`LINK_PAD`만큼 좁게)로 잰다. 잴 때는 편집 표시(빈칸의 면, '이 항목 빼기', 그림 칸의 '바꾸기')를 뺀다(`.is-fitting`). 빼지 않으면 칸 옆으로 나온 단추를 넘침으로 보고 편집 화면에서만 글자를 줄인다. 넘침은 칸 밖뿐 아니라 카드의 안쪽 여백까지 내려간 글, 서로 겹친 글, 옆 항목 자리로 넘어간 글까지 본다(글자 자리는 글꼴마다 캔버스로 잰다). 편집 칸은 띄어쓰기를 그대로 두어(pre-wrap) 줄 끝 띄어쓰기가 칸 밖에 걸리는데, 그것은 글로 세지 않는다. 거꾸로 넘치는 칸이 없으면 모든 칸의 글자를 같은 단계로 키우고(한 단계, 1.2배), 그래도 칸에 높이가 남으면 줄이 쌓이는 부품(점 목록, 개요, 걱정과 대책, 준비 상황, 추진 일정, 평가표, 시장 규모, 맡은 사람 목록, 표)은 칸마다 줄 사이를 단계로 넓힌다(`--bk-air`, 줄 위아래에 최대 24px). 글자를 더 키우면 장마다 글자 크기가 들쭉날쭉하고, 가운데에 작게 모으면 위아래가 빈다. 키울 때는 글이 없는 그림(구성비 띠, 막대, 원)이 키우기 전의 반 밑으로 눌려도 넘친 것으로 본다(글이 없어서 넘침으로 보이지 않는다). 앱과 내보낸 HTML이 같은 함수를 쓴다. 발표할 때 움직이는 중인 장은 재지 않는다: 움직임 엔진이 움직이는 동안 `data-mo-play`를 붙이고 끝나면 떼며 `mo-end`를 보낸다. 그동안 글과 막대는 옮겨지거나 커지는 중이고 숫자는 0부터 굴러가는 중이라, 재면 움직이며 넘긴 장과 뒤로 돌아온 장의 글자 크기가 달랐다. 맞춘 값은 그대로 두었다가 끝나면 다시 맞춘다(처음 맞추기는 움직임이 걸리기 전이다). 안 보이는 장(내보낸 파일이 발표하는 동안 숨긴 장)은 맞춘 값을 지우지 않고 건너뛰고, 여백에 걸쳐도 되는 틈은 캔버스 px라 장을 그리는 크기와 상관없다.
- **놓을 자리 찾기(`dropTarget`):** 끄는 부품을 뺀 줄들을 기준으로, 손에서 가장 가까운 칸을 찾는다. 칸의 위아래 28%면 그 위나 아래에 새 줄, 왼쪽 오른쪽 반이면 그 옆자리. 거기 둘 수 없으면 둘 수 있는 자리 가운데 가장 가까운 곳. 경계에서 떨리지 않게 조금 옆에서 봐도 지금 자리면 바꾸지 않는다. 손이 지금 보이는 놓을 자리(파란 점선 칸) 안에 있으면 자리를 바꾸지 않는다: 자리 찾기는 끄는 부품을 뺀 모습으로 재는데 화면에는 놓을 자리를 넣은 모습이 보여서, 그 칸 안에서 손을 움직였는데 다른 데로 튀면 보이는 것과 놓이는 곳이 어긋난다.
- **끌기(`src/screens/editor/BlockEditor.tsx`):** 6px 움직이면 끌기 시작. 집어 든 부품은 손 아래 크기로 줄어 들리고 끄는 빠르기만큼 살짝 기운다. 놓일 자리에는 파란 점선 칸이 생기고 다른 부품이 미끄러져 비켜 난다(FLIP, 스프링). 놓으면 부품이 손에서 나와 제 비율 그대로 자리로 커지며 맞춰진다. 장 밖에 놓거나 Esc면 그만둔다. 끄는 동안은 저장하지 않고 놓을 때 한 번만 바꿔서 되돌리기 한 번이면 돌아온다.
- **부품 고르기(`BlockLibrary.tsx`, 화면 이름은 ‘컴포넌트’):** 오른쪽 칸의 탭 두 개(이 장 설정 / 컴포넌트) 가운데 하나. 탭을 바꿔도 칸 폭이 같아 슬라이드 크기가 출렁이지 않고, 지금 어디에 있는지와 어디로 돌아가는지가 늘 보인다. 오른쪽 칸을 접는 좁은 창(1100px 아래)에서만 슬라이드 아래 '컴포넌트 넣기'로 띄운다. 넣는 법은 탭 줄의 (i)에 접어 두고, 이 장이 컴포넌트 장이 아니면 상자 없는 한 줄 알림(‘넣으면 컴포넌트 장이 돼요’, ‘지금 바꾸기’). 묶음은 같은 폭으로 나눈 글자 칩 한 줄(전체, 글, 숫자, 차트, 일정, 비교, 이미지, 이음표)로 놓고, 목록에서는 묶음마다 긴 이름, 개수, 무엇이 들어 있는지 한 줄(`BLOCK_GROUPS`의 `short`, `description`). 카드는 예시 내용을 넣은 그림과 이름이고(테두리 상자 없이), 마우스를 올리면 그림이 떠오르며 발표할 때의 움직임을 한 번 보여 준다. 끌어다 놓거나, 누르면 알맞은 자리(`autoTarget`)에 카드에서 날아가 들어간다.
- **부품 장이 아닌 장에 놓으면** 그 장을 같은 내용의 부품 장으로 바꿔 넣는다(`composeFrom`, 글은 하나도 빠지지 않는다. 테스트가 모든 레이아웃을 확인). 예전에 부품 장이었던 장(부품이 여럿인 부품 장을 다른 레이아웃으로 바꾸면 줄은 장에 남겨 둔다)은 남겨 둔 줄을 되살린다. 장을 부품 장으로 바꾸는 곳(레이아웃 바꾸기, 부품 장으로 바꾸기, 끌어 넣기, AI 제안)은 모두 `asCompose` 하나를 쓴다. 따로 `composeFrom`을 부르던 AI 제안은 남겨 둔 줄을 덮어써 그 안의 글을 지웠다. 끄는 동안 바뀔 모습을 미리 보여 준다. 표지와 단락 장, 자리가 없는 장이면 다음 장에 부품 장을 새로 만든다. 레이아웃 부품 하나뿐인 부품 장은 그 레이아웃으로 되돌릴 수 있다(`unwrapCompose`).
- **내 컴포넌트(`deck/blocks/saved.ts`, `screens/editor/SavedParts.tsx`):** 조립해 둔 것을 다시 쓴다. 고른 컴포넌트의 도구 '내 컴포넌트로 저장'에서 그 컴포넌트, 그 줄(놓인 비율 그대로), 장 전체(제목 칸, 바탕, 움직임, 장 넘기기, 나오는 차례까지) 가운데 하나를 고른다. 글과 바탕, 나오는 때도 같이 간다. 컴포넌트 고르기 맨 위의 '기본 컴포넌트 / 내 컴포넌트'로 바꿔 본다. 컴포넌트 하나는 기본 컴포넌트와 같은 길(끌어다 놓기, 누르면 알맞은 자리)로, 한 줄은 이 장 맨 아래에, 장 하나는 이 장 다음에 새 장으로 넣는다. 넣을 때마다 부품, 줄, 항목의 id를 새로 만든다(`freshRows`). 기본 컴포넌트와 같은 규칙으로 막는다: 부품 수, 줄 수, 장 높이를 넘으면(`rowsIssue`) 카드가 흐려지고 까닭과 '다음 장에 새로 넣기'를 보인다. 작은 그림은 저장할 때 장에서 차지한 크기(`size`)로 그린다: 높이에 따라 짜임을 바꾸는 컴포넌트가 다른 높이로 그려지면 저장한 모습과 달라 보였다. 너무 넓적하면 줄 높이는 두고 위아래 여백만 늘린다. 저장한 것은 발표 밖에 두고 AI에게 보내지 않는다.
- **고른 부품의 도구:** 장 아래 도구 줄이 그 부품의 도구로 바뀌고 오른쪽에 '완료'(Esc)가 생긴다. 칸 위에 띄우면 제목이나 위 줄 부품을 덮어서다. 메뉴는 위로 열리고 Esc는 메뉴만 닫는다. 고른 부품에는 왼쪽 위에 이름표(끌기 손잡이)가 남는다. 끌어 옮기기(화살표 키로도), 바탕(없음, 옅은 면, 진한 면: 지금 바탕의 이름을 보이고 누르면 설명과 함께 고른다), 움직임(알아서, 올라오기, 나타나기, 펼치기, 밀려오기, 튀어나오기, 다가오기, 세우기, 초점 맞추기, 없음; 올리면 그 자리에서 미리 보기, 메뉴의 작은 그림도 같은 움직임), 모양, 항목 추가, 복제, 빼기(Delete). 칸 사이 손잡이를 끌면 정해진 비율에 붙는다. 줄 사이 손잡이를 끌면 위아래 두 줄이 높이를 나눠 갖고(24분의 1에 붙고, 잘리지 않을 높이 밖으로는 안 끌린다) 두 번 누르면 똑같이 되돌린다. 본문 위에 손을 올리면 두 손잡이가 옅게 보여 끌 수 있는 곳을 알린다. 새로 넣은 부품은 자리에 맞춰진 뒤 발표할 때의 움직임을 한 번 보여 준다(움직임 '없음'이면 안 한다).
- **이미지 넣기 (`screens/editor/useImageInput.ts`):** 화면 캡처를 붙여 넣거나(Ctrl+V) 이미지 파일을 장 위에 끌어다 놓으면 바로 들어간다. 이미지 컴포넌트를 먼저 찾아 넣고 칸을 눌러 파일을 고르던 길이 회사에서 가장 흔한 일(캡처해서 붙이기)에 너무 멀었다. 넣을 곳은 고른 이미지 컴포넌트, 비어 있는 이미지 칸(이미지와 설명 장의 이미지, 빈 이미지 컴포넌트), 그 밖에는 새 이미지 컴포넌트를 컴포넌트를 넣을 때와 같은 길로(자리가 없으면 다음 장). 끄는 동안 장에 테두리와 '놓으면 이 장에 이미지로 들어가요'가 뜬다. 이미지의 가로세로는 파일 머리에서 읽고(`lib/image.ts`의 `imageSize`: PNG, JPEG와 회전 정보, GIF, WebP, SVG), 놓을 자리는 이미지 비율에 가장 잘 맞는 곳(`imageTarget`: 세로 사진은 옆 칸으로, 넓은 캡처는 넓은 칸으로, 같으면 이미 쓴 내용 뒤에), 그 줄의 칸 너비도 이미지에 맞춘다(`fitImage`. 이미지 옆에 다른 컴포넌트를 넣거나 뺄 때도). 보이는 법은 사진(JPEG)이 칸과 비율이 비슷할 때만 꽉 채우기, 화면 캡처와 도면은 잘리지 않게 전체 보이기. 전체 보이기는 이미지 비율대로 가장 크게 그리고 모서리와 옅은 테두리를 이미지에 둔다(회색 판 위에 얹으면 그림 두 장을 겹친 것처럼 보였다). 설명은 이미지 바로 밑에 붙는다. 이미지 칸은 280px 밑으로 낮아지지 않는다(낮으면 캡처의 글씨를 못 읽는다).
- **움직임:** 부품을 읽는 차례대로 하나씩. '알아서'면 레이아웃 부품은 그 레이아웃의 연출을 그 칸 안에서, 부품 장만의 부품은 부품마다 짠 연출로(`src/motion/engine.ts`의 `block`).
- **이음표(`BLOCK_LINKS`):** 화살표, 더하기, 결과(=), 견주기(vs). 두 부품이 어떻게 이어지는지를 부품 사이에 끼워 보인다. 칸을 차지하지 않고 칸 사이에 서서, 칸 너비 비율과 칸 수 같은 자리 규칙은 그대로다. 같은 줄의 두 부품 사이(왼쪽 부품의 `link`)와 두 줄 사이(위 줄의 `link`)에만 서고, 줄의 끝과 마지막 줄 아래에는 없다(`tidyLinks`: 부품을 빼거나 옮겨 설 데가 없어지면 뺀다). 이음표가 선 사이는 양쪽 칸이 24px씩 비켜(`LINK_PAD`) 이음표가 혼자 서는 96px을 낸다. 칸의 면이나 가장자리에 걸치면 한쪽 칸에 가려 깨져 보여서다(조합 시험 `checkCombos`가 칸에 걸친 이음표를 찾는다). 줄 사이에 서면 위아래 줄이 그만큼 낮아져 잘리지 않을 높이에 더한다(`rowNeeds`). 칸 사이 이음표가 선 줄은 부품을 줄 가운데에 둔다(위에 붙이면 이음표만 아래에 떠 보인다). 색은 강조색이 아니라 글자색을 옅게 한 색이다(답이 아니라 관계라서). 부품 고르기의 '이음표' 묶음에서 끌어 칸 사이에 놓으면 가장 가까운 사이에 붙고, 양쪽 칸이 비켜 나는 모습을 미리 보여 준다. 누르면 고른 부품의 오른쪽(없으면 처음 빈 사이)에 들어간다. 장의 이음표를 누르면 도구 줄에서 모양을 바꾸거나 뺀다(Delete). 부품을 끌어 옮기면 그 부품 오른쪽의 이음표는 두고 간다. 발표할 때는 앞 부품이 나온 뒤에 나온다(화살표는 가리키는 쪽으로 밀려 나오고, 나머지는 튀어나온다). 안 비교 레이아웃의 화살표도 같은 모양과 색이고, 두 면 사이의 혼자 쓰는 자리(`--cp-mid`)에 선다.
- **글자:** 칸이 좁거나 낮으면 컨테이너 쿼리로 글자를 글자 크기 비율(1.2)의 단계로 줄인다. 반 칸, 3분의 1 칸이나 높이 300px 밑은 한 단계(0.84), 4분의 1 칸은 두 단계(0.7)이고, 높이로는 한 단계까지다. 좁고 낮아도 곱하지 않고 작은 쪽 하나만 쓴다. 곱하면 제목, 숫자, 본문이 모두 바닥(22px, `--fs-min`)까지 내려가 크기 차이가 없어진다. 한 줄에 부품이 둘 이상이면 넓은 칸도 옆 칸과 같은 단계로 둔다(`.is-shared`). 단계가 다르면 나란한 소제목의 크기가 어긋나 줄이 비뚤어 보인다. 같은 줄의 부품은 소제목 윗선을 맞추려고 모두 위에서부터 그리되, 줄 안에서 가장 긴 내용을 기준으로 묶음째 가운데로 내린다(`--bk-lift`, `fitBlocks.ts`). 위에만 붙여 두면 높은 줄에서 아래 절반이 통째로 비어 칸이 엉성하게 잡힌 것처럼 보인다. 글이 시작하는 선은 칸마다가 아니라 줄에 하나다: 옅은 면, 진한 면은 안쪽 여백만큼 글이 아래에서 시작하니, 옆 칸의 글도 그 선에서 시작한다(예전에는 강조 상자 옆의 핵심 한 줄이 칸 위에 붙고 면 안의 글만 내려가 있었다). 가장 낮은 줄에서 칸을 다 쓴 긴 글을 차트처럼 묶음에서 빼면 짧은 쪽만 내려가 소제목 윗선이 어긋났다. 내리지 않는 부품(차트, 표, 그림)은 묶음에 넣지 않고, 그 옆에서는 소제목 없는 짧은 부품(숫자, 강조 상자)만 가운데로 내린다. 차트 옆의 숫자가 칸 위에 붙으면 아래 절반이 비고, 차트 옆의 목록까지 내리면 차트의 소제목과 윗선이 어긋난다. 칸의 80% 넘게 쓰는 목록, 준비 상황, 묻고 답하기 옆에 소제목 없는 짧은 부품이 있을 때도 그 글 칸을 차트처럼 빼고 짧은 부품끼리 가운데로 내린다(짧은 부품이 위 3분의 1에 몰리고 아래가 비었다). 차트 옆의 숫자는 한두 단계 키우지만, 몇 중 몇과 비율 원처럼 자기 큰 숫자가 있는 그림 옆에서는 키우지 않는다(나란한 두 숫자의 크기가 달라진다). 넓고 낮은 칸에서 숫자 옆에 점을 눕힌 몇 중 몇은 스스로 가운데에 서므로 묶음에서 뺀다.
- **짜임 바꾸기:** 그보다 작은 자리에서는 글자를 더 줄이지 않고 부품이 짜임을 바꾼다(공개 디자인 시스템의 '흘리기, 쌓기, 모양 바꾸기', [OPEN-SOURCE.md](OPEN-SOURCE.md)). 넓고 낮으면 목록을 여러 단으로 흘리고(개요, 준비 상황, 맡은 사람, 목차, 도넛의 비율 목록, 한 줄을 다 쓰는 지표 흐름표의 넷 이상) 쌓인 것을 옆으로 눕힌다(큰 숫자는 숫자 오른쪽에 이름과 설명, 전과 후도 두 숫자 오른쪽에 이름과 덧붙임 글. 한 줄을 다 쓰는 넓은 칸(1200px 넘고 높이의 두 배 넘게 넓은)에서는 거꾸로 이름과 설명을 격자의 왼쪽 4칸에, 숫자를 5번째 칸부터 둔다: 숫자 옆에 이름을 붙이면 묶음이 왼쪽에 몰려 오른쪽 절반 넘게 비었고, 격자 선에 맞추면 위아래 줄의 칸 나눔과도 줄이 맞는다. 숫자와 흐름은 숫자 옆에 선, 강점과 약점은 네 칸 한 줄, 2×2 우선순위는 칸마다 이름 옆에 설명, 맡은 사람 나란히는 한 단이 460px 남짓 넘으면 동그라미 옆에 이름. 위아래로 쌓으면 사람마다 제 단의 왼쪽 반만 써서 한 줄을 다 쓰는 세 사람이 칸 왼쪽에 몰렸다). 좁고 높으면 나란한 것을 줄로 쌓는다(핵심 숫자, 하나 크게의 나머지 숫자, 목차 나란히): 나란히 두면 숫자가 칸의 3분의 1 너비에 맞춰 작아지고 칸 높이 가운데에 낮은 띠만 남는다. 줄로 쌓으면 줄이 칸 높이를 나눠 채우고, 줄이 넉넉하면 이름을 숫자 위에 두어 숫자가 칸 너비를 다 쓴다. 핵심 숫자 부품의 숫자는 나란한 것끼리 한 크기이고, 그 크기는 가장 긴 숫자가 들어가는 글자 크기 단계에서 고른다(칸 너비로 그대로 줄이면 단계 밖의 크기가 된다). 두 단으로 바꾸는 높이는 항목 수마다 한 단으로 들어가는 가장 낮은 높이 바로 위로 잡는다. 그보다 낮게 잡으면 그 사이 높이에서는 어느 쪽으로도 들어가지 않는다. 두 값 비교의 막대 한 쌍이 좁으면(150px 밑) 발표할 때 앞 값 숫자를 빼고 뒤 값 숫자를 막대 한 쌍의 너비로 키운다(막대마다 숫자를 둘씩 달면 14px까지 작아졌다). 앞 값끼리, 뒤 값끼리는 가장 긴 숫자에 맞춘 한 크기다. 편집할 때는 앞 값도 고칠 수 있게 그대로 둔다. 줄이 쌓이는 부품(막대, 목차, 비교)은 줄 안에 위아래 여백을 두어, 낮은 칸에서도 숫자와 선이 붙지 않고 잰 높이도 그 여백까지 든다. 그래도 안 되는 자리는 편집기가 고르지 않는다.
- **AI:** 부품 장의 모양(부품의 해시 id, 종류, 너비, 모양, 바탕, 움직임, 나오는 때와 빠르기와 쪽, 나오는 차례, 칸이 찼는지)만 본다. 사람처럼 짜임을 바꾸자고 제안할 수 있다: 빈 부품 넣기(`add_block`), 옮기기(`move_block`, 글은 부품과 함께), 빈 부품 빼기(`remove_block`), 모양·바탕·움직임·나오는 때·빠르기·들어오는 쪽·항목 수·강조(`set_block`), 나오는 차례(`set_order`, 부품 해시 id만), 한 줄의 너비(`set_spans`), 이음표(`set_link`, 모양 파일의 `link`와 `rowLinks`), 부품 칸의 안내 문구(`set_hint`의 `block`). 장을 부품 장으로 바꾸거나 되돌리는 것(`set_layout`)은 편집기와 같은 규칙(`asCompose`, `unwrapCompose`)이다. 놓을 자리와 높이는 편집기에서 끌어다 놓을 때와 같은 규칙(`whyNot`, 부품마다 잰 높이)으로 보고, 장에 들어가지 않으면 `no_room`으로 건너뛴다. 부품 안의 글은 쓰지 못한다. 부품이 있으면 빈 장이 아니라 지우지 않는다.

## 6. 디자인 시스템 (슬라이드)

**콘셉트: 조용한 본문, 분명한 시작.** 표지는 결정 요청 칸을 짙은 면으로 강하게. 단락 장과 마지막 장은 본문과 같은 바탕에 큰 번호와 큰 글씨로(색 면은 고르는 모양). 흰 장 사이에 짙은 장이 툭 끼면 장마다 무게가 달라 보인다. 본문 장은 흰 여백, 좌측 정렬, 큰 제목으로 조용하게.

테마 2종: 바탕은 흰색 아니면 검은색. 크림색처럼 색이 있는 바탕은 낡고 무거워 보여서 쓰지 않는다. 강조색은 고르거나 브랜드 색으로 직접 고를 수 있다. 흰 테마의 짙은 면은 검정이 아니라 강조색을 깊게 가라앉힌 색이다(코발트면 짙은 남색). 새까만 면은 흰 장 사이에서 너무 세고, 아무 색도 없는 표지는 밋밋하다. 흰 바탕, 짙은 남색 면, 강조색 하나는 보고 자료에서 오래 쓰인 짝이다.

| 테마 | 배경 | 글자 | 강조 | 짙은 면 | 제목 서체 |
|---|---|---|---|---|---|
| 화이트 | #FFFFFF | #16171A | #2F55D4 (코발트) | 강조색과 #0A0D16을 반씩 (코발트면 #1D3175) | Pretendard 700 |
| 블랙 (id `navy`) | #000000 | #F4F4F5 | #6B93FF (하늘) | #222327 (한 단계 뜬 검정) | Pretendard 700 |

- 예전의 세리프 테마(id `serif`)는 고르는 목록에서 뺐다. 열면 화이트에 명조 제목(`font: 'serif'`)으로 바꾼다(`plainTheme`). id는 예전 버전과 주고받는 파일 때문에 그대로 둔다.

**색.** 공개된 색 체계의 원칙을 따라 우리 값으로 골랐다(값을 옮겨 오지 않았다).

- 역할을 나눈다: 강조색은 '답'(큰 숫자, 고른 막대, 점)에만, 넓은 면(표지 옆면, 진한 면 부품, 추천안, 색 면 단락 장)은 짙은 면(`--bold-bg`, `themes.ts`의 `deepOf`), 그 위의 강조는 강조색을 밝힌 색(`--bold-accent`, 4.5:1). 검은 테마에서 장 전체를 덮는 짙은 면(단락 장, 마지막 장, 색 면 표지)은 바탕과 같은 검정이고, 옆면, 카드처럼 일부만 덮는 면만 한 단계 뜬 검정이다.
- 맥락은 회색, 말하려는 한 곳만 색 (Datawrapper의 차트 색 안내). 작년, 다른 조각, 뺀 요인은 회색 단계.
- 회색은 색을 섞지 않은 중립 회색이다. 강조색을 바꿔도 회색이 따로 놀지 않는다.
- 가장 옅은 글자(`--ink-3`: 단위, 출처, 머리말)도 바탕에서 4.5:1, 카드 면(`--surface`)에서 4:1을 넘긴다. 22px 글자가 프로젝터에서 바래면 3:1로는 읽히지 않는다. 검은 테마의 짙은 면은 카드 면(#141517)보다 한 단계 더 떠서, 카드 모양과 짙은 면 모양이 같은 색으로 보이지 않게 한다.
- 강조색(`ACCENT_COMBOS`) 9개(코발트, 하늘, 청록, 숲, 남보라, 자두, 벽돌, 황토, 먹). 두 바탕과 장의 바탕 셋에서 맞춰 보고 골랐다.
- 강조색은 바탕에서 읽히게 저절로 밝히거나 어둡게 한다: 흰 바탕은 3:1, 검은 바탕은 4.5:1(짙은 색은 검정 위에서 3:1을 넘겨도 가라앉아 흐려 보인다).
- 검은 바탕의 로고 모음은 밝은 판을 깔지 않고 로고를 흑백으로 뒤집어 밝게 한다(`invert` + `screen`). 표지, 사례의 회사 로고 하나는 색을 살려 밝은 판 위에.
- 섞을 때는 sRGB. oklch로 섞으면 색상이 먼 둘 사이에서 주황으로, 회녹색이 분홍으로 틀어진다.

- 서체: 기본은 모두 Pretendard. 테마 메뉴의 '글꼴'에서 맞춰 본 짝 넷 가운데 하나를 고른다(`themes.ts`의 `FONTS`): 프리텐다드(제목과 본문), SUIT(제목과 본문), 명조 제목(Hahmlet 제목 + Pretendard 본문), 본명조 제목(Noto Serif KR 제목 + Pretendard 본문). 모두 SIL OFL 1.1이고 앱과 내보낸 파일에 들어 있어 윈도우에서도 같다. `word-break: keep-all`, 제목 `text-wrap: balance`, 큰 제목은 자간을 좁게.
  - 제목과 본문을 따로 고르게 하지 않는다. 비슷한 고딕 둘을 섞으면 어긋나 보이고, 본문까지 명조면 회의실 화면에서 읽기 어렵다. 짝으로만 고르면 어느 것을 골라도 보기 좋다.
  - 명조는 제목(과 큰 숫자)에만 쓴다. 본문은 획이 고른 고딕이 화면에서 잘 읽힌다.
  - 글꼴마다 굵기의 느낌이 다르다. 장의 굵기(본문 400, 이름표 600, 제목 700)는 Pretendard에 맞춰 정했고, SUIT는 같은 굵기에서 한 단계 가늘어서 굵기마다 한 단계 굵은 파일을 잇는다(`src/fonts/suit.css`).
  - 고른 글꼴에 없는 글자는 Pretendard로 그린다(글꼴 목록 끝에 늘 Pretendard). SUIT에는 자주 쓰는 한글 2,350자 남짓만 있다.
  - 글꼴마다 다른 값(글꼴 높이와 한글 윗선 `box`, `gap`, 숫자 폭 `glyph`, 큰 숫자 줄 높이 `tall`)은 `FONT_LOOK`에 캔버스로 잰 값으로 둔다. 단락 번호의 끝자리 숫자 옆 빈칸은 `styles/section.css`의 `.f-<글꼴> .sc-num`. 새 글꼴을 더하면 갤러리 `&font=<id>`로 `checkFrame()`, `checkCombos()`를 보고, 부품 높이 표를 그 글꼴로도 재어 높은 쪽을 쓴다(`blockHeights.ts`).
- 타입 스케일(1920 기준): 한 비율(1.2)의 단계 22 · 26 · 30 · 36 · 44 · 52 · 62 · 74 · 90 · 108 · 128 · 154 · 184 · 220 · 264에서만 고른다. 장 제목 62(31pt), 부제 36, 칸 제목 36, 본문 30(15pt), 보조 26, 출처 22. 표지와 한 문장 메시지 90, 큰 숫자 108~264. 단계 밖의 크기를 섞으면 비슷한 글끼리 몇 px씩 달라 위계가 흐려진다. 예전에는 40가지 넘는 크기를 썼고 제목 72, 본문 34로 보고 자료치고 커서 장이 꽉 차 보였다. 22는 회의실 뒷자리에서 읽히는 바닥이라 작은 글은 거의 줄이지 않고 큰 글을 더 줄였다. 보내는 자료(`d-read`)는 한 단계씩 작게(제목 52, 본문 26).
- 틀: 모든 장은 같은 틀 안에 그린다. 좌우 120(`--pad-x`), 위아래 72(`--pad-y`)로 왼쪽과 오른쪽, 위와 아래가 각각 같다. 제목(과 부제) 아래에서 본문 상자까지는 72(`--body-gap`)로 레이아웃 장과 부품 장이 같아서, 장을 넘겨도 본문 윗선이 움직이지 않는다. 줄 선은 한 굵기(`--rule`, 2)라 레이아웃 부품과 다른 부품을 한 장에 놓아도 선이 섞이지 않는다. 위아래는 글자가 실제로 그려진 선으로 맞춘다: 위는 제목 글자의 윗선, 아래는 하단 표시(단락 밑줄)의 아랫선이 틀선에 닿는다. 줄 높이의 빈 위아래까지 상자로 맞추면 큰 제목이 있는 위는 넓고 작은 하단 표시가 있는 아래는 좁아 보인다(예전에는 위 111, 아래 35로 보였다). 글꼴마다 글자 위 빈칸이 달라서 테마가 글꼴 높이와 한글 윗선의 자리(`--head-box`, `--head-gap`, `themes.ts`)를 넘기고, 틀선에 닿는 글(제목, 표지의 결정 요청과 발표자, 마지막 장의 제목과 연락처, 단락 목록)은 그만큼 당긴다. 단락 번호처럼 큰 숫자는 숫자마다 글자 옆 빈칸이 달라 끝자리 숫자마다 당긴다. 장 끝까지 깐 바탕과 옆면(표지의 결정 요청 면, 사례의 결과 면, 그림 면)은 틀이 아니지만, 그 안의 글과 그림은 틀 안에 있다. 하단 표시는 단락 밑줄이 없는 장(요약, 순서)에서도 같은 자리에 있어서, 넘길 때 아래 줄이 움직이지 않는다. 본문 상자 아래는 하단 표시, 24 띄우고 출처 한 줄, 본문과 28. 코드에서 본문 상자를 어림할 때는 `deck/frame.ts`(CSS와 같은지 `frame.test.ts`가 본다). 틀을 벗어난 장이 없는지는 갤러리 콘솔의 `checkFrame()`으로 잰다(글자와 그림이 그려진 선으로).

**숫자의 꼴.** 공개된 조판과 데이터 시각화 안내(시카고 매뉴얼의 빼기 기호 문답, Butterick의 Practical Typography, 세계은행 데이터 시각화 스타일 안내, 대시보드 디자인 시스템의 '큰 값 작은 단위' 패턴)의 원칙을 따라 정했다(글을 옮겨 오지 않았다). 모두 그릴 때만 바꾸고 저장한 글은 그대로다(`slides/fields.tsx`의 `Shown`, `paint`).

- 나란한 숫자는 한 크기: 핵심 숫자처럼 같은 줄에 놓인 숫자는 가장 긴 값에 맞춘 크기 하나를 같이 쓴다(`useSharedUnits`). 칸마다 따로 맞추면 '40%'는 크고 '1,200시간'은 작아져 숫자의 크기가 값의 크기처럼 읽힌다. 칸의 너비도 모두 같아야 해서, 칸 사이 나누는 줄은 칸 안쪽 여백이 아니라 칸 사이 틈 가운데에 그린다. '하나 크게'의 첫 숫자만 따로 크다. 컴포넌트 '전과 후'도 전과 후를 같은 크기로 두고 전은 옅게, 후는 강조색으로 가른다. 바뀐 만큼(▼ 2.1%p)은 결과인 후 바로 아래에 붙는다.
- 숫자와 단위: 큰 숫자(핵심 숫자, 사례의 성과, 안 비교의 비용)는 뒤의 단위('%', '시간', '억 원')를 두 단계(1/1.44) 작게, 같은 바탕선에 둔다(`.slide .u`, `UNIT_K`). 한글 단위는 숫자만큼 넓고 무거워서 같은 크기면 답보다 단위가 먼저 읽힌다. 숫자 하나와 짧은 단위의 꼴('3.6시간', '−3%', '2~3배')만 나누고, '3년 6개월', '약 30억 원'처럼 그 꼴이 아니면 그대로 그린다. 편집할 때도 같은 꼴로 보이지만 칸의 글자는 하나도 바뀌지 않는다.
- 빼기 기호: 숫자 앞의 붙임표(-)와 줄표(–)는 빼기 기호(−, U+2212)로 그린다. 붙임표는 소문자 높이에 맞춘 짧은 선이라 숫자 옆에서 낮고 짧다. 날짜('2026-10-25'), 번호('A-1'), 범위('3-4월')의 붙임표는 그대로다(`minusSigns`).
- 숫자 폭: 혼자 크게 서는 숫자(핵심 숫자, 사례 성과, 비용)는 비례폭 숫자로 글자 사이를 고르게, 위아래로 쌓여 자리를 맞춰 읽는 숫자(표, 지표표, 막대 값, 비중, 진행률, 일정의 시기)는 고정폭 숫자(`tabular-nums`)로.

**계산할 때의 숫자 읽기.** 값 둘 이상으로 계산하는 곳(전과 후의 바뀐 만큼, 목표 대비 실적과 목표 대비의 달성률, 몇 중 몇, 증감 요인의 끝 값, 구성비의 비중과 합계, 깔때기 전환율, 두 값 비교의 차이, 기간별 달성, 원인 순위, 쌓은 막대, 색 표, 지표 흐름표)은 모두 `slides/numbers.ts`의 해석기(`readAmount`, `amountPair`, `changeOf`, `seriesIn`)로 읽는다. 예전에는 글에서 숫자만 뽑아서 '6분 → 40초'가 ▲ 567%로, '1.2억 원 → 8,000만 원'이 크게 는 것으로 나왔다. 틀린 숫자는 듣는 사람이 그대로 믿는다.

- 큰 수의 자리(조, 억, 만, 천, '3천만', '1억 2,000만 원')와 시간(초, 분, 시간, 일, 주, 개월, 년, '1시간 30분'), 무게, 길이, 용량은 같은 바탕 값으로 바꿔 견준다. '이상', '이내', '정도' 같은 덧말은 떼고 읽는다.
- 견줄 수 없는 두 값('3건 → 40%', '2명 → 5대', '6분 → 40')은 계산한 숫자와 화살표를 보이지 않는다. 틀린 것을 보여 주느니 안 보여 주는 게 낫다. 단위가 %인 두 값의 차이는 %p로 적는다.
- 한 그림의 값은 보통 같은 단위로 적고 몇 개에만 단위를 붙인다. 그래서 숫자만 적은 값은 단위를 적은 값이나 단위 칸의 단위로 읽는다('117억, +9, −2'). 서로 다른 단위 무리가 섞이면 막대는 적은 숫자대로 그리되 계산한 숫자(달성률, 전환율, 합계, 끝 값)는 보이지 않는다.
- 숫자가 둘 이상인 글('3~5일', '2024년 120억')은 값으로 읽지 않는다. 진행률, 비율 원, 위치 비교의 점수처럼 칸 하나로 그리는 값은 단위와 상관없이 적은 숫자 그대로다.

**나란한 칸은 한 틀, 본문은 끝까지.** 칸이 나란한 레이아웃(핵심 숫자, 단계 흐름, 일정, 세로 칸 요점)은 이름, 숫자, 설명 줄을 모든 칸이 같이 쓴다(CSS subgrid). 한 칸의 이름이 두 줄이 되어도 옆 칸의 설명이 따라 내려가 줄이 맞는다. 장 한 장을 다 쓸 때는 작은 띠가 본문 가운데에 뜨지 않게 짠다.

- 단계 흐름: 단계는 같은 너비의 칸이고, 위의 선은 칸 왼쪽 끝에서 글의 틈 앞까지 긋는다(선 사이의 틈이 단계 사이). 선 줄은 본문 윗선에, 담당과 시간은 칸마다 선을 하나 두고 본문 아래 끝 줄에 둔다. 설명은 이름 바로 아래 한 덩이. 담당과 시간이 하나도 없으면 띠를 가운데에 둔다. 칸 모양은 칸을 본문 높이만큼 세운다. 단계 수(3, 4, 5–6)마다 글자를 한 단계씩.
- 핵심 숫자: 나누는 줄은 본문 위아래 끝까지, 이름과 숫자와 설명은 칸 안의 눈높이(가운데보다 조금 위)에.
- 일정(가로)과 세로 칸 요점: 내용이 적어도 띠가 낮지 않게 글자를 한 단계씩 키운다(일정은 시기를 가장 크게).
- 핵심 포인트: 장 한 장에 포인트가 서넛뿐이면 이름과 설명을 한 단계씩 키운다(줄마다 높이의 반 넘게 비어 글이 작아 보였다). 타일은 이름을 면의 위에 크게, 설명을 면의 아래 끝에 둔다(포스터처럼). 이름이 작으면 면 가운데가 비어 빈 상자처럼 보였고, 한 면 안이라 둘이 떨어져 있어도 한 덩이로 읽힌다. 보내는 자료는 한 단계 작게.
- 단락 번호: 두 모양 모두 오른쪽 아래에 아주 크게(600px), 획은 가늘게(200) 둔다. 바탕 모양은 옅은 글자색(`--ink-3`, 반복 표시라 강조색이 아니다), 색 면은 밝힌 강조색. 굵은 강조색 번호를 제목 위에 얹은 꼴은 흔한 단락 장 서식처럼 보였다. 숫자의 오른쪽 끝을 틀선에 맞추는 빈칸 값은 굵기 200에서 다시 쟀다(SUIT는 400부터라 400).
- 마지막 장의 요청 번호: 요청 제목과 같은 크기, 같은 글자선에 가늘고 옅게(`--ink-3`) 왼쪽에 둔다. 강조색 동그라미에 넣은 번호는 흔한 서식처럼 보였다. 요청은 제목과 설명 두 줄이라 번호를 앞에 둔다(한 줄짜리 목차는 오른쪽 끝).
- 목차: 항목 몇 개뿐인 장이라 글이 곧 장의 그림이다. 목록은 줄이 본문 높이를 고르게 나눠 채우고, 이름은 항목 수(2–3, 4, 5, 6)마다 한 단계씩 크게(90–52px) 왼쪽에, 번호는 같은 크기로 가늘고 옅게(글자색 `--ink-3`) 줄 오른쪽 끝에 둔다. 번호를 이름 앞에 작은 강조색으로 두면 흔한 서식 목록으로 보였고, 이름만 왼쪽에 있으면 줄 오른쪽이 비었다. 나란히는 제목을 단락 장처럼 크게(108px) 두고, 칸마다 위에 굵은 선을 그은 띠(번호, 이름)를 본문 바닥에 앉힌다. 띠를 가운데에 두면 짧은 이름 몇 개가 낮게 떠 보였다. 발표할 때는 선을 왼쪽부터 긋고(나란히는 칸마다 이어서) 이름이 올라온 뒤 번호가 뜬다. 부품 칸의 나란히는 좁은 칸에서 다섯, 여섯이면 셋씩 두 줄로, 좁고 높으면 목록처럼 줄로 쌓는다.
- 이 짜임은 `.l-<레이아웃>` 규칙에만 있다. 부품 장의 레이아웃 부품은 기본 규칙을 그대로 써서 잰 높이 표(`blockHeights.ts`)가 바뀌지 않는다.

**사용자가 고르는 것.** 글상자를 끌어 옮기는 대신, 아래를 고르면 시스템이 배치한다. AI도 같은 선택지 안에서만 제안한다.

| 어디서 | 고르는 것 |
|---|---|
| 테마 메뉴 (발표 전체) | 테마(화이트/블랙), 강조색(또는 직접), 글꼴(프리텐다드/SUIT/명조 제목/본명조 제목), 글자 크기(작게/보통/크게: 크게는 글자 크기 단계를 하나 올린 1.2배), 아래 표시(섹션만/섹션과 쪽 번호/쪽 번호만/숨기기), 움직임, 장 넘기기 |
| 이 장 설정 (장마다) | 레이아웃, 모양, 강조할 항목, 바탕(바탕/반대 색/강조색), 이 장의 움직임, 두 판으로 나뉜 장이면 옆 판의 자리(왼쪽/오른쪽)와 너비 |
| 장 위에서 끌기 | 항목의 순서(손잡이), 옆 판의 자리와 너비(판의 이름표, 판 사이), 부품 장의 부품(5-1) |

- 바탕 '반대 색'은 밝은 테마에서 어둡게, 어두운 테마에서 밝게 바꾼다. 강조색은 그 바탕에서 읽히도록(3:1 이상) 저절로 밝히거나 어둡게 한다.
- 표지, 섹션, 결정 요청은 모양(표지: 옆 면/아래 띠/색 면, 섹션과 결정 요청: 바탕/색 면)으로 면을 고르므로 장의 바탕은 바꾸지 않는다.
- 색 면(`--bold-bg`)은 쨍한 강조색이 아니라 강조색을 깊게 한 색이다(위 '색'). 쨍한 강조색은 차트의 강조 막대, 점, '추천' 표처럼 작은 곳에만 쓴다. 안 비교의 추천안, 단계 흐름의 강조 단계, 진한 면 부품처럼 넓은 면도 짙은 면으로 칠한다(검은 테마는 한 단계 뜬 검정에 강조색 테두리).
- 번호는 실제 순서가 있는 곳(목차, 일정, 섹션, 다음 단계)에만 쓴다.

**장 모음 (`#/system`).** 디자인 시스템을 한 화면에서 본다. 색 견본(짙은 면처럼 섞어 만든 색도 실제 장과 같은 조건에서 읽는다), 글자 크기, 장의 바탕 세 가지, 그리고 모든 레이아웃의 모든 모양을 쓰임 묶음(`LAYOUT_GROUPS`)대로 늘어놓는다. 테마, 강조색, 예시 내용/빈 칸을 바꾸면 모두 함께 바뀐다. 홈의 '장 모음 보기'와 장 추가 메뉴의 '모든 장을 그림으로 보기'(새 탭)에서 연다. 예시 내용은 `src/deck/showcase.ts`의 지어낸 값이고, 저장된 발표는 읽지 않는다. 새 레이아웃을 넣으면 묶음 하나에 넣고 예시 장을 채운다(테스트가 확인한다).

## 7. 편집기 UX

```
┌───────────────────────────────────────────────────────────────────────┐
│ ‹ [발표 제목]   저장됨                         AI  테마  내보내기  [발표하기] │
├──────────┬───────────────────────────────────────────┬────────────────┤
│ 1 표지    │     [⠿ 숫자 2 | ‹ › | ★강조 | ⧉ 🗑]          │설정 | 움직임 | 컴포넌트│
│ 2 핵심요약 │   ┌─────────────────────────────────┐   │ [그림] 레이아웃    │
│ 3 …      │   │  슬라이드 (바로 눌러서 입력)        │   │        바꾸기 ›  │
│          │   └─────────────────────────────────┘   │ ● 빈칸 3곳 다음 빈칸│
│ + 장 추가 │  [AI로 다듬기][모양][+항목]  [미리 보기][▶][⧉][숨김][🗑] │ 모양 / 꾸미기     │
│          │  발표자 노트                                │                │
└──────────┴───────────────────────────────────────────┴────────────────┘
```

- **앱 화면의 디자인 시스템:** 슬라이드의 디자인 시스템(6장, `#/system`)과 따로, 편집 도구 화면은 조용한 회색 바탕에 선택만 파란색(`--sel`)을 쓴다. 값은 `src/styles/base.css` 맨 위의 변수(`--app-bg`, `--panel`, `--line`, `--ink`~`--ink-3`, `--sel`, `--sel-soft`, 마우스를 올린 것의 `--hover`/`--hover-2`, `--r-sm`/`--r`/`--r-lg`, `--shadow-pop`)만 쓴다(앱 화면의 CSS는 `app.css`가 `src/styles/`의 화면별 파일을 정한 차례로 가져온다). 부품은 같은 것을 같은 모양으로: 단추(`.btn`, `.btn-ghost`, `.btn-sm`, 그림만 있는 `.icon-btn`), 고르기(`.seg`, 칸을 다 쓰면 `.seg-fill`. 고르는 단추는 줄을 바꾸지 않는다), 말풍선(모든 `title`, `screens/tooltip.ts`), 접어 둔 설명((i) `Info`), 팝오버(`Popover`), 켜고 끄기(`Toggle`). 설명 글은 화면에 늘어놓지 않는다: 필요한 설명은 (i)나 말풍선에, 그림만 있는 단추는 `title`에 하는 일을 적는다(끝에 괄호로 단축키를 붙이면 옅게 따로 보인다).
- **이 장 설정(오른쪽 칸):** 늘 보는 것만 한 화면에 둔다. 지금 레이아웃(그림, 이름, '바꾸기'), 빈칸 줄('빈칸 N곳', '다음 빈칸'을 누를 때마다 빈 칸으로 차례로, 목록은 펼쳐야), 모양(그 레이아웃의 모양 그림, 강조할 항목, 옆 판의 자리와 너비), 꾸미기(바탕). 레이아웃 목록은 '바꾸기'를 눌러야 따로 열리고(돌아가기 줄, Esc), 그림에 마우스를 올리면 슬라이드 자리에 그 레이아웃으로 미리 보인다(누르면 바뀐다). 장마다 무엇을 쓰면 되는지(`slide.guide`)는 왼쪽 목록의 장 이름 말풍선에 둔다.
- **움직임(오른쪽 칸의 둘째 탭, `editor/MotionPanel.tsx`):** 이 장의 미리 보기, 움직임 정도, 장 넘기기(이어 움직이기 포함), 그리고 부품 장이면 나오는 차례. 차례 목록은 '장이 나올 때', 'N번 누르면'으로 묶어 보이고, 끌어서 차례를 바꾼다. 줄을 누르면 장 위에서도 그 컴포넌트가 골라지고(장 위에서 고르면 목록의 그 줄이 펼쳐진다), 움직임, 언제, 들어오는 쪽, 빠르기를 고르면 그 컴포넌트만 바로 한 번 움직여 보인다. 시간 막대는 두지 않는다: 비개발자가 밀리초를 맞추게 하지 않고, 고른 값으로 엔진이 시간을 정한다([MOTION.md](MOTION.md)).
- **장 위에서 고른 것의 도구 (`editor/SelectionBar.tsx`):** 레이아웃 장에서 칸을 누르면(키보드로 들어가도) 그 칸이 든 항목이나 옆 판을 파란 테로 두르고 바로 위에(위에 자리가 없으면 안쪽 위에) 도구 막대를 띄운다. 항목: 이름(끌면 순서 바꾸기), 앞뒤로(가로 목록은 왼쪽·오른쪽, 세로 목록은 위·아래), 강조(레이아웃에 강조가 있으면), 복제, 빼기. 옆 판: 이름(끌면 옮기기, 판의 이름표에 넘긴다), 반대쪽으로, 아래로(표지), 좁게·넓게. 제목 덩어리(표지, 섹션의 제목과 부제, `LayoutSpec.place`): 이름을 잡고 위아래로 끌면 덩어리가 놓이는 칸 위에 세 자리(위, 가운데, 아래)가 보이고 손이 있는 자리로 바로 옮겨 가 놓으면 붙는다(`options.place`, Esc는 처음 자리로, 한 번 끈 것은 되돌리기 한 단계). 위·가운데·아래 단추로도 고른다. 표지에서 제목을 위로 올리면 로고는 아래로 비켜 주고, 색 면 섹션은 큰 번호를 아래에 둔 채 제목만 올린다. 글상자를 아무 데나 놓게 하지 않고 세 자리에만 붙이는 것은 줄과 여백, 글자 윗선·아랫선이 틀에 맞게 하려고다. 그 밖의 칸: 무슨 칸인지와 '모양'. 막대가 떠 있으면 항목 모서리의 손잡이와 빼기, 판의 이름표는 숨긴다(같은 일이 두 번 보이지 않게). 부품 장의 부품은 부품마다 자기 도구(이름표와 아래 도구 줄)가 있다.
- **슬라이드 아래 단추:** 'AI로 다듬기'(고르는 부탁), '모양'(그 레이아웃의 모양을 그림으로 보고 고르기. 예전의 '다른 모양'은 누를 때마다 다음 모양으로 넘어가 무엇이 나올지 몰랐다), 항목 추가 / 미리 보기, 지금 장부터 발표, 복제, 발표에서 빼기, 지우기. 자리가 모자라면 오른쪽부터 글자를 숨기고 그림만 남긴다(이름은 말풍선으로).
- **슬라이드 모드:** 슬라이드 위 글자를 바로 클릭해서 고친다. 빈칸에는 회색 안내 문구와 옅은 면이 보이고, 쓰는 중에는 면 대신 파란 실선 하나(`.ed-halo`, 점선 상자는 쓰지 않는다). 면은 글보다 조금 넓게 깔되 이웃한 칸, 항목, 부품 칸 끝을 넘지 않는다(`slides/halos.ts`). 서식은 없다(붙여넣기도 글자만).
- **문서 모드:** 모든 장의 칸을 문서처럼 한 화면에서 이어서 쓴다. 옆의 작은 슬라이드가 실시간으로 바뀐다. 많이 채울 때 빠르다.
- **장 추가:** 레이아웃을 쓰임 묶음(결론과 메시지, 숫자와 차트, 진행과 계획, 비교와 선택, 자료와 사례, 시작과 끝)으로 나눠 보여 준다.
- **빈칸 확인:** 장마다 빈칸 표시. 발표 전에 빈칸이 남았으면 알려준다.
- **항목 순서 바꾸기:** 항목(카드, 줄, 단계, 막대)에 손을 올리면 왼쪽 위에 손잡이가 보인다. 끌면 순서가 바로 바뀌어 그려지고(이웃은 미끄러져 비켜 난다, `slides/itemDrag.ts`), 끄는 항목의 가운데가 다른 항목 상자에 들어갔을 때만 자리를 바꾼다(크기가 다른 이웃 사이에서 떨지 않게). Esc는 처음 순서로, 한 번 끈 것은 되돌리기 한 단계. 손잡이에서 화살표 키로도 옮긴다. 사람이 고른 강조는 그 항목을 따라가고(`followIndex`), 고르지 않은 강조(마지막 항목 같은 자리로 정한 것)는 자리에 남는다. 자리로 그리는 장(포지셔닝)은 끌지 않는다.
- **옆 판 옮기기 (`slides/panes.tsx`):** 두 판으로 나뉜 장(표지의 옆 면, 사례의 결과, 이미지와 설명의 이미지, 결정 요청의 요청 목록, `LayoutSpec.panes`)은 판 위쪽 가운데의 이름표를 끌어 반대쪽으로 옮기고(`options.flip`), 판 사이를 끌어 너비를 고른다(`options.pane`, 장 너비를 12로 나눈 칸 수 가운데 레이아웃이 정한 값; 끄는 동안 고를 수 있는 너비마다 점선과 이름이 보이고 놓으면 가장 가까운 값에 붙는다. 두 번 누르면 기본 너비). 표지는 아래쪽으로 끌면 아래 띠 모양이 된다. 글상자를 마음대로 놓게 하지 않는 것은 그러면 줄과 여백이 어긋나고 글이 잘려서다. 끄는 판은 손을 따라오고, 놓으면 다른 칸이 새 자리로 미끄러진다. 오른쪽 칸(이 장 설정)에서도 같은 값을 고른다.
- **되돌리기:** Ctrl/⌘+Z, 타이핑은 묶어서 한 단계.
- **자동 저장:** 고칠 때마다 저장된다. 따로 누를 저장 단추는 없고, Ctrl/⌘+S는 기다리지 않고 바로 저장한다(알림으로 알린다). 위쪽의 저장 상태(폴더에 저장됨 / 이 브라우저에만 저장됨 / 폴더 저장 멈춤)에 마우스를 올리면 그 말이, 누르면 어디에 저장되는지와 할 일, 단축키가 나온다.
- **버전 기록:** 시계 버튼. 날짜별 시간 줄, 이름 붙인 버전은 채운 점. 버전마다 앞 버전에서 고친 장을 적는다. 누르면 전체 화면 미리 보기(지금과 다른 장 표시)에서 되돌린다.

## 7-1. 저장과 버전

덱이 사라지지 않게 하는 것이 목표다. 서버는 쓰지 않는다.

- **두 곳 저장:** IndexedDB(늘, 0.4초 뒤)와 보관 폴더(골랐으면, 1.5초 뒤). 화면을 떠나거나 창을 숨길 때 남은 저장을 바로 끝낸다. `navigator.storage.persist()`로 브라우저가 저장 공간을 비우지 않게 요청한다.
- **보관 폴더:** File System Access API(크롬, 엣지). 폴더 핸들은 IndexedDB에 둔다. 권한은 브라우저를 새로 열 때마다 다시 받아야 하므로 '허용하기' 상태를 따로 둔다. 파일 이름은 처음 저장할 때 제목으로 정하고 바꾸지 않는다. 같은 이름이 있으면 `(2)`를 붙이고, 이름을 기억해 둔 파일이 다른 발표 것이면 쓰지 않는다.
- **맞추기:** 홈을 열 때, 편집기를 열 때 폴더와 브라우저 중 `updatedAt`이 큰 쪽을 쓴다. 덮이는 쪽은 내용이 다르면 버전(`파일을 열기 전`)으로 남긴다. 폴더에 없는 발표는 폴더로 옮기되, '지운 발표'에 있으면 다른 PC에서 지운 것이므로 목록에서 뺀다.
- **버전:** 목록(가벼운 정보와 장마다의 비교 값)과 내용(덱 전체)을 다른 저장소에 둔다. 자동 버전은 같은 내용의 버전이 이미 있으면 남기지 않는다. 자동은 30개(폴더는 10개)까지, 이름 붙인 버전은 지울 때까지.
- **작업 파일(.deck):** `{ format: 'html-maker/deck', version: 1, savedAt, deck }` JSON. 노트를 포함한다. 남에게 보내는 HTML과 다르다.
- **내 컴포넌트(`store/saved.ts`):** 발표와 따로 이 브라우저(IndexedDB, 저장소 `html-maker-parts`)와 보관 폴더의 `내 컴포넌트.components` 하나에 둔다. 발표를 지워도 남고 어느 발표에서든 쓴다. 두 곳 가운데 `updatedAt`이 큰 쪽을 쓰고(발표 맞추기와 같게), 컴포넌트 탭을 열 때마다 다시 읽는다(그 사이 폴더를 허용했을 수 있다). 지우면 알림의 '되돌리기'로 그 자리에 돌려놓는다.
- **내 컴포넌트 파일(.components):** `{ format: 'html-maker/components', version: 1, updatedAt, parts }` JSON. 모두 또는 하나를 파일로 저장해 다른 사람과 주고받는다. 읽을 때는 발표 파일과 같은 규칙(`cleanRows`)으로 이 버전이 아는 컴포넌트와 값만 넣고, 뺀 것이 있으면 몇 개인지 알린다(`cleanPart`).

## 8. 발표와 내보내기

- **발표하기:** 전체 화면, 방향키·스페이스·PageUp/PageDown(클리커), Esc로 종료. 숨긴 장은 건너뛴다. B/W로 화면 가리기. '누르면' 나오는 컴포넌트가 남은 장은 다음 키가 장을 넘기지 않고 그 컴포넌트를 보인다(발표자 화면에 남은 수). 움직임은 [MOTION.md](MOTION.md).
- **비워 둔 부품:** 발표, 발표자 화면, 내보내기, 인쇄에서는 글도 그림도 없는 부품을 빼고 그린다(`shownRows`). 빈 칸이 회색 안내 문구 없이 빈 상자로만 남아 보이지 않게. 줄이 비면 그 줄과, 그 줄에 걸린 이음표도 뺀다. 저장된 발표는 그대로다(편집할 때는 다 보인다).
- **발표자 화면:** '발표하기' 옆 화살표 → '발표자 화면과 함께 발표'(Alt+F5). 큰 화면에는 슬라이드만, 노트북에는 지금 장·다음 장·노트·지난 시간·모든 장이 보인다.
  - 설치 없이 크롬·엣지의 Window Management API로 창을 화면마다 놓는다. 처음 한 번 '창 관리' 허락을 묻는다. 허락하지 않으면 슬라이드만 발표한다.
  - 두 창은 BroadcastChannel로 이어서 어느 창에 키가 가도(클리커) 같이 넘어간다. 한쪽에서 끝내면 둘 다 닫힌다. 발표 내용은 창 사이에서만 오간다.
  - 화면이 '복제'로 연결돼 있으면 발표자 화면에서 Windows 키 + P → '확장'을 안내한다.
  - 창 두 개 방식은 회사 PC 설정에 따라 안 될 수 있어서 기본은 '슬라이드만 발표'이고, 발표자 화면은 직접 고른다.
- **HTML 파일:** 폰트(실제 쓰인 글자 묶음만)와 이미지를 파일 안에 넣는다. 인터넷 없이 열린다. 열면 모든 장이 세로로 보이고, "발표 시작"으로 슬라이드쇼. 발표자 노트는 넣지 않는다(미리 보내도 안전). 이 파일을 다시 열면 편집할 수 있다. CSP로 어떤 주소에도 연결하지 못하게 하고, 스크립트는 들어 있는 뷰어 하나만(해시로) 허용한다.
- **PDF:** 브라우저 인쇄로 장마다 1920×1080 한 쪽.
- **PPT (그림):** 장마다 발표할 때 모습 그대로의 그림(1920×1080 PNG) 한 장을 꽉 채운 .pptx. 글은 그림이라 PowerPoint에서 고칠 수 없고, 발표자 노트는 노트 칸에 글로 들어간다(HTML과 달리 노트가 들어가니 보내기 전에 확인하라고 메뉴에 적는다). 숨긴 장은 뺀다. 서버 없이 화면 안에서 만든다(`export/rasterize.tsx`): 진짜 `SlideCanvas`를 화면 밖 1920×1080 상자에 발표 모드로 그리고, 쓴 글꼴 조각을 받은 뒤 부품 장을 다시 맞추고(`fitBlocks`), 그 DOM을 XML로 옮겨 CSS(slides.css, blocks.css)와 글꼴(data: 주소)과 함께 SVG `foreignObject`에 넣어 캔버스에 그린다. 움직임 엔진은 부르지 않아서 다 보인 끝 모습이다. 파일은 공개 규격 ECMA-376(Office Open XML)의 짜임대로 직접 쓴다(`export/pptx.ts`: 틀 하나, 빈 레이아웃 하나, 테마, 노트 틀, 장마다 그림과 노트). ZIP도 직접 묶는다(`export/zip.ts`, PNG는 그대로, XML은 `CompressionStream`으로 deflate). 의존성을 늘리지 않는다. 장마다 그리므로 장이 많으면 몇 초 걸리고, 그동안 몇 장째인지 알림에 보인다. 편집 화면의 콘솔에서 `await pptPreview()`로 그림만 볼 수 있다.

## 9. 기술

- Vite + React + TypeScript 정적 웹앱.
- **로컬 서버** (`server/serve.ts`, Node 내장만. 빌드하면 `dist-node/serve.mjs`): `127.0.0.1:41580`에만 묶는다. 포트를 고정하는 이유는 IndexedDB와 폴더 권한이 주소(포트 포함)마다 따로라서다. `localhost`로 오면 `127.0.0.1`로 보내고, 다른 Host 헤더는 거절한다(DNS 리바인딩 방어). GET/HEAD만, `dist` 밖 파일은 내주지 않는다. 모든 응답에 CSP(`connect-src 'self'` 등)를 붙이고, 빌드한 `index.html`에도 같은 CSP를 meta로 넣는다.
- **나눠 주기:** `npm run pack`이 `dist`, 서버, 더블클릭 실행 파일(맥 `.command`, 윈도우 `.bat`), 사용법을 묶는다. 받는 사람은 Node.js만 있으면 된다. 빌드 결과에 바깥 주소가 있으면 멈춘다.
- 상태: zustand, 저장: IndexedDB(idb-keyval) + File System Access API, 정렬: dnd-kit.
- 폰트: pretendard(dynamic subset), @sun-typeface/suit(굵기마다 나뉜 파일), @fontsource-variable/hahmlet, @fontsource-variable/noto-serif-kr(둘 다 unicode-range 조각). 앱은 쓴 글자가 든 조각만 받고, 내보낸 HTML에도 그 조각만 넣는다(`export/fonts.ts`).

## 11. AI(MCP): 모양만 보고, 제안만 한다

Claude Code나 Codex가 MCP로 붙어서 발표의 구성과 모양을 다듬을 수 있다. 사람이 적은 글은 AI에게 가지 않는다(MCP 응답은 AI 회사 서버로 간다고 보고 설계했다).

```
브라우저 앱 ──PUT 모양──▶ 로컬 서버 ──▶ AI 공유/decks/<해시>.json ──▶ MCP 서버 ──▶ Claude Code / Codex
     ▲                                                                   │
     └──GET 제안── 로컬 서버 ◀── AI 공유/requests/<id>.json ◀── propose_changes
     └──POST 결과─▶ 로컬 서버 ──▶ AI 공유/results/<id>.json ──▶ get_result
```

- **켜는 법:** 편집기 위쪽 **AI** 버튼에서 발표마다 직접 켠다(`deck.aiShare`). 가져온 발표, 복제한 발표는 꺼진 채로 시작한다. 같은 곳에서 AI에게 보이는 내용을 그대로 볼 수 있고, Claude Code·Codex 연결 명령을 복사할 수 있다.
- **모양(`src/ai/share.ts`):** 덱에서 고른 값으로 새로 만든다. 보고 종류, 시간, 장 순서, 레이아웃, 장 역할(카탈로그에 있는 말만), 숨김, 칸마다 `empty | filled | long`, 항목 수, 옵션, 테마와 강조색. 장과 덱의 원래 id 대신 해시를 쓴다(가져온 파일의 id에는 아무 글이나 있을 수 있다). 제목, 적은 글, 숫자, 이미지, 노트, 소속·이름·연락처는 넣지 않는다.
- **세 겹 확인:** 앱이 만들고, 로컬 서버가 `checkShape`로 꼴을 확인해서 쓰고, MCP 서버가 읽을 때 다시 `checkShape`, 내보낼 때 `onlyKnownStrings`(모든 글자가 카탈로그·정해진 말·해시인지)로 막는다.
- **MCP 서버(`mcp/server.ts`):** 의존성 없는 stdio JSON-RPC. 스스로를 Node 권한 모델(`--permission --allow-fs-read/write=AI 공유`)로 다시 띄워서 다른 파일을 읽지 못하고 다른 프로그램을 실행하지 못한다. 권한 모델이 심볼릭 링크를 따라가는 문제는 링크·하드 링크를 읽지 않는 것으로 막는다. 오류는 정해진 문구만.
- **도구 다섯 개:** `list_decks`, `get_catalog`, `get_shape`, `propose_changes`, `get_result`. 글을 읽는 도구는 없다.
- **제안(`src/ai/ops.ts`):** 장 넣기·빈 장 지우기·옮기기·숨기기, 레이아웃, 항목 수(빈 항목만 줄임), 옵션(장마다 장 넘기기 포함), 테마, 장 안내, 칸 안내 문구. 칸의 글을 쓰는 동작은 없다. 꼴이 하나라도 어긋나면 제안 전체를 받지 않는다. 한 발표에 보지 않은 제안은 5개까지.
- **사람이 결정:** 제안이 오면 오른쪽 아래에 알림이 뜨고, 미리 보기에서 바뀌는 것 목록과 적용한 뒤의 장들을 본다. 적용하면 그 전 상태를 버전(‘AI 제안을 적용하기 전’)으로 남기고, 되돌리기 한 번으로 돌아온다. 결과(적용/거절, op마다 코드)는 AI가 `get_result`로 본다.
- **다른 웹사이트 막기:** AI 창구는 `X-HTML-Maker` 머리글이 있어야 하고 Origin이 같아야 한다. 다른 사이트가 머리글을 붙이면 브라우저가 먼저 허락을 묻는데(OPTIONS), 서버는 허락하지 않는다.

### AI에게 부탁 (터미널 없이)

비개발자가 터미널을 열고 MCP를 연결해 말을 거는 대신, 슬라이드 아래 **AI에게 부탁**(이 장)이나 위쪽 **AI** 버튼(발표 전체)에서 부탁을 고른다. 로컬 서버가 이 PC의 Claude Code를 대신 띄워 부탁을 전하고, 제안이 오면 미리 보기가 바로 열린다.

```
[부탁 고르기] ──POST {ask, deck 해시, slide 해시}──▶ 로컬 서버 ──stdin: 정해진 문장──▶ claude -p (도구 없음 + gyeol MCP만)
     ▲                                                                                        │
     └── 진행(도구 이름), 제안 id ◀── 로컬 서버 ◀── AI 공유/requests/<id>.json ◀── propose_changes
```

- **부탁(`src/ai/asks.ts`):** 이 장 넷(더 어울리는 모양으로, 핵심이 눈에 띄게, 칸 안내 다듬기, 앞뒤에 필요한 장), 발표 전체 셋(보고 흐름 점검, 시간에 맞추기, 테마와 움직임). 오가는 것은 id와 해시뿐이고, AI에게 갈 문장은 로컬 서버가 `askPrompt`로 정해진 말로 만든다. 사람이 적은 글은 받지 않는다.
- **띄우는 법(`server/agent.ts`):** `claude -p --restricted --tools "" --strict-mcp-config --mcp-config <gyeol만> --allowedTools mcp__gyeol__* --permission-prompts none`. 파일 읽기·쓰기, 명령 실행, 웹 도구가 아예 없고, 사용자의 훅·플러그인·다른 MCP 서버도 읽지 않는다. AI가 볼 수 있는 것은 MCP 서버가 내주는 모양뿐이다. 사람이 Claude Code를 직접 쓸 때보다 좁다. 한 번에 하나, 3분이 넘으면 끈다.
- **ACP를 쓰지 않은 까닭:** ACP는 편집기와 에이전트를 잇는 표준이지만 Claude Code, Codex 모두 따로 어댑터를 깔아야 하고, 우리는 대화가 아니라 정해진 부탁 하나를 맡기면 된다. 이미 깔린 Claude Code의 비대화 실행이 도구를 더 좁게 막을 수 있다.
- **Codex:** Codex의 비대화 실행(`codex exec`)은 도구를 하나씩 끄는 방식이라 버전이 오르며 새 도구가 생기면 열릴 수 있다. 그래서 바로 띄우지 않고, 부탁 문장을 복사해 붙여 넣게 한다(Claude Code가 없는 PC도 같다).
- **진행과 결과:** 오른쪽 아래 카드에 ‘켜는 중 → 모양을 보는 중 → 정리하는 중’을 보여 주고 그만둘 수 있다. 제안이 오면 미리 보기가 바로 열리고, 바뀌는 장은 ‘지금 → 적용하면’을 나란히 먼저 보여 준다. 바꿀 게 없으면 AI가 말한 까닭(마크다운을 걷고 280자까지)을 카드에 남긴다. AI → 앱 쪽 글이라 내용이 나가는 길이 아니다.
- **공유:** 부탁을 누르면 그 발표의 AI 공유를 켠다(모양을 봐야 부탁을 들어줄 수 있다). 끄기는 위쪽 AI 버튼에서.
