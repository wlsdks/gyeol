# Framo 설계

회사에서 PPT로 하던 발표를 HTML로 만드는 빌더. 팀장, 본부장께 결정을 받는 보고(사업 제안, 고객 제안 계획, 개선 제안, 계획)만이 아니라 주간 업무 보고, 결과·장애 보고, 프로젝트 착수, 지식 공유, 팀 소개처럼 동료나 다른 부서 앞에서 하는 발표도 다룬다. 사용자는 대부분 비개발자다. 개인 PC에서 localhost로만 띄운다.

## 1. 원칙

1. **AI(또는 규칙)는 모양만, 사람은 내용만.** 발표 형태를 받아 골격(장 구성, 레이아웃, 칸마다 작성 안내)을 만들고, 내용은 사람이 채운다.
2. **내용은 이 PC 밖으로 나가지 않는다.** 서버 저장 없음, 외부 전송 없음. 덱은 브라우저(IndexedDB), 사용자가 고른 보관 폴더, 사용자가 내보낸 파일에만 있다. AI(MCP)에도 내용은 주지 않는다(11장). 바깥 연결은 둘뿐이다: 사람이 띄우는 ‘AI에게 부탁’(Claude Code)과, GitHub의 이 저장소 릴리스에 새 버전을 묻고 받는 것(9장 ‘새 버전’). 어느 쪽에도 발표 내용은 실리지 않는다.
5. **결론부터.** 듣는 사람은 바쁘다. 표지에 결정 요청(결정받을 것이 없는 발표는 부제), 둘째 장에 결론(한 장 요약, 오늘의 한 줄), 마지막 장에 받을 결정이나 부탁. 처음 두 장만 봐도 무엇에 관한 발표이고 무엇을 해 주면 되는지 알게 한다.
3. **자유도를 줄여서 디자인을 지킨다.** 글상자를 마음대로 옮기는 기능은 없다. 사용자는 레이아웃을 고르고 빈칸을 채운다. 배치, 서체, 여백은 시스템이 정한다.
4. **처음 보는 사람도 설명 없이 쓴다.** 익숙한 구조(왼쪽 슬라이드 목록, 가운데 슬라이드, 아래 발표자 노트), 모든 선택지에 기본값, 모든 빈칸에 안내 문구.

## 2. 사용 흐름

```
홈(내 발표) ─ 새 발표 만들기 ─▶ 마법사 3단계 ─▶ 편집기 ─▶ 발표 / 내보내기
                                  1. 발표 종류   어떤 발표인가요?            세 묶음 13가지 + 고른 종류로 만들어지는 장 네 장의 그림
                                  2. 발표 상황   누구에게, 얼마나 발표하나요? (듣는 사람, 시간, 방식) + 구성 미리보기
                                  3. 표지       표지를 채워 주세요           (제목, 결정받고 싶은 것 또는 부제, 소속, 발표자, 테마) + 표지와 이어질 장
```

- 마법사는 모든 항목에 기본값이 있어서 "다음"만 눌러도 끝난다.
- 1단계는 종류 열셋을 회사에서 PPT를 만드는 자리 셋으로 묶어 세로 칸으로 나란히 둔다(`DECK_GROUPS`: 제안하고 결정받기, 진행과 결과 보고하기, 알리고 나누기). 단추에는 이름과 한 줄 설명만. 오른쪽 카드는 글로 된 흐름 대신 그 종류의 이야기 흐름마다 실제로 만들어지는 장(`Blueprint.showcase`)을 2×2로 작게 그린다. 칸에는 안내 예시가 진하게 들어가서 어떤 장인지 알아볼 수 있다. 두 번 누르면 바로 다음 단계. 빈 발표는 아래 줄 왼쪽의 다른 길이다.
- 2단계의 고르는 줄에는 이름만 두고, 고른 것이 무엇을 바꾸는지는 그 아래 한 줄로. 선택을 바꾸면 "10장으로 만들어요"와 장 그림이 즉시 바뀐다(새로 들어온 장만 살짝 나타난다). 발표 형태가 모양을 바꾼다는 걸 눈으로 보여준다.
- 3단계는 적는 대로 오른쪽의 큰 표지가 바뀐다. 결정을 받는 종류(`examples.ask`가 있는 것, `asksDecision`)만 '결정받고 싶은 것'을 묻고, 주간 업무 보고, 프로젝트 착수, 지식 공유, 팀 소개는 부제를 묻는다. 이런 발표의 표지는 결정 요청 칸이 없고 아래 띠 모양으로 만든다(옆 면은 위쪽이 결정 요청 자리라 비워 두면 짙은 면의 위가 빈다). 표지 아래에 이어질 장을 작게 넷(낮은 화면은 셋, 넘치면 마지막 칸에 남은 장 수) 그려서 오른쪽 칸 아래가 비지 않게 한다. 테마는 견본과 이름으로 고른다.
- 설명 글을 화면에 늘어놓지 않는다. 꼭 필요한 설명만 옆에 (i)를 두고 마우스를 올리면 툴팁으로 보인다(`Info`). 홈의 보관 폴더 안내도 같다.
- 화면 비율: 묻는 말은 두 칸 위에 걸치고, 왼쪽(고르는 것)과 오른쪽 카드는 같은 줄에서 시작해 높이가 비슷하게 칸 너비를 단계마다 잡는다. 틀 전체는 머리줄과 아래 줄 사이 가운데에 둔다(위에 붙이면 큰 화면에서 아래만 크게 빈다). 1920×1080에서는 틀을 1480까지 넓히고 단추와 그림을 키운다.
- 1280×600(윈도우 노트북 150%), 1366×650, 1536×730에서 세 단계 모두 스크롤 없이 한 화면에 들어가고 가로 스크롤은 없다. 장이 많은 구성(30분)은 2단계 오른쪽 카드 안에서만 스크롤한다.

## 3. 골격 생성 규칙

발표 형태가 바꾸는 세 가지:

| 입력 | 바뀌는 것 |
|---|---|
| 종류 (13가지, 아래 표) | 이야기 순서와 장 구성 (blueprint) |
| 듣는 사람 (본부장·임원, 팀장, 팀 동료, 다른 부서, 여러 분이 함께) | 장마다 무엇을 챙기는 장인지(`focus`: 숫자 numbers, 자세한 실행 detail, 배경 context) 달아 두고, 듣는 사람이 더 챙기는 장(`up`)은 우선순위 3을 2로, 덜 챙기는 장(`down`)은 2를 3으로 바꿔 장 수를 맞춘다. 본부장·임원: 숫자를 챙기고 세부를 덜어 내며 목차가 없다. 팀장, 팀 동료: 실행 계획과 세부까지. 다른 부서: 배경을 먼저 푼다. 여러 분이 함께: 구성 그대로 |
| 시간 (5, 10, 20, 30분+) | 목표 장 수 5, 7, 11, 15. 보고는 질문과 토론이 길어서 한 장에 2분 남짓. 우선순위 낮은 장부터 뺀다 |
| 방식 (회의실 발표, 화상 회의, 보고서로 보내기) | 글 밀도와 작성 안내. 보고서로 보내면 혼자 읽어도 이해되게 설명을 더 넣도록 안내 |

- 어느 종류든 표지 → 결론(한 장 요약, 지식 공유는 오늘의 한 줄) → … → 마지막 한 장(받을 결정이나 부탁)의 뼈대는 같고, 마지막 장은 한 번만 나온다(`generate.test.ts`). 한 장 요약은 줄 이름(배경, 제안, 기대 효과, 요청 사항)을 미리 넣고 줄마다 다른 안내를 단다(`hints['items.N.body']`).
- 위험과 대응, 안 비교(A안/B안/C안, 추천안 강조), 필요한 자원(예산/인력/기간) 같은 보고용 장은 이름표를 미리 채운다(`prefill`). 이름표는 구조라서 미리 넣어도 되지만 내용은 넣지 않는다.

- 유형별 blueprint는 사람이 설계한 장 목록이다. 각 장은 레이아웃, 역할 이름, 우선순위(1~3), 대상 청중, 챙기는 것(focus), 칸별 안내 문구를 가진다. 장의 안내(`guide`)는 짧은 한 문장으로 쓴다.
- 장 수 맞추기: 우선순위 1은 절대 빼지 않는다. 3부터, 같은 우선순위면 뒤쪽부터 뺀다. 섹션 구분 장들은 묶음으로 넣거나 뺀다(일부만 있으면 어색하다).
- 규칙 기반이라 AI 없이도 돈다. AI는 MCP로 구성과 모양만 손볼 수 있다(11장).

종류는 회사에서 PPT를 만드는 자리를 공개된 보고서 작성 안내(업무 보고를 계획·현황·결과 보고로 나누는 글, 품의서와 주간 업무 보고, 장애 보고 양식의 항목)에서 모아 셋으로 묶었다. 종류 id는 저장 파일에 남으니 바꾸지 않는다. 예전 버전은 모르는 종류를 빈 발표처럼 다룬다(이름이 비고, AI에게는 `blank`로 보인다).

| 묶음 | 종류 | 마지막 장 |
|---|---|---|
| 제안하고 결정받기 | 사업 제안, 개선 제안, 검토 보고(여러 안 비교), 고객 제안 계획, 연간·반기 계획 | 결정 요청 (우선순위 1) |
| 진행과 결과 보고하기 | 주간·월간 업무 보고, 실적 보고, 결과 보고, 문제·장애 보고 | 요청 사항 (실적 보고만 1, 나머지는 2라 짧은 발표에서는 빠진다) |
| 알리고 나누기 | 프로젝트 착수, 조사·분석 보고, 지식 공유·교육, 팀·업무 소개 | 함께 정할 것, 다음에 할 일, 정리, 이럴 때 찾아 주세요 |

## 4. 데이터 모델

```ts
Deck  { id, title, meta: { type, audience, duration, method, org, presenter, date, contact, logo },
        theme: { id, accent? }, logo, slides: Slide[] }
Slide { id, layout, purpose, section, fields: {title, lead, body, ...}, items: Item[],
        hints, guide, notes, options, hidden }
Item  { id, title, body, value, meta, image }
```

- 레이아웃이 달라도 칸 이름(title, lead, body, items[].title/body/value/meta)을 공유한다. 그래서 레이아웃을 바꿔도 내용이 유지된다.
- 레이아웃의 최대 항목 수보다 많은 항목은 지우지 않고 숨긴다. 다시 바꾸면 돌아온다.
- 소속, 발표자, 날짜, 연락처, 로고는 덱 단위 값이다. 표지에서 고치면 마지막 장에도 반영된다. 결정 요청 한 줄은 표지의 칸(`fields.ask`)이다. 결정을 받지 않는 발표는 편집할 때도 이 칸을 그리지 않는다(적어 둔 것이 있으면 그대로 보인다).

## 5. 레이아웃 (26개 + 부품 장)

표지(결정 요청 포함), 섹션 구분, 목차, 한 장 요약, 한 문장 메시지, 핵심 숫자, 목표 대비 실적, 두 값 비교, 증감 요인, 추이, 진행 현황, 구성비, 단계 흐름, 깔때기, 표, 핵심 포인트, 비교(지금과 바뀐 뒤, 위험과 대응), 2×2 우선순위, 위치 비교, 일정, 사례, 안 비교, 이미지와 설명, 로고 모음, 막대 비교, 결정 요청.

- **모양(variant):** 한 레이아웃 안에서 같은 칸을 다르게 놓은 것. 칸은 늘거나 줄지 않아서 바꿔도 내용이 그대로다. 목차(목록/나란히), 한 장 요약(줄/칸), 핵심 숫자(나란히/하나 크게/카드), 핵심 포인트(줄/세로 칸/타일), 비교(두 면/표), 일정(가로/세로), 안 비교(나란히/표), 막대 비교(가로 막대/세로 막대/점과 선), 추이(선/면), 구성비(띠/도넛/100칸), 단계 흐름(선으로 잇기/칸), 두 값 비교(묶은 막대/두 선/점 두 개), 섹션과 결정 요청(바탕/색 면), 표지(옆 면/아래 띠/색 면).
- **목표 대비 실적:** 목표와 실적을 같은 단위로 적으면 달성률은 저절로 계산한다. 막대는 실적만큼 채우고 목표 자리에 세로 줄. 목표를 넘은 만큼은 진하게, 모자란 만큼은 빗금으로 목표 줄에 붙여 칠한다. 좋고 나쁨을 색으로 판정하지 않는다(낮을수록 좋은 지표가 있어서). 눈여겨볼 지표 하나만 강조색. 모양은 표(지표마다 한 줄)와 **나란히**(지표가 적을 때 지표마다 한 단: 이름, 크게 쓴 달성률, 막대, 목표와 실적을 이름과 숫자로 한 줄씩). 나란히는 단 사이를 세로 줄로만 나누고 면을 깔지 않으며, 다섯 줄을 모든 단이 같이 써서(subgrid) 설명이 없는 단도 달성률과 막대가 옆 단과 같은 높이에 선다. 여섯이면 셋씩 두 줄. 목표와 실적의 이름은 표의 머리 줄에 적은 이름을 단마다 다시 쓰고, 편집할 때는 첫 단의 이름 자리에서 고친다(머리 줄을 편집할 때만 보이던 때는 그 줄만큼 64px가 늘어, 발표 화면으로 잰 높이에 맞춘 칸에서 글자를 두 단계 줄였다).
- **두 값 비교:** 항목마다 앞 값(작년, 계획)과 뒤 값(올해, 실적). 두 값의 이름은 칸으로 바꾼다. 묶은 막대는 0부터, 두 선은 추이처럼 바닥을 올려 그린다. '점 두 개'는 항목마다 한 줄에 앞 값과 뒤 값의 점을 찍고 사이를 잇는다(덤벨): 항목이 많아도 줄이 가지런하고, 움직일 때 뒤 값의 점이 앞 값에서 출발해 미끄러진다. 앞 값은 옅은 회색, 뒤 값은 강조색. 항목 이름 아래에 앞 값에서 몇 % 바뀌었는지(▲▼) 계산해 붙이되, 늘어난 것이 좋은지는 장마다 달라서 색으로 가르지 않는다.
- **증감 요인(폭포):** 처음 값(예: 목표)과 요인마다 더하고 뺀 값을 적으면 끝 값(예: 실적)은 계산한다. 따로 적으면 서로 안 맞을 수 있어서다. +, ▲는 더하기, -, −, △, ▼는 빼기로 읽는다(`src/slides/numbers.ts`). 더한 요인은 강조색, 뺀 요인은 옅은 회색, 처음과 끝은 글자색. 처음과 끝이 증감보다 훨씬 크면 바닥을 올리고, 처음과 끝 막대를 바닥줄에서 조금 띄워 그 틈에 축을 끊은 표시(//)를 둔다. 예전처럼 막대 아래쪽을 바탕색 띠로 비스듬히 끊으면 낮은 줄에서 막대 바닥에 흰 금이 간 것처럼, 그리다 만 자국으로 보였다. 모양은 세로(바닥에서 위로)와 **가로**(요인 이름이 길거나 요인이 많을 때). 가로는 줄마다 왼쪽에 이름, 왼쪽 축에서부터 뜬 막대, 오른쪽 끝 한 줄에 값을 둔다(막대 끝에 붙이면 끝 값이 큰 줄에서 값이 칸 밖으로 나간다). 막대 사이는 세로 선으로 잇고, 줄 사이 틈 없이 여백을 줄 안에 두어 축과 잇는 선이 끊기지 않는다. 발표할 때 더한 요인은 왼쪽에서 뻗고 뺀 요인은 앞 막대가 끝난 자리에서 왼쪽으로 줄어든다.
- **추이:** 시기마다 숫자를 적으면 점을 찍어 선으로 잇는다. 모두 0보다 크고 폭이 좁으면 0부터 그리지 않는다(흐름을 보는 장이라 납작해지지 않게). 0을 지나면 0 줄을 긋는다. 목표선은 적었을 때만, 강조 점은 기본이 마지막(`highlight.fallback: 'last'`). 값 이름표는 점 위, 양옆보다 낮은 점은 점 아래가 먼저이고, 그 자리가 선을 지나거나 그래프 밖으로 나가거나 다른 이름표, 점과 겹치면 옆으로 비킨 자리, 점 바로 옆(숫자 가운데를 점 높이에), 반대쪽(위 아래)을 차례로 재어 가장 덜 겹치는 자리를 고른다(`trendPlace`, 그린 뒤 글꼴이 바뀌거나 움직임이 끝나면 다시). 가파르게 내려오는 선의 끝 점은 위에 두면 이름표가 들어오는 선 위에 얹혔고, 바닥에 가까우면 아래에 둘 자리도 없어 강조한 큰 숫자가 바닥줄에 걸쳤다(그래서 점 바로 옆). 그래프 위 띠(가장 높은 점의 강조한 숫자 자리)는 숫자 크기를 따라 늘어서, 글자 크기 '크게'에서도 맨 위 점의 숫자가 그래프 밖으로 나가지 않는다. 이름표가 목표선에 걸치면 선 위로(점 아래 이름표는 선 아래로) 비켜 선다: 바탕색 둘레는 글자 둘레만 지워서, 목표선이 숫자 한가운데를 지나면 글자 사이로 점선이 보였다. 목표선의 높이(`--ty`)와 점의 높이로 CSS가 고르고, 걸치지 않는 이름표는 그대로 둔다. 숫자가 빈 시기는 발표할 때 점을 찍지 않는다. 시기 이름은 점과 같은 칸(항목 수로 똑같이 나눈 칸)의 가운데에 두고, 칸보다 길면 띄어쓰기에서 줄을 바꾼다(한 줄로 묶어 두던 때는 '10월 1주'처럼 긴 이름이 칸 밖으로 넘쳐 점보다 오른쪽으로 밀리고 옆 이름과 겹쳤다). 무너지기 쉬운 값은 갤러리 `set=edge`로, 긴 이름은 `&names=`로 본다.
- **진행 현황:** 과제마다 진행률 막대와 상태. 상태 글(완료, 진행 중, 지연, 예정 등)을 읽어 색을 정하고, 비우면 발표할 때 진행률로 짐작한다(100%는 완료, 0%는 예정, `statusOf`). 읽을 수 없는 글('검토 중')은 색 없이 그 글 그대로. 머리줄 오른쪽에 상태별 과제 수를 모아 지연이 먼저 보이게. 상태는 늘 글자와 함께 색을 쓴다. 상태별 모양은 과제를 상태마다 한 단에 모은다(있는 상태만, 완료, 진행 중, 지연, 예정 차례). 단 머리는 상태 이름과 과제 수, 윗줄이 상태 색이고, 과제마다 이름 아래 얇은 막대, 막대 끝에 진행률을 둔다(이름 옆에 두면 넷이 나란할 때 열 글자 남짓한 이름도 두 줄이 됐다). 짜임과 컴포넌트의 높이는 과제 수가 아니라 가장 많이 모인 단의 과제 수로 고른다(`laneRows`, 과제 다섯이 모두 진행 중이면 단 하나가 다섯 줄이다): 둘까지면 글자를 한 단계 키우고 줄 사이를 넓히고, 넷부터는 진행률을 이름 줄 끝으로 올리고, 다섯부터는 이름을 한 단계 줄이고, 여섯부터는 담당과 기한을 이름 뒤 같은 줄에 둔다. 항목 수로 고르던 때는 과제가 한 단에 몰리면 컴포넌트 칸이 모자라 글자를 줄였다(잴 때도 과제를 모두 한 단에 모아 잰다, 갤러리 `&lane=1`). 단이 상태를 말하므로 발표할 때는 지연된 과제의 사정(예: 2주 지연)만 글로 남기고, 편집할 때는 상태를 고쳐 다른 단으로 옮길 수 있게 모든 과제에 상태 칸을 보인다. 상태 글은 이름 줄의 오른쪽 끝에 둔다: 따로 한 줄을 두면 편집할 때만 과제마다 한 줄씩 높아져 칸을 넘었다. 상태 칸이 빈 과제는 진행률로 짐작해 단을 정하고, 진행률도 없으면 예정에 둔다.
- **막대 비교의 점과 선:** 굵은 막대 대신 가는 선과 그 끝의 점으로 길이를 읽는다. 값이 고만고만한 항목이 많을 때 면이 덜 무겁고, 끝의 점이 숫자 자리를 짚는다. 다 찬 자리까지는 줄 선 굵기의 옅은 선을 깔고, 강조한 점만 강조색에 옅은 고리를 둘러 선에서 떼어 낸다. 점은 선과 따로 두어서, 발표할 때 선이 늘어나는 동안 점이 선 끝을 따라 미끄러진다(선과 같이 늘이면 점이 타원으로 찌그러진다).
- **구성비:** 값을 더한 전체에서 각 항목의 비중. 모두 %로 적었으면 적은 그대로, 금액이나 건수면 비중을 계산해 크게 보이고 적은 값과 합계는 작게. 강조할 조각만 강조색, 나머지는 큰 조각부터 진한 회색 단계. 강조가 없으면 강조색의 농담. 농담의 단계(`slides/tints.ts`)는 어두운 바탕(검은 장, 짙은 면 부품)에서 따로 둔다(base.css의 `--ta-*`, `--tg-*`): 흰 바탕과 같은 비율로 검정에 섞으면 옅은 쪽 조각이 sRGB 13~29라 프로젝터에서 바탕과 같은 검정으로 보였다. 숫자와 단위는 붙여 쓴다('131억 원'). 도넛의 이름표는 표처럼 읽는다: 줄마다 색 점과 이름(덧붙임은 이름 아래), 오른쪽 끝에 값과 큰 비율, 셋이 한 바닥선. 칸은 모든 줄이 같이 써서(subgrid) 숫자끼리 위아래 자리가 맞고, 줄 높이는 모두 같다. 예전에는 비율을 왼쪽에 크게 두고 줄마다 굵은 색 막대를 세워, 덧붙임이 있는 줄만 높아 줄 사이가 들쭉날쭉했고 이름 오른쪽이 줄 끝까지 비었다. 반 칸에서는 값을 이름 아래로 내리고 줄 높이는 줄마다 따로 둔다(줄이 두세 겹인 반 칸에서 모든 줄을 덧붙임이 있는 줄에 맞추면 여섯 줄이 반 칸보다 높았다). 다섯, 여섯이면 고리를 줄여 이름표에 자리를 더 주고 값을 이름과 비율 사이 한 줄에 둔다. 넓고 낮은 줄에서는(넷 이상) 이름표를 고리 옆 한 줄로 늘어놓는다(구성비 띠의 이름표와 같은 짜임). 고리가 작아지면 가운데 합계도 단계를 낮춘다(고리 안쪽 지름에 닿지 않게). 여섯을 한 줄로 늘어놓을 줄이 높으면 셋씩 두 줄로 둔다(한 줄이면 비율 숫자끼리 붙고 목록 위아래가 비었다). **100칸**은 10×10 칸 하나가 1%다: 비중을 내림하고 남는 칸은 소수점 아래가 큰 항목부터 하나씩 주어 모두 100칸이고, 왼쪽 위에서부터 줄마다 항목 차례로 칠한다. 이름표는 도넛과 같고, 합계는 칸 아래에 둔다(목록 위에 두면 목록 쪽이 한 줄 높아져 낮은 칸에서 일찍 눕혀야 했다). 칸 사이와 모서리는 칸 크기를 따라 줄어서 작은 칸에서도 틈이 칸보다 굵어 보이지 않는다. 발표할 때는 칸이 한 칸씩 차오른다.
- **단계 흐름:** 날짜 없는 순서(업무 절차, 바뀌는 절차). 기본 모양은 단계마다 위에 굵은 선을 긋고 그 아래 가는 번호, 이름, 설명을 두는 줄이다. 선이 이어져 순서의 띠로 읽힌다. 번호를 동그라미에 넣어 점 사이를 잇는 꼴과 칸 사이 꺾쇠는 흔한 서식처럼 보여 뺐다(목차, 마지막 장과 같은 말). 움직일 때 단계마다 선이 왼쪽부터 그어지고 다음 단계의 선이 이어서 그어진다. 일정(날짜가 있는 순서)과 나눠 쓴다. 강조할 단계 하나는 선을 두 배 굵기의 강조색으로, 번호도 강조색으로(강조색 바탕에서는 강조가 글자색이라 굵기로 알아본다). 장 한 장을 다 쓸 때 담당과 시간은 모든 단계가 한 줄에 맞는 아래 줄에 두고, 설명과 그 줄 사이는 300px(설명, 틈, 담당 줄의 합)까지만 벌려 띠 전체를 본문 가운데에 둔다. 담당 줄을 본문 바닥까지 내리면 설명이 한 줄일 때 단계마다 설명 아래가 360px 넘게 비었다.
- **위치 비교(포지셔닝 맵):** 두 기준(가로, 세로)의 점수로 회사나 안을 점으로 찍는다. 점수가 모두 0~10이면 0~10 눈금, 아니면 가장 큰 값까지. 가운데 점선 십자는 두 기준의 중간. 강조할 점(보통 우리)만 강조색으로 크게, 나머지는 회색. 이름표는 점 옆에 붙이되, 이웃한 이름표나 점과 겹치면 반대쪽이나 위아래로 비킨다: 그리기 전에 글 길이로 어림하고(`labelSides`), 그린 뒤에 실제 크기로 다시 고른다(`fitBlocks.ts`의 `labels`, 내보낸 파일도 같다). 이름표는 판의 바탕색을 깔아 가운데 점선이 이름표 밑으로 지나가고(이름표가 판 가운데 가까이 서면 점선이 이름과 점수 사이를 그었다), 모든 점보다 위에 그린다(같은 자리의 강조 점 둘레 빛이 앞 점 이름표의 첫 글자를 덮었다). 점수는 편집할 때만 이름 아래에 보인다. 축 이름 옆의 화살표는 글자(↑ →)가 아니라 다른 화살표(`ArrowMark`)와 같은 선과 꽉 찬 머리로 그린다(2×2 우선순위도 같다): 글자는 화살표를 쳐 넣은 것처럼 보였다. 선은 잇는 선과 같은 굵기(줄 선의 1.5배), 머리는 축 이름의 글자 크기를 따른다.
- **깔때기:** 단계마다 한 줄에 이름, 숫자, 막대. 막대는 왼쪽 끝을 맞춰 남은 만큼(첫 단계 대비 길이)을 세고, 그 단계에서 빠진 만큼(앞 단계 길이에서 이 길이까지)을 막대 뒤에 옅게 이어 위에서 아래로 계단이 진다. 앞 단계에서 넘어온 비율은 막대의 시작 위에, 처음부터 끝까지의 비율은 가장 긴 첫 막대의 끝 위에 단계 이름으로('지원에서 합격까지 7.5%', 이름이 길거나 비면 '전체 전환율'). 예전에는 이름과 숫자 칸 아래에 '처음부터 끝까지' 줄을 따로 두어 무엇의 비율인지 알기 어려웠다. 비율은 계산한다. 막대는 회색, 강조할 단계(기본은 마지막)만 강조색. 단계는 순서가 있는 항목이라 가로 막대로 둔다(ONS 차트 지침: 항목은 가로 막대, 세로 막대는 시간 순서에). 예전의 가운데 맞춘 막대는 단계마다 짙어지는 강조색과 막대 끝에 붙은 숫자 때문에 숫자 줄이 들쭉날쭉하고 흔한 깔때기 그림처럼 보였다.
- **표:** 칸은 넷까지(머리말 h1~h4, 항목의 title, meta, value, body). 발표할 때는 머리말도 칸도 비운 칸이 빠진다. 칸 너비는 글에 맞춘다: 표 전체가 한 격자이고 줄이 그 칸을 같이 써서(subgrid), 칸마다 가장 긴 글까지 늘고 남는 너비는 칸마다 똑같이 나눈다(칸 사이가 고르다). 글이 표보다 길면 긴 설명 칸이 줄을 바꾼다. 칸마다 비율을 정해 두던 때는 '상태'처럼 짧은 넷째 칸이 가장 넓어 오른쪽이 비고, 긴 첫째 칸만 두 줄로 꺾였다. 금액, 비율, 건수만 든 칸은 오른쪽에 맞춘다('11월' 같은 날짜는 글로 본다). 강조할 줄 하나.
- **일정:** 시기 아래 가는 선 위에 작은 꽉 찬 점을 찍는다. 굵은 테두리의 큰 동그라미에 둘레까지 두른 점은 흔한 서식처럼 보였다. 장 한 장을 다 쓸 때 시기는 일정의 답이라 가장 크게 둔다(넷까지 62, 다섯·여섯은 44). 지금 단계를 고르면 지나온 구간의 선과 점은 강조색, 지금 점은 바탕 틈을 둔 가는 고리, 남은 점은 옅게. 세로 목록 모양은 단계마다 한 줄에 시기, 점, 할 일, 설명을 두고(칸은 모든 줄이 같이, 셋이 한 바닥선) 점을 잇는 세로 선은 끊기지 않게 하나로 긋는다. 점 둘레에 바탕색 테를 두르던 때와, 부품 칸에서 줄 사이에 틈이 생기던 때는 점마다 선이 끊겨 점선처럼 보였다. 지금 점은 강조색에 옅은 강조색 테, 남은 점은 속이 빈 고리. 시기는 할 일보다 한 단계 작고 옅게(같은 크기면 두 글이 겨뤘다), 가장 긴 시기만큼만 넓게 잡아 점 옆에 붙인다. 할 일과 설명은 5 : 7로 나누고, 할 일부터 오른쪽 끝까지 줄마다 가는 선을 그어 한 줄로 묶는다(시기와 점 쪽은 세로 선이 줄을 나눈다). 설명을 본문 가운데에 두고 선이 없던 때는 할 일이 짧으면 설명만 오른쪽에 떠 보였고, 설명을 할 일 바로 뒤에 붙이면 묶음이 왼쪽에 몰려 오른쪽 절반이 비었다.
- **비교:** 두 면 모양은 면을 칠하지 않고 앞은 옅은 글자색 머리 괘선, 바뀐 뒤는 강조색 머리 괘선으로 두 쪽을 나누고(예전에는 옅은 면과 옅은 강조색 면이 나란한 둥근 카드 둘이었다), 두 쪽 사이(`--cp-mid`) 가운데에 가는 꺾쇠(›) 하나를 둔다(`slides/arrow.tsx`의 `ArrowMark`, 발표할 때는 가리키는 쪽으로 조금 밀려 나온다). 점에서 선이 나와 꽉 찬 세모 머리가 닿는 화살표는 흔한 다이어그램 그림이라 괘선으로 나눈 두 쪽 사이에서 떠 보였다(사용자 의견, 2026-10). 표 모양은 면 없이 두 쪽이 가운데로 모여 줄마다 짝을 짓는다: 왼쪽은 오른쪽 끝에, 오른쪽은 왼쪽 끝에 붙이고 그 사이 가운데에 줄마다 작은 꺾쇠. 예전에는 두 쪽 모두 왼쪽에 붙여서 짧은 글이면 쪽마다 오른쪽 절반이 비고, 왼쪽 글과 오른쪽 쪽의 화살표 사이가 멀어 짝이 읽히지 않았다. 두 면 안의 줄은 내용 높이에서 남는 높이를 똑같이 나눠 받고, 머리 줄은 그 절반을 받아 머리 글을 아래에 둔다. 줄마다 글 위아래에 더해지는 만큼 머리 위에도 더해져서, 머리 위 여백(줄 여백과 면 아래 여백의 합)이 마지막 줄 아래 여백과 늘 같다. 예전에는 줄이 높이를 나눠 갖고(1fr, 둘까지는 220px) 머리 위는 48px 그대로라 장에서 위 57, 아래 97~114px였고, 줄이 220px에서 멈추면 남는 높이를 머리 줄이 받아 머리와 첫 줄 사이가 130px 넘게 떴다. 면 아래 여백은 마지막 줄 안에 둔다: 컴포넌트 칸이 낮으면 줄이 면의 아래 여백까지 내려와 마지막 줄이 면 바닥에 15px로 붙었는데, 그 여백이 칸 안이라 맞추기도 몰랐다. 표 모양과 나란한 두 목록은 줄이 둘까지면 줄을 220px에서 멈추고 머리와 줄을 한 덩어리로 가운데에 둔다(머리 위의 선은 머리말 칸의 윗선이라 같이 내려간다). 머리 줄이 남는 높이를 받으면 머리말과 첫 줄 사이가 130px 넘게 떴다.
  - 나란한 두 목록: 하는 일과 하지 않는 일처럼 한쪽이 다른 쪽으로 바뀌는 것이 아닌 두 목록. 화살표와 강조색 면을 쓰면 '왼쪽이 오른쪽이 된다'로 읽혀서(이번에 해요 → 이번에는 안 해요) 화살표 없이 둘을 같은 무게로 둔다: 쪽마다 위에 글자색 선 하나, 머리말, 줄 선으로 나눈 글. 프로젝트 착수의 '하는 일과 하지 않는 일'이 이 모양으로 시작한다.
- **안 비교:** 안마다 위에 선을 긋고 그 아래에 이름, 비용, 내용을 쌓는다. 추천안만 짙은 면에 올리고, 면의 위 여백이 선 아래 여백과 같아서 안끼리 이름과 비용이 한 줄에 맞는다. '추천'은 강조색 글자로만 둔다. 안은 내용 높이로 서고 안들을 한 묶음으로 본문 가운데에 둔다(본문 높이까지 늘이면 추천안의 짙은 면만 아래가 230px 비었다). 안마다 회색 판을 깔고 둥근 '추천' 표를 달던 때는 웹 서비스의 요금제 카드처럼 보였다. 안이 하나면 고를 것이 없으니 장을 다 쓰는 한 덩어리로 그린다: 왼쪽에 이름과 비용(이 장의 답이라 크게), 오른쪽에 내용. 추천으로 고르지 않았으면 선과 글을 한 덩어리로 장 가운데에 둔다(장 높이를 다 쓰면 위의 선과 가운데의 글이 한참 떨어졌다). 판 하나를 왼쪽 760px에 두던 때는 장의 오른쪽 절반이 통째로 비었다.
- **로고 모음:** 다섯까지는 한 줄에 모두, 그보다 많으면 두 줄로 나눠 윗줄에 하나 더(7개는 4·3, 9개는 5·4, `logoColumns`). 덜 찬 마지막 줄은 가운데에 둔다(칸을 반 칸으로 나눠 반 칸만큼 민다). 한 줄에 넷을 두던 때는 5개가 4·1로 마지막 줄에 하나만 남았다. 부품 칸에서는 칸 너비가 한 줄에 놓을 수 있는 가장 많은 수를 정하고(180px 밑으로 좁아지지 않게), 줄 수를 먼저 정한 뒤 줄마다 고르게 나눈다(8개는 6·2가 아니라 4·4, 11개는 6·5).
- **숫자 장의 출처:** 핵심 숫자, 막대 비교, 목표 대비 실적에는 출처·기준 시점 칸이 있다(선택).
- 숫자를 넣기 전에는 편집 화면에서 예시 막대를 흐리게 보여 줘서 어떤 장인지 알아보게 한다. 발표와 내보낸 파일에는 나오지 않는다.

- 모든 슬라이드는 1920×1080 고정 캔버스에 디자인하고 화면에 맞춰 축소·확대한다. 어디서 열어도 같은 모양이다.
- 긴 글: 칸마다 글자 수 단계에 따라 글씨를 줄인다(내보낸 파일에서도 같은 결과가 나오도록 측정이 아니라 길이 기준). 목록 항목의 칸(핵심 포인트, 일정, 2×2 우선순위의 제목)은 가장 긴 항목으로 한 단계를 골라 모두 같이 쓴다: 항목마다 고르면 긴 제목만 작아져 나란한 제목의 크기가 줄마다 달랐다. 그래도 넘치면 편집기에서 경고한다.
- 항목 수에 따라 배치가 바뀐다(2~4열 등).

## 5-1. 부품 장: 부품을 골라 끌어다 놓기

레이아웃이 맞지 않는 장은 부품을 골라 직접 꾸민다. 그래도 글상자를 아무 데나 두지 않는다. **12×12칸의 판에만 들어가서** 대충 놓아도 반듯하다.

- **부품(`src/deck/blocks/`):** 부품 장만의 부품 40가지(핵심 한 줄, 제목과 글, 점 목록, 인용, 강조 상자, 큰 숫자, 전과 후, 목표 대비, 비율 원, 몇 중 몇, 숫자와 흐름, 개요, 걱정과 대책, 강점과 약점, 예상 질문, 준비 상황, 추진 일정, 맡은 사람, 이미지, 평가표, 시장 규모, 원인 순위, 기간별 달성, 항목별 증감, 쌓은 막대, 색 표, 지표 흐름표, 흐름, 연결도, 나누기, 모으기, 칸 조립, 소제목, 숫자 한 줄, 막대 하나, 범위, 상태, 단계 표시, 날짜, 주석)와 레이아웃을 그대로 쓰는 부품 19가지(한 장 요약, 핵심 숫자, 추이, 증감 요인, 표 등). 레이아웃 부품은 그 레이아웃의 그리기, 칸, 안내, 움직임을 그대로 쓰고 장의 머리(제목, 부제, 출처)만 뺀다. 그래서 장을 부품 장으로 바꿔도 생김새가 같다.
- **맡은 사람의 체계도:** 맨 앞 사람(이끄는 사람)을 위 가운데에, 나머지를 아래에 나란히 두고 선으로 잇는다(추진 체계). 동그라미는 빼고 글을 가운데로 둔다: 동그라미와 글을 옆으로 두면 세로 선이 둘 사이에 떨어져 글에 꽂혀 보였다. 선은 칸의 가짜 요소라 움직일 때는 칸이 아니라 글을 올리고, 선은 이끄는 사람 아래에서 내려와 가운데에서 양옆으로 퍼진 뒤 사람마다 내려온다.
- **움직이는 컴포넌트(묶음 ‘움직임’):** 발표할 때 데이터가 오가고 나뉘고 모이는 모습을 보이는 부품. 움직임이 주인공이지만 편집할 때, PDF, 축소 목록의 다 보인 모습만으로도 한 장의 그림으로 읽혀야 한다(움직임은 시작 모습만 정하고 끝 모습은 CSS 그대로). 강조색은 답(흐름이 닿는 곳)에만, 선과 화살표는 이음표처럼 글자색을 옅게 한 색이다. 흐름은 단계(시스템)를 옅은 면의 상자로 나란히 두고 사이를 잇는 선으로 잇는다: 보내는 상자의 가장자리에 반쯤 걸친 점에서 선(연결도와 같은 굵기, 줄 선의 1.5배)이 나와, 끝이 받는 상자의 가장자리에 닿는 꽉 찬 세모 머리로 끝난다. 예전에는 104px 사이에 가는 선과 꺾쇠가 떠 있어 화살표 글자(⟶)를 쳐 넣은 것처럼 보였고, 다섯 단계면 상자가 좁아져 글자 크게에서 '신청 접수'가 두 줄로 꺾였다(사이는 이제 옆 칸 사이와 같은 72px). 오가는 것 앞에는 같은 잇는 선을 줄인 범례를 둔다. 발표할 때는 점이 맺히고 선이 그어지는 동안 데이터 조각이 선 끝을 타고 건너가며, 조각이 받는 상자로 들어갈 때 머리가 밀려와 닿는다. 오가는 양은 상자 아래 끝에 숫자로 두어 나란한 단계끼리 한 줄에 서고, 강조할 단계(기본은 마지막)만 옅은 강조 면과 테두리, 강조색 숫자다. 단계 상자가 210px 남짓보다 좁아지면(단계 수마다 문턱이 다르다) 상자를 세로로 쌓고 이름과 설명을 한 줄에, 양을 오른쪽 끝에 둔다: 나란히 두면 단계 이름이 두세 글자마다 꺾였고, 쌓을 때 이름과 설명을 위아래로 두면 상자 하나가 두 줄 높이라 넷만 쌓아도 칸을 넘쳤다. 가장 좁은 너비는 4칸이다(3칸에 다섯 단계를 쌓으면 860px로도 모자랐다). 칸에 면은 깔지 않는다: 단계 상자가 이미 면이라 상자 안에 상자가 된다(`rules.ts`의 `FLAT`, 연결도도 같다). 연결도는 가운데(짙은 면)를 사이에 두고 이어진 것(옅은 면)을 양옆에 나눠 두고(앞의 반, 홀수면 하나 더가 왼쪽), 상자마다 가운데 쪽으로 나온 선이 줄기에서 둥글게 꺾여 가운데 상자에 닿는다. 한쪽 단의 상자는 모두 2줄씩 차지하는 같은 높이의 칸이라(오른쪽이 하나 적으면 한 줄 내려 엇갈린다) 선의 세로 길이를 '상자 높이 + 사이'의 배수로 CSS만으로 그린다. 선은 모두 테두리로 그린다: 줄여 그린 장에서 배경으로 그린 선과 테두리로 그린 선은 픽셀에 맞춰지는 자리가 달라 이음매가 1px 어긋났다. 칸이 720px보다 좁으면 가운데를 위에 한 줄로, 이어진 것을 아래에 들여 쌓고 왼쪽 줄기에서 가지를 뻗는다(이름과 설명은 한 줄에. 위아래로 두면 여섯을 쌓아 860px로도 모자랐다). 나누기는 전체 하나를 몇 조각으로 나눈 몫이다: 무엇의 합계인지와 합계(큰 숫자, 글자색. 비우면 조각을 더한 값)를 위에, 그 아래 굵은 막대 하나를 조각의 몫대로 나눈다(사이는 8px 바탕 틈, 색은 구성비와 같은 강조색의 농담, 강조할 조각을 고르면 그것만 강조색이고 나머지는 회색 농담). 조각의 이름과 값은 그 조각 바로 아래, 막대와 같은 몫의 칸에서 조각 색의 짧은 세로선 옆에 선다: 범례를 따로 두면 색을 맞춰 보며 눈을 옮겨야 했다. 조각마다 이름과 값이 들어갈 너비를 글자 수로 어림해(`splitNeed`) 그 너비가 몫이 되는 칸 너비를 문턱으로 고르고, 칸 안쪽(면의 여백을 뺀 너비)이 그보다 좁으면 막대 아래 목록(조각 색 네모, 이름, 값과 몫)으로 바꾼다. 넓은 칸의 목록은 여러 단으로 흘린다(한 단이면 다섯 줄이 칸 높이를 다 가져갔다). 숫자는 `seriesIn`으로 한 기준에 맞춰 더하고, 단위가 섞여 더할 수 없으면 막대를 비우고 몫을 보이지 않는다. 모으기는 여러 값을 더한 합계다: 값마다 한 줄(이름, 값, 조각)을 두고 맨 아래 합계 줄을 셈의 합계 선(`--rule`, 옅은 글자색)으로 나눈다. 합계 줄은 무엇의 합계인지, 합계(강조색, 이 부품의 답), 합계 막대. 줄의 조각은 합계 막대에서 그 값이 들어갈 자리에 그대로 놓여(앞 조각들이 끝난 곳부터) 줄마다 한 칸씩 오른쪽으로 내려가는 계단이 된다: 따로 그린 작은 막대를 늘어놓으면 합계 막대의 어느 조각이 어느 값인지 색으로만 맞춰야 했다. 막대와 조각은 같은 식(몫과 앞의 틈 수)으로 자리를 잡아 조각이 막대의 제 조각 바로 위에 선다. 칸 안쪽이 960px보다 넓으면 이름, 값, 조각이 세 칸(모든 줄이 함께 쓰는 subgrid, 값은 합계까지 오른쪽 끝을 맞춘다), 좁으면 이름과 값 한 줄 아래 조각을 둔다(세 칸이면 합계가 값 칸을 넓혀 조각 자리가 300px도 남지 않았다). 칸 조립은 비율을 작은 네모 칸의 판으로 보인다: 큰 숫자(강조색) 옆(좁으면 위)에, 사이를 칸 한 변의 16%로 좁힌 판을 둔다. 한 줄을 다 쓰고 높이도 넉넉한 칸(540px부터)은 숫자 아래에 판을 눕혀 칸 너비를 다 쓰고, 칸도 72px까지 키운다: 숫자 옆에 두면 판이 칸 높이에 걸려 네모 하나로 오른쪽 끝에 서고, 숫자와 판 사이가 칸의 3분의 1 넘게 비었다. 전체가 100까지의 정수면 칸 하나가 하나(60명 중 47명이면 6줄 10칸), 아니면 100칸으로 백분율이다. 전체 칸은 비우면 100이라 열어야 보이는 칸이다(편집할 때 늘 보이면 낮은 줄에서 판 자리를 먹어 글자가 0.7까지 줄었다). 줄 수는 √n 부근에서 빈자리가 가장 적은 것으로 고른다(`tileGrid`). 채운 칸은 왼쪽 단부터 단마다 아래에서 위로 쌓여 단 하나가 전체의 열에 하나다. 상자가 납작하면 줄을 반으로 줄여 옆으로 눕히고, 넓은 칸에서는 판을 칸의 오른쪽 끝에 붙인다(숫자는 왼쪽 끝). 판의 칸은 눕혀도 한 변 20px 밑으로 줄지 않는다. 몇 중 몇(`ratio`)과 같은 '전체 가운데 몇'이지만 몇 중 몇은 셀 수 있는 것을 점(사람이면 사람 모양)으로 20개까지 하나씩 세는 조용한 부품이고, 칸 조립은 100칸까지 하나씩 세고 판 전체를 한 덩어리로 보이며 발표할 때 칸이 날아와 맞춰지는 부품이다.
- **작은 컴포넌트(묶음 ‘작게’):** 좁은 칸(3칸, 4칸)과 낮은 줄(100~220px)에 여럿 쌓거나 넷을 나란히 두는 부품. 혼자서는 할 말이 적어서, 쌓았을 때 한 목록으로, 나란할 때 한 줄로 읽히는 것이 먼저다. 그래서 면을 깔지 않는 것이 기본이고 선 하나, 글자 크기 단계, 글자색 셋으로 짠다. 넓은 칸(8칸, 12칸)에서는 늘이지 않고 짜임을 눕힌다: 위아래로 쌓던 이름과 값을 한 글자선 위 왼쪽과 오른쪽에 둔다. 늘이면 왼쪽에 글이 몰리고 오른쪽이 통째로 빈다. 소제목은 위에 글자색 선(`--rule`) 하나와 소제목 크기의 제목이다. 개요, 준비 상황의 첫 줄 선과 같은 선이라 아래에 쌓인 컴포넌트와 한 꼴로 읽힌다. 묶음의 이름이지 답이 아니라서 강조색을 쓰지 않고 면도 고를 수 없다(면을 깔면 그 자체가 칸 하나로 읽혀 묶는 힘이 사라진다). 혼자 한 줄을 쓰면 칸 아래쪽에 붙는다: 묶는 컴포넌트가 아래 줄에 있어서, 남는 높이에서 가운데나 위에 두면 앞 줄에 붙어 보였다(줄이 하나뿐인 장은 묶을 아래 줄이 없어 가운데). 덧붙임은 좁으면 아래, 넓으면(720px 넘게) 같은 줄 오른쪽 끝에 같은 글자선으로 둔다. 숫자 한 줄은 큰 숫자를 작게 줄인 것이 아니라 목록의 한 줄이다: 이름(이름표 크기, `--ink-2`), 숫자(강조색, 큰 숫자보다 세 단계 작은 62), 변화(`--ink-2`, 적은 그대로. 늘고 준 것을 색으로 가르지 않는다), 덧붙임(`--ink-3`). 아래에 옅은 선을 그어서 좁은 칸에 셋을 쌓으면 선으로 나뉜 한 목록으로 읽히고, 위의 소제목(글자색 선)과 개요처럼 한 꼴이 된다. 선은 내용에 붙어 칸에 높이가 남아도 칸 아래로 떨어지지 않는다. 옅은 면을 고르면 면이 칸을 나누므로 선을 긋지 않는다. 넓은 칸(1000px 넘게)에서는 이름을 왼쪽에 본문 크기로, 숫자와 변화를 오른쪽 끝에 두고 이름과 숫자를 한 글자선에 맞춘다(표의 한 줄처럼). 막대 하나는 목표 대비보다 조용하다: 숫자가 답이고 막대는 그 몫을 보이는 그림이라 막대는 12px로 가늘고, 자리는 옅은 선 색(`--line`), 채운 몫은 강조색이며 값이 닿은 끝만 4px 둥글다. 몫은 적은 글에서 읽는다: 전체를 적었으면 전체에 대한 몫, 아니면 백분율, 아니면 목표까지 가운데 큰 쪽에 대한 몫. 셋 다 아니면 막대 없이 글만 둔다(어긋난 그림을 그리지 않는다). 목표는 막대를 위아래로 가로지르는 글자색 눈금과 그 아래의 이름(‘목표 4억 원’, 이름은 바꿀 수 있다)이다. 이름은 눈금 자리를 따라가되 칸 밖으로 나가지 않게, 이름 앞뒤의 빈 몫을 눈금 자리의 비율로 나눠 눈금이 늘 이름 안의 같은 비율 자리에 온다. 이름과 숫자는 한 줄에 두되 안쪽이 440px보다 좁으면(3칸, 면을 깐 4칸) 이름 아래에 숫자를 둔다: 한 줄에 두면 숫자가 자리를 먼저 가져가 이름이 한두 글자씩 꺾였다. 넓은 칸에서는 이름을 격자의 왼쪽 4칸에, 막대를 그 오른쪽에, 숫자를 오른쪽 끝에 한 줄로 눕힌다. 범위는 가는 눈금(`--line`) 위의 강조색 띠(양 끝 4px 둥글게)와 그 양 끝 위의 값이다. 낮은 값은 띠의 왼쪽 끝에서 오른쪽으로, 높은 값은 오른쪽 끝에서 왼쪽으로 서서 숫자가 띠의 끝을 짚는다. 띠가 좁아 둘이 한 줄에 들지 않으면 높은 값이 아랫줄로 내려가 겹치지 않는다. 눈금은 범위와 표시를 다 담고 그 바깥에 범위 너비의 4분의 1씩 여유를 둔다(더 두면 3칸 너비에서 띠가 좁아 양 끝 값이 한 줄에 들지 않았다). 지금 값 같은 표시는 바탕색으로 속을 채운 글자색 고리라 띠 위에 있어도 밖에 있어도 같은 꼴이고, 그 이름은 막대 하나의 눈금 이름처럼 고리를 따라간다. 값을 견줄 수 없으면(‘화요일’, ‘목요일’) 그림 없이 ‘낮은 값 – 높은 값’ 글만 둔다. 넓은 칸에서는 이름을 왼쪽 4칸에 띠와 같은 높이로 둔다. 상태는 모양(진행 중, 완료, 예정, 지연)으로 고르고, 색이 아니라 꼴로 가른다: 완료는 꽉 찬 글자색 원, 진행 중은 오른쪽 반이 찬 강조색 원(강조색은 지금 움직이는 일에만), 예정은 빈 옅은 고리(`--ink-3`), 지연은 글자색 고리에 시계 바늘. 준비 상황처럼 좋음·나쁨 색으로 가르지 않는 것은 작은 칸 여럿이 각자 초록, 빨강을 띠면 장이 신호등처럼 시끄럽고, 흑백 인쇄나 강조색을 바꾼 장에서도 꼴은 그대로 읽히기 때문이다. 상태 이름은 표시 옆에 늘 글로 적는다(표시는 그 이름 글자 크기에 맞춰 같이 줄고 커진다). 넓은 칸에서는 상태, 할 일, 언제·누가를 한 줄에 두고 상태 칸을 같은 너비로 잡아 위아래로 쌓은 상태끼리 할 일의 왼쪽 끝이 맞는다. 단계 표시는 지금 몇 번째 단계인지를 번호(강조색, 숫자 한 줄의 숫자와 같은 크기)와 ‘/ 전체’로 크게 두고, 그 아래 단계마다 작은 점 하나를 한 줄 위에 둔다: 지난 단계는 글자색으로 채운 점과 글자색 선, 지금 단계는 강조색의 큰 점, 남은 단계는 빈 고리와 옅은 선. 단계 흐름이 버린 번호 동그라미가 아니라 작은 점이라 좁은 칸에서도 한 줄 높이다. 점은 줄의 양 끝에 닿는다: 단계마다 같은 너비의 칸을 두고 칸 안에서 점을 제 차례의 비율(i / (n - 1))만큼 밀면, 칸 사이에 틈이 있어도 점이 줄 전체를 고르게 나눈다. 칸이 넓으면(안쪽 640px 이상: 6칸부터) 단계 이름을 점 아래에 같은 비율로 두고(첫 이름은 왼쪽 끝, 마지막은 오른쪽 끝) 지금 단계만 글자색 굵게, 좁으면 지금 단계 이름만 번호 옆에 둔다. 좁은 칸에서 숨긴 이름은 편집할 때 제 점의 칸 위에 겹쳐 고친다(그림 위에서 고치는 칸처럼). 한 줄을 다 쓰면 이름과 번호를 왼쪽 4칸에, 점 줄을 나머지에 둔다. 날짜는 달력 한 장을 글자로만 짠 꼴이다: 일의 숫자를 왼쪽에 크게(74, 강조색, 고정폭 숫자 두 자리 너비라 8일과 22일을 쌓아도 오른쪽 글의 왼쪽 끝이 맞는다), 그 오른쪽에 달과 요일(이름표 크기), 그날 하는 일, 덧붙임을 차례로 둔다. 달력 그림은 쓰지 않는다. ‘11월 8일’을 한 줄에 두고 8만 키우면 작은 글, 큰 숫자, 작은 글이 번갈아 출렁였고, 위아래로 쌓으면 숫자 한 줄과 꼴이 같아 나란히 두었을 때 둘이 구별되지 않았다. 사람이 적은 꼴은 그대로 읽는다(11월 8일, 2026년 11월 8일 (금), 2026. 11. 8., 11/8). 달까지는 적은 그대로 보이고, 날짜 하나로 읽히지 않는 글(11월 둘째 주, 연말, 기간)은 나누지 않고 소제목 크기로 굵게 둔다. 편집할 때는 달 줄 위에 적은 글을 겹쳐 고친다. 아주 좁은 칸(안쪽 320px 이하, 3칸의 카드)에서는 숫자와 달만 한 글자선에 두고 하는 일을 그 아래 칸 너비를 다 써서, 넓은 칸에서는 덧붙임을 하는 일과 같은 글자선의 오른쪽 끝으로 보낸다. 주석은 표나 그림 아래, 또는 쌓은 단의 맨 아래에 두는 작은 글(이름표 크기, `--ink-3`)과 그 앞에 굵게 건 이름(출처, 기준, 주의, `--ink-2`)이다. 이름은 제 너비만큼의 칸을 잡고 글은 그 옆에서 줄을 바꿔도 같은 왼쪽 끝으로 내려간다(이름 밑으로 파고들면 두 줄째부터 이름이 글의 첫 낱말처럼 읽힌다). 왼쪽 세로 막대, 강조색 띠, 아이콘은 쓰지 않고 면도 고를 수 없다: 본문보다 한 걸음 물러나 있어야 하는 글이라 표시나 면이 붙으면 위의 표나 그림보다 먼저 눈에 띈다. 칸 안에서는 위에 붙어 위의 것에 이어 읽힌다.
- **계산하는 부품:** 사람이 적은 글은 그대로 보이고, 모양만 글에서 읽는다. 비율 원은 비율만큼 둘레를 채운다(반원 게이지 모양은 손잡이가 호의 끝을 따라간다). 낮은 칸에서는 원을 왼쪽에, 이름과 덧붙임을 오른쪽에 둔다: 위아래로 쌓으면 글이 높이를 먼저 가져가 원이 지름 50px대로 줄었다. 위아래로 쌓는 칸(셋이 나란한 칸 같은)에서는 원, 이름, 덧붙임 차례이고 이름은 원의 짝이 되게 소제목 크기다(세 칸 너비처럼 좁으면 이름표 크기). 원은 칸 너비의 72%까지만 키운다: 이름을 원 위의 작은 이름표로 두고 원이 칸 너비를 다 쓰던 때는 원만 크고 무엇의 비율인지가 뒤로 밀렸다. 그림은 칸에 맞춰 줄어들 뿐 넘치지 않아서, 잘리지 않는 높이를 잴 때 그림의 가장 작은 크기(원 지름 120, 반원 너비 160, 목표 대비 막대 16, 원인 순위의 그래프 높이 100, 쌓은 막대의 가장 높은 막대 100)도 본다(`measureBlocks.ts`의 `FIGURE_MIN`). 몇 중 몇은 전체가 20개까지면 점 하나가 하나, 더 많으면 점 100개로 백분율을 보이고, 단위가 '명'이면 점 대신 사람 모양. 점은 숫자 바로 아래나 옆에 한 덩어리로 둔다(점 칸이 남는 높이를 다 가져가면 점이 칸 아래에 붙어 숫자와 한참 떨어졌다). 한 줄로 늘어놓을지 줄을 늘릴지는 점이 더 커지는 쪽이고, 그 갈림의 칸 비율은 점 수마다 다르다(열 개면 5.5:1, 다섯 개면 2.7:1). 둘 다 가장 큰 크기(72px)면 한 줄로: 줄을 늘린 배치는 넓은 칸의 반도 쓰지 않는다. 숫자와 흐름은 흐름 칸의 숫자(쉼표나 띄어쓰기로 나눔, '1,200'은 한 숫자)로 작은 선을 그린다. 선 끝(지금 숫자)은 강조색 점, 선 처음은 글자색의 빈 동그라미이고 그 왼쪽에 처음 값을 적은 그대로 작게 둔다: 처음 값이 없으면 높낮이만 보여서, 넓은 칸에서는 선이 무엇에서 무엇으로 왔는지 모르는 장식처럼 보였다. 선의 높이는 너비의 반까지(한 줄을 다 쓰면 12:5)이고 남는 높이는 숫자와 선을 묶어 가운데로 둔다(한 줄에 부품이 둘 이상이면 `--bk-lift`로). 칸 높이를 다 쓰던 때는 높은 칸에서 선이 칸만 한 비탈이 됐다. 한 줄을 다 쓰는 넓은 칸에서는 숫자를 격자의 왼쪽 4칸에, 선을 5번째 칸부터 둔다(큰 숫자와 같은 나눔). 준비 상황은 상태 글(완료, 진행 중, 지연, 예정)을 진행 현황과 같은 규칙(`statusOf`)으로 읽어 표시를 고른다. 추진 일정은 기간 칸 이름을 할 일의 기간 글에서 찾아 처음 칸부터 끝 칸까지 막대를 긋고(`spanIn`, '1월'을 '11월' 안에서 잡지 않는다), 기간 칸 이름은 쉼표나 줄바꿈이 있으면 그것으로만 나누고(`colsOf`, 이름 안의 띄어쓰기는 그대로), 띄어쓰기로만 적었으면 큰 기간 뒤의 작은 기간과 때를 앞말과 한 칸으로 묶는다('10월 1주 10월 2주', '3월 상순', '1분기 말'. 예전에는 '10월', '1주'가 따로 칸이 됐다). '10월 1주 2주 3주'처럼 앞 칸의 큰 기간을 빼고 적으면 이어받고, 기간 글도 그렇게 읽는다('10월 2주~3주'는 10월 3주까지, '11월'은 11월의 칸 모두). 이름이 칸보다 길면 글자를 줄이지 않고 띄어쓰기에서 두 줄로 쌓는다. 안내 문구는 쉼표로 나눈 꼴('11월, 12월, 1월')을 보인다(편집할 때의 예시 칸이기도 해서 설명을 적지 않는다), 지금 칸을 적으면 지난 일은 흐리게, 하는 일은 강조색, 할 일은 옅은 강조색으로 칠한다. 막대가 기간을 보여 주므로 기간 글은 칸 이름보다 더 적은 것이 있을 때만 보인다. 맡은 사람은 사진을 받지 않고(사람 사진을 발표 파일에 담지 않게) 이름 첫 글자 동그라미도 두지 않는다: 회색 동그라미가 사진이 빠진 자리처럼 보였다. 나란히는 사람마다 위에 선을 긋고, 목록은 줄 사이에 선을 긋는다. 평가표는 기준마다 평가 글을 안 차례로 나눠(띄어 쓰기나 쉼표) 좋음, 보통, 나쁨(상 중 하, ○ △ ×도)을 꽉 찬 원, 반 찬 원, 빈 원으로 그리고(`gradeOf`), 읽지 못한 글('1.9억' 같은)은 그대로 보인다. 추천하는 안을 적으면 그 안에만 옅은 띠와 강조색을 쓴다. 시장 규모는 원을 바닥에 맞춰 겹치되 크기를 규모에 비례시키지 않는다(전체 시장이 목표의 백 배가 넘기 일쑤라 비례하면 목표가 점이 된다). 규모는 옆 목록의 큰 숫자로 읽고, 강조색은 마지막(목표)에만. 원인 순위(파레토)는 막대가 전체에서 그 원인의 몫, 선이 앞에서부터 더한 몫(누적 비율)이고 둘이 같은 눈금이라 눈금이 하나다(눈금 둘을 겹치지 않는다). 누적 점은 그 원인의 칸 가운데, 막대와 이름 바로 위에 찍는다: 칸의 오른쪽 끝에 찍던 때는 점이 막대와 막대 사이에 떠서 어느 원인까지 더한 몫인지 읽히지 않았다. 첫 점은 첫 막대의 머리에 앉으므로 첫 막대의 숫자만 점 지름만큼 더 올리고, 80%를 넘긴 점이 첫 점이면 몫을 따로 적지 않는다(요점 줄이 같은 몫을 말한다). 누적 비율이 80%에 닿기까지의 원인만 강조색이고, 위에 '상위 3개가 전체의 88%'처럼 요점을 계산해 적는다. 원인은 적은 차례 그대로 둔다(장 위에서 순서를 바꾼 대로 보여야 해서 저절로 줄 세우지 않고, 안내에 '많은 것부터'). 막대 숫자는 선 위에 그리고 숫자 둘레를 바탕색으로 지워, 선이 숫자 앞에서 끊긴다(원인들의 몫이 비슷하면 선이 다음 막대의 숫자 바로 위를 지난다). 그래프가 낮으면(가장 낮은 줄, 면 위의 좁은 칸) 막대 숫자를 바닥줄 아래, 이름 바로 위로 내린다: 막대 위에 두면 선이 숫자들의 높이를 지나가 숫자와 점이 한 줄로 꿰인 띠가 됐다. 막대와 선의 자리는 100px는 되어야 한다(면 위의 좁은 칸에 원인 여덟이면 40px로 줄었다). 가로 막대 모양은 원인 이름이 길 때를 위한 것으로, 원인마다 한 줄(이름, 막대, 수, 누적)이다. 막대 칸 하나가 전체(100%)이고, 앞 원인들까지 더한 몫을 옅게 깔고 그 끝에 이 원인의 몫을 진하게 잇는다. 위에서 아래로 읽으면 몫이 계단처럼 쌓여 마지막 줄에서 100%가 되고, 80% 자리에 머리부터 끝 줄까지 점선을 세워(막대 뒤라 막대가 지나는 곳에서는 가려진다) 어느 원인에서 80%를 넘는지가 보인다. 막대가 저마다 0에서 시작하면 몫은 보여도 더한 몫이 선 없이 읽히지 않는다. 막대 굵기는 줄 높이의 3분의 1 남짓(24~48px, 원인이 셋이면 굵게 여덟이면 가늘게)이다. 기간별 달성은 실적 막대와 목표 줄(막대보다 조금 넓은 가로 줄)을 겹치고, 목표를 넘은 기간만 강조색, 못 미친 기간은 회색이다. 이름 아래에 달성률, 위에 'N번 중 M번 달성'. 목표 숫자는 편집할 때만 막대 위에 칸으로 보이고 발표할 때는 목표 줄과 달성률로 읽는다. 목표와의 차이 모양은 경영 보고에서 계획 대비 편차를 그리는 꼴(IBCS의 편차 차트)이다: 목표(100%)를 가로 기준선으로 두고 기간마다 넘은 만큼 위로(강조색), 모자란 만큼 아래로(회색) 막대를 세우고 막대 끝에 +5%, −15%처럼 차이를 적는다. 실적 막대 끝의 목표 줄을 눈으로 견주지 않아도 모자란 기간이 기준선 아래로 내려가 보인다. 기준선의 높이는 차이의 범위로 정해서, 모두 목표를 넘었으면 바닥에 붙고 빈 아래 반쪽을 두지 않는다. 눈금은 10%는 잡는다: 차이의 범위만큼만 잡으면 +5%, +2%뿐인 장에서 +5% 막대가 그래프 높이를 다 채워 크게 넘은 것처럼 보였다. 이름 아래에는 실적과 목표를 '42 / 40'으로 둔다. 항목별 증감은 0을 세로 선으로 두고 늘어난 것은 오른쪽, 줄어든 것은 왼쪽으로 뻗는다. 항목 이름은 막대 반대쪽, 0 선 바로 옆에 둔다(늘어난 항목은 0 선 왼쪽, 줄어든 항목은 오른쪽): 이름을 칸 왼쪽 끝에 모으면 0 선이 가운데쯤이라 늘어난 항목은 이름과 막대 사이가 칸의 반 가까이 비어 한 줄로 읽히지 않았다. 0의 자리와 막대의 눈금은 막대를 가장 길게 잡되 막대 끝의 숫자와 0 선 반대쪽의 이름이 칸 안에 들게 CSS가 칸 너비로 셈한다(이름과 숫자의 폭은 글자 수로 어림). 한쪽에만 막대가 있으면 0 선이 이름 바로 옆으로 가서 보통의 가로 막대가 되고, 이름이 칸의 42%보다 길면 줄을 바꾼다. 늘어난 것이 좋은지(매출) 나쁜지(비용)는 장마다 달라서 강조할 쪽을 모양으로 고른다(늘어난 쪽 강조, 줄어든 쪽 강조). 쌓은 막대는 나눈 것 이름(쉼표로 나눔, 이름 안의 띄어쓰기는 그대로)과 기간마다의 값(쉼표로 나눔)으로 쌓고, 맨 아래 칸이 강조색, 위로 갈수록 옅다. 값 그대로와 100%로 두 모양이고, 칸 안 숫자는 칸이 숫자보다 높을 때만 보인다(칸마다 크기 상자의 컨테이너 쿼리). 세 세로 막대 차트는 낮은 칸에서 소제목과 표시 줄을 한 줄에 놓아 막대 높이를 지킨다. 막대 너비는 항목 칸의 반 남짓(56%)이고 가장 넓어도 160px이다(120px까지였을 때는 한 줄을 다 쓰는 막대 넷 사이가 막대의 두 배 넘게 비었다). 색 표(히트맵)는 줄마다의 값(쉼표로 나눔, '-'는 빈 칸)을 강조색 하나의 진하기로 칠하고(가장 낮은 값이 가장 옅고 가장 높은 값이 강조색 그대로), 칸마다 숫자를 그대로 둔다. 숫자 색은 칸의 진하기가 문턱을 넘으면 강조색 위의 글자색으로 바꾸는데, 문턱은 강조색 아홉, 두 테마, 카드에서 3:1 밑으로 내려가지 않게 셈한 값이다(검은 바탕은 더 늦게, 강조색 바탕은 짙은 면까지 칠한다). 표 전체에서 견주면 가장 높은 칸과 낮은 칸에 고리를 두르고 위에 어디인지 적고, 줄마다 견주면(줄마다 단위가 다를 때) 고리 없이 줄마다 제 눈금이다. 지표 흐름표는 지표마다 흐름 칸으로 작은 선을 긋고 지금 값(마지막)과 바로 앞 또는 처음보다 바뀐 만큼을 나란히 둔다. 선은 지표마다 제 눈금이라 단위가 다른 지표를 한 표에 두고, 강조색은 지금(선 끝 점과 지금 값)에만, 바뀐 만큼은 오른 것이 좋은지가 지표마다 달라 색 없이 ▲▼로 적는다(단위가 %면 %p).
- **자리(판, `deck/blocks/board.ts`):** 부품 장의 본문은 가로 12칸, 세로 12칸의 판이다. 부품마다 판의 네모 자리(`Block.at`: x, y, 너비, 높이를 칸 수로)를 갖고, 판은 늘 빈틈없이 덮인다: 판을 한 번에 가로나 세로로 자르고, 자른 조각을 다시 자르는 꼴(나무, `Tree`)만 쓴다. 그래서 아무 데나 빈칸이 남거나 부품이 겹칠 일이 없고, 옆 칸 사이는 72px(`BLOCK_COL_GAP`), 위아래 사이는 48px(`BLOCK_GAP`)로 늘 같다. 줄과 칸이 있던 때(0.4까지, 줄은 셋, 한 줄에 칸은 셋, 칸 너비는 정해진 비율, 한 칸에 위아래로 셋까지 쌓기)는 작은 부품을 큰 부품 사이에 끼울 수 없고 칸이 늘 줄 높이만큼 커서 칸 안이 비었다. 판은 작은 부품이 2×3칸, 큰 차트가 8×7칸처럼 제 크기를 갖고, 숫자 둘을 위아래로 두고 옆에 차트를 두는 짜임도 따로 쌓기 없이 자른 조각으로 된다. 예전 발표의 줄은 열 때 같은 짜임의 판으로 바꾼다(`legacy.ts`의 `boardFromRows`, `migrateDeck`. `Deck.version` 2). 한 장에 부품은 열까지, 그 가운데 작은 부품(`BlockSpec.small`)이 아닌 것은 여섯까지(`MAX_LARGE`). 크기는 사람이 정하지 않아도 판이 고른다: 옆에 넣으면 그 묶음의 부품들이 보기 좋은 너비(`prefSpan`)의 비율로 너비를 다시 나누고(숫자 셋은 4·4·4), 위아래로 넣으면 그 너비에서 잘리지 않는 가장 낮은 높이를 바라고 남는 높이는 받는 차례대로 나눈다: 차트, 표, 그림처럼 높이를 받으면 커지는 부품(`STRETCHY`)이 먼저, 그다음 면이 있는 부품(강조 상자, 카드 면: 면째 커져서 빈 자리로 보이지 않는다), 모두 글과 숫자뿐이면 모두가 바라는 높이의 비율대로. 예전처럼 남는 높이를 똑같이 나누면 한 줄로 늘어선 점 목록이 판의 절반을 받아 글 위아래가 비었다. 글자 단계는 칸 너비로도 커져서 넓을수록 높이가 덜 들지는 않는다(숫자 카드는 3칸에서 4줄, 4칸에서 5줄). 그래서 옆으로 나눈 가지가 들어가는지는 가장 작은 너비의 합이 아니라 자식마다 들어가는 너비로 그 너비를 딱 나눌 수 있는지로 보고, 놓을 때도 나눈 크기를 그런 나눔 가운데 바라는 크기와 가장 덜 다른 것으로 고친다(`sizesFor`, 남는 길이는 받는 차례가 높은 부품에게). 가장 작은 너비의 합으로 보던 때는 들어간다고 본 판을 놓지 못해 예전 자리에 글자를 줄였고, 구성비 띠(6~8칸에서 7줄, 9칸부터 8줄) 하나만 든 줄에 7줄을 주어 놓지 못하자 크기를 따지지 않고 놓아 띠가 한 줄로 찌그러졌다. 잘리지 않는 높이는 부품, 모양, 바탕(그대로 / 카드와 강조색 면), 항목 수, 칸 너비마다 갤러리에서 고를 수 있는 글꼴 짝마다 잰 표(`deck/blockHeights.ts`, 높은 쪽)에 여유 10px(`HEIGHT_SLACK`)와 차트처럼 너무 납작하면 보기 나쁜 부품의 바닥 높이를 더한 것이다(판의 칸 수로 올린다, `rowsFor`). 여유를 두는 것은 잰 높이가 글이 딱 들어가는 높이라서다: 같은 부품을 다른 창에서 다시 재면 줄바꿈이 갈리는 자리의 글자 폭이 조금씩 달라 10~20px씩 달랐고, 딱 맞춘 칸은 그 창에서 글자를 한두 단계 줄였다. 윈도우의 글자 그리기는 또 다르다. 항목이 셋 이상인 목록은 칸이 낮으면 줄 사이가 붙어서 240px 밑으로 두지 않지만, 항목이 옆으로 늘어서는 너비(항목이 늘어도 높이가 같은 너비)에서는 그 바닥이 없다. 선 차트(추이, 두 값 비교의 선)는 판 너비를 다 쓰면 바닥 높이를 80px 낮춘다: 납작해 보이는 것은 높이가 아니라 너비와 높이의 비율이라서. 막대 차트는 낮추지 않는다(막대 위 숫자, 아래 이름과 증감의 자리는 너비와 상관없어서 낮춘 만큼 막대만 눌린다). 높이를 가늠하는 본문 상자는 편집 화면 기준이다(`boardAreaH`, 비운 제목의 안내도 자리를 차지한다). 발표 화면은 이보다 넓어서 잘리지 않는다. 부품이 커지면(항목을 더하거나 모양, 바탕을 바꾸거나 제목이 길어지거나 글자 크기를 바꾸면) 편집기의 모든 고침이 판을 다시 맞춰(`settleDeck`) 모자란 부품이 옆에서 자리를 받는다. AI의 제안을 적용할 때와 조합 시험도 같은 규칙이다. 그래도 들어가지 않는 자리는 놓을 자리로 고르지 않고, 항목 추가와 모양 바꾸기도 막는다. 끄는 동안 보이는 모습과 놓은 뒤, AI의 제안이 같은 계산을 한다. 막을 때는 까닭(`NoRoom`: 부품 수, 큰 부품 수, 너무 좁아지는 칸, 높이)을 끄는 동안 놓을 자리 아래에, 부품 고르기 카드에('이 장엔 자리가 없어요', 눌러서 까닭. 어느 부품도 못 넣으면 카드마다 붙이지 않고 위에 한 번), 도구 단추에 보인다. 판 너비를 혼자 써야 하는 부품(표처럼 옆에 다른 부품이 서면 읽히지 않는 것)과 함께 둘 수 없는 짝(표 옆 목록, 좁은 칸의 로고 열 개)은 본문 높이를 몰라도 너비만으로 막는다(`soloBeside`, 문서 보기와 시험에서도 같다). 그래도 글을 길게 쓰거나 파일에서 읽어 넘치면 `slides/fitBlocks.ts`가 넘치는 칸의 글자를 단계로 줄인다(`--bk-fit`). 잰 높이는 보통 글자 크기라 크게나 명조에서 딱 그 높이면 모자랄 수 있다. 한 줄을 다 쓰지 않는 칸은 한쪽에 이음표가 선 너비(`LINK_PAD`만큼 좁게)와 온 너비 둘 다 재어 높은 쪽을 쓴다: 칸 너비로 크기가 정해지는 한 줄 숫자(큰 숫자의 값)는 넓을수록 커서 더 높이 든다. 좁은 너비로만 재던 때는 3칸 숫자 카드가 온 너비에서 넘쳐 글자를 두 단계 줄였다. 잴 때는 편집 표시(빈칸의 면, '이 항목 빼기', 그림 칸의 '바꾸기')를 뺀다(`.is-fitting`). 빼지 않으면 칸 옆으로 나온 단추를 넘침으로 보고 편집 화면에서만 글자를 줄인다. 넘침은 칸 밖뿐 아니라 카드의 안쪽 여백까지 내려간 글, 서로 겹친 글, 옆 항목 자리로 넘어간 글까지 본다(글자 자리는 글꼴마다 캔버스로 잰다). 칠한 칸이 늘어선 것(색 표의 칸들, `data-fit-box`)은 줄마다 보고 안쪽 여백에 조금도 들어가지 않게 한다: 글자는 여백에 몇 px 걸쳐도 티가 안 나지만, 칠한 칸이 들어가면 그쪽 여백만 좁아 보인다(크게에서 색 표 여덟 줄이 아래 여백을 6px 먹었다). 편집 칸은 띄어쓰기를 그대로 두어(pre-wrap) 줄 끝 띄어쓰기가 칸 밖에 걸리는데, 그것은 글로 세지 않는다. 거꾸로 넘치는 칸이 없으면 모든 칸의 글자를 같은 단계로 키우고(한 단계, 1.2배), 그래도 칸에 높이가 남으면 줄이 쌓이는 부품(점 목록, 개요, 걱정과 대책, 준비 상황, 추진 일정, 평가표, 시장 규모, 맡은 사람 목록, 표)은 칸마다 줄 사이를 넓혀 칸 바닥까지 채운다(`--bk-air`, 줄 위아래에 최대 24px, 넘치지 않는 가장 넓은 값을 1px 단위로 찾는다). 글자를 더 키우면 장마다 글자 크기가 들쭉날쭉하고, 가운데에 작게 모으면 위아래가 빈다. 예전에는 넓히는 값을 24, 18, 12, 6 네 단계에서만 골라서 줄이 넷인 목록은 한 단계가 칸 높이로 100px쯤이었다: 한 단계만 넘쳐도 아래 단계로 내려가 옆의 색 표는 바닥까지 닿는데 지표 흐름표만 칸의 4분의 3에서 끝났다. 판의 같은 띠(가장 바깥 줄)에 부품이 둘 이상이면, 칸 높이를 거의 다(80%) 쓰는 부품(차트, 표, 바닥까지 채운 목록) 옆에서 칸의 60%도 쓰지 않는 짧은 부품(두 줄 글, 숫자, 강조 상자)은 자기들끼리 띠 가운데로 내린다(`--bk-lift`). 소제목이 있어도 내린다: 차트 옆 소제목과 두 줄 글을 위에 붙여 두면 칸 아래 절반이 통째로 비어 옆 칸만 꽉 차 보였다. 60~80%를 쓰는 부품은 위에 그대로 둔다(조금만 내려가면 나란한 소제목의 윗선이 어긋나 실수처럼 보인다). 키울 때는 글이 없는 그림(구성비 띠, 막대, 원)이 키우기 전의 반 밑으로 눌려도 넘친 것으로 본다(글이 없어서 넘침으로 보이지 않는다). 앱과 내보낸 HTML이 같은 함수를 쓴다. 발표할 때 움직이는 중인 장은 재지 않는다: 움직임 엔진이 움직이는 동안 `data-mo-play`를 붙이고 끝나면 떼며 `mo-end`를 보낸다. 그동안 글과 막대는 옮겨지거나 커지는 중이고 숫자는 0부터 굴러가는 중이라, 재면 움직이며 넘긴 장과 뒤로 돌아온 장의 글자 크기가 달랐다. 맞춘 값은 그대로 두었다가 끝나면 다시 맞춘다(처음 맞추기는 움직임이 걸리기 전이다). 안 보이는 장(내보낸 파일이 발표하는 동안 숨긴 장)은 맞춘 값을 지우지 않고 건너뛰고, 여백에 걸쳐도 되는 틈은 캔버스 px라 장을 그리는 크기와 상관없다.
- **놓을 자리 찾기(`dropTarget`, `place.ts`):** 손 아래에서 바라는 자리를 먼저 바라는 차례대로 고른다. 판 둘레(본문 가장자리에서 안쪽으로 조금)는 판의 그 쪽 끝(맨 위·아래 새 줄, 맨 왼쪽·오른쪽 새 칸), 칸 사이 선 둘레는 그 선 위에 끼우기, 부품 안이면 가장 가까운 변 쪽(그 부품 옆, 그다음 그 부품이 든 묶음 옆)이다. 옮기는 중이면 부품 가운데는 그 부품과 맞바꾸기다(맞바꾸면 자리와 크기를 서로 바꾸고 이음표도 함께 바꾼다). 바라는 자리에 둘 수 없으면 다음으로 바라는 자리, 그래도 안 되면 둘 수 있는 자리 가운데 놓일 자리가 가장 가까운 곳이라 대충 놓아도 늘 정해진 자리에 들어간다. 옮기는 부품은 빼고 다시 넣는 것이라 새 자리에서 크기를 새로 받는다. 손이 지금 보이는 놓을 자리(파란 점선 칸) 안에 있으면 자리를 바꾸지 않는다: 자리 찾기는 끄는 부품을 뺀 판으로 재는데 화면에는 놓을 자리를 넣은 판이 보여서, 그 칸 안에서 손을 움직였는데 다른 데로 튀면 보이는 것과 놓이는 곳이 어긋난다. 끄는 동안에는 판의 칸 점(12×12)이 옅게 보여 부품이 칸에 붙는다는 것을 알린다.
- **위아래로 놓기:** 작은 컴포넌트를 큰 것 옆에 모아 두는 짜임(숫자 둘을 위아래로 두고 옆에 차트, 강조 상자 아래 주석)은 부품의 위나 아래에 놓아 판을 그 너비 안에서 자른다(따로 쌓는 값은 없다. 예전의 `stack`은 열 때 판으로 바꾼다). 아래에 놓은 부품은 위 부품의 너비를 나눠 쓰고 옆 부품은 그대로다. 위아래로 놓인 부품(`isStacked`)은 가운데로 내리지 않는다(위아래가 이미 높이를 나눠 썼다). 부품을 빼면 위아래나 옆 이웃이 그 자리를 덮는다. 발표할 때 비워 둔 부품은 빼고 옆 부품이 넓혀 덮는다(`shownBlocks`). 움직일 때는 읽는 차례(위에서 아래, 왼쪽에서 오른쪽)로 하나씩 나온다.
- **끌기(`src/screens/editor/BlockEditor.tsx`):** 6px 움직이면 끌기 시작. 집어 든 부품은 손 아래 크기로 줄어 들리고 끄는 빠르기만큼 살짝 기운다. 놓일 자리에는 파란 점선 칸이 생기고 다른 부품이 미끄러져 비켜 난다(FLIP, 스프링). 놓으면 부품이 손에서 나와 제 비율 그대로 자리로 커지며 맞춰진다. 장 밖에 놓거나 Esc면 그만둔다. 끄는 동안은 저장하지 않고 놓을 때 한 번만 바꿔서 되돌리기 한 번이면 돌아온다.
- **부품 고르기(`BlockLibrary.tsx`, 화면 이름은 ‘컴포넌트’):** 오른쪽 칸의 탭 두 개(이 장 설정 / 컴포넌트) 가운데 하나. 탭을 바꿔도 칸 폭이 같아 슬라이드 크기가 출렁이지 않고, 지금 어디에 있는지와 어디로 돌아가는지가 늘 보인다. 오른쪽 칸을 접는 좁은 창(1100px 아래)에서만 슬라이드 아래 '컴포넌트 넣기'로 띄운다. 넣는 법은 탭 줄의 (i)에 접어 두고, 이 장이 컴포넌트 장이 아니면 상자 없는 한 줄 알림(‘넣으면 컴포넌트 장이 돼요’, ‘지금 바꾸기’). 묶음은 같은 폭으로 나눈 글자 칩 한 줄(전체, 글, 숫자, 차트, 일정, 비교, 이미지, 이음표)로 놓고, 목록에서는 묶음마다 긴 이름, 개수, 무엇이 들어 있는지 한 줄(`BLOCK_GROUPS`의 `short`, `description`). 카드는 예시 내용을 넣은 그림과 이름이고(테두리 상자 없이), 마우스를 올리면 그림이 떠오르며 발표할 때의 움직임을 한 번 보여 준다. 끌어다 놓거나, 누르면 알맞은 자리(`autoTarget`)에 카드에서 날아가 들어간다.
- **부품 장이 아닌 장에 놓으면** 그 장을 같은 내용의 부품 장으로 바꿔 넣는다(`composeFrom`, 글은 하나도 빠지지 않는다. 테스트가 모든 레이아웃을 확인). 한 문장 메시지는 그 문장이 장의 제목, 근거가 부제가 되고 판은 비운다: 핵심 한 줄 부품으로 옮기면 빈 제목 칸 아래에 같은 문장이 작게 서서 같은 말을 두 번 쓰는 장처럼 보였다. 예전에 부품 장이었던 장(부품이 여럿인 부품 장을 다른 레이아웃으로 바꾸면 줄은 장에 남겨 둔다)은 남겨 둔 줄을 되살린다. 장을 부품 장으로 바꾸는 곳(레이아웃 바꾸기, 부품 장으로 바꾸기, 끌어 넣기, AI 제안)은 모두 `asCompose` 하나를 쓴다. 따로 `composeFrom`을 부르던 AI 제안은 남겨 둔 줄을 덮어써 그 안의 글을 지웠다. 끄는 동안 바뀔 모습을 미리 보여 준다. 표지와 단락 장, 자리가 없는 장이면 다음 장에 부품 장을 새로 만든다. 레이아웃 부품 하나뿐인 부품 장은 그 레이아웃으로 되돌릴 수 있다(`unwrapCompose`).
- **내 컴포넌트(`deck/blocks/saved.ts`, `screens/editor/SavedParts.tsx`):** 조립해 둔 것을 다시 쓴다. 고른 컴포넌트의 도구 '내 컴포넌트로 저장'에서 그 컴포넌트, 그 줄(놓인 비율 그대로), 장 전체(제목 칸, 바탕, 움직임, 장 넘기기, 나오는 차례까지) 가운데 하나를 고른다. 글과 바탕, 나오는 때도 같이 간다. 컴포넌트 고르기 맨 위의 '기본 컴포넌트 / 내 컴포넌트'로 바꿔 본다. 컴포넌트 하나는 기본 컴포넌트와 같은 길(끌어다 놓기, 누르면 알맞은 자리)로, 한 줄은 이 장 맨 아래에, 장 하나는 이 장 다음에 새 장으로 넣는다. 넣을 때마다 부품, 줄, 항목의 id를 새로 만든다(`freshRows`). 기본 컴포넌트와 같은 규칙으로 막는다: 부품 수, 줄 수, 장 높이를 넘으면(`rowsIssue`) 카드가 흐려지고 까닭과 '다음 장에 새로 넣기'를 보인다. 작은 그림은 저장할 때 장에서 차지한 크기(`size`)로 그린다: 높이에 따라 짜임을 바꾸는 컴포넌트가 다른 높이로 그려지면 저장한 모습과 달라 보였다. 너무 넓적하면 줄 높이는 두고 위아래 여백만 늘린다. 저장한 것은 발표 밖에 두고 AI에게 보내지 않는다.
- **부품의 테두리(`slides/blockFrame.ts`):** 편집 화면에서 올리거나 고른 부품의 테두리는 칸이 아니라 부품이 그린 것(글자 줄, 그림, 면과 선)의 둘레에 14px 띄워 두른다. 옅은 면과 진한 면은 면이 곧 부품이라 칸 그대로. 칸에 두르면 차트 옆의 두 줄 글이나 가운데로 내린 숫자의 테두리만 칸 높이만큼 크게 떠서, 부품과 테두리의 크기가 맞지 않아 보였다. 고른 부품의 테두리는 진한 선에 아주 옅은 면이고, 그 안의 칸에 글을 쓰는 동안은 옅어져 쓰는 칸의 실선 하나만 또렷하다(예전에는 부품 테두리와 칸 테두리가 같은 굵기와 색으로 두 겹이었다). 끌기 손잡이와 위에 뜨는 도구도 이 테두리에 붙는다. 맞추기(`fitBlocks`)가 끝난 뒤에 재므로 글을 고치거나 글자가 커지고 줄 사이가 넓어지면 테두리도 따라간다.
- **고른 부품의 도구:** 장 아래 도구 줄이 그 부품의 도구로 바뀌고 오른쪽에 '완료'(Esc)가 생긴다. 칸 위에 띄우면 제목이나 위 줄 부품을 덮어서다. 메뉴는 위로 열리고 Esc는 메뉴만 닫는다. 고른 부품에는 왼쪽 위에 이름표(끌기 손잡이)가 남는다. 끌어 옮기기(화살표 키로도), 바탕(없음, 옅은 면, 진한 면: 지금 바탕의 이름을 보이고 누르면 설명과 함께 고른다), 움직임(알아서, 올라오기, 나타나기, 펼치기, 밀려오기, 튀어나오기, 다가오기, 세우기, 초점 맞추기, 없음; 올리면 그 자리에서 미리 보기, 메뉴의 작은 그림도 같은 움직임), 모양, 항목 추가, 복제, 빼기(Delete). 판을 나누는 선(옆 칸 사이, 위아래 사이)을 끌면 선 양쪽이 크기를 주고받고 판의 칸에 붙는다(`moveGutter`). 잘리지 않을 크기 밖으로는 끌리지 않고, 더 끌 수 없는 쪽으로 끌면 무엇이 잘리는지 한 번 알린다(`gutterLimit`). 본문 위에 손을 올리면 선의 손잡이가 옅게 보여 끌 수 있는 곳을 알린다. 새로 넣은 부품은 자리에 맞춰진 뒤 발표할 때의 움직임을 한 번 보여 준다(움직임 '없음'이면 안 한다).
- **이미지 넣기 (`screens/editor/useImageInput.ts`):** 화면 캡처를 붙여 넣거나(Ctrl+V) 이미지 파일을 장 위에 끌어다 놓으면 바로 들어간다. 이미지 컴포넌트를 먼저 찾아 넣고 칸을 눌러 파일을 고르던 길이 회사에서 가장 흔한 일(캡처해서 붙이기)에 너무 멀었다. 넣을 곳은 고른 이미지 컴포넌트, 비어 있는 이미지 칸(이미지와 설명 장의 이미지, 빈 이미지 컴포넌트), 그 밖에는 새 이미지 컴포넌트를 컴포넌트를 넣을 때와 같은 길로(자리가 없으면 다음 장). 끄는 동안 장에 테두리와 '놓으면 이 장에 이미지로 들어가요'가 뜬다. 이미지의 가로세로는 파일 머리에서 읽고(`lib/image.ts`의 `imageSize`: PNG, JPEG와 회전 정보, GIF, WebP, SVG), 놓을 자리는 이미지 비율에 가장 잘 맞는 곳(`imageTarget`: 세로 사진은 옆 칸으로, 넓은 캡처는 넓은 칸으로, 같으면 이미 쓴 내용 뒤에), 그 줄의 칸 너비도 이미지에 맞춘다(`fitImage`. 이미지 옆에 다른 컴포넌트를 넣거나 뺄 때도). 보이는 법은 사진(JPEG)이 칸과 비율이 비슷할 때만 꽉 채우기, 화면 캡처와 도면은 잘리지 않게 전체 보이기. 전체 보이기는 이미지 비율대로 가장 크게 그리고 모서리와 옅은 테두리를 이미지에 둔다(회색 판 위에 얹으면 그림 두 장을 겹친 것처럼 보였다). 설명은 이미지 바로 밑에 붙는다. 이미지 칸은 280px 밑으로 낮아지지 않는다(낮으면 캡처의 글씨를 못 읽는다).
- **움직임:** 부품을 읽는 차례대로 하나씩. '알아서'면 레이아웃 부품은 그 레이아웃의 연출을 그 칸 안에서, 부품 장만의 부품은 부품마다 짠 연출로(`src/motion/engine.ts`의 `block`).
- **이음표(`BLOCK_LINKS`):** 화살표, 더하기, 결과(=), 견주기(vs). 두 부품이 어떻게 이어지는지를 부품 사이에 끼워 보인다. 칸을 차지하지 않고 칸 사이에 서서, 칸 너비 비율과 칸 수 같은 자리 규칙은 그대로다. 나란한 두 부품 사이(왼쪽 부품의 `link`, 오른쪽 변)와 위아래 두 부품 사이(위 부품의 `linkBelow`, 아래 변)에만 서고, 판의 끝에는 없다(`tidyLinks`: 부품을 빼거나 옮겨 설 데가 없어지면 뺀다). 이음표 양쪽은 말이 되는 짝이어야 한다(`linkFits`): 결과(=)는 오른쪽(아래)이 숫자나 글, 화살표는 같은 종류끼리이거나 숫자나 글로 가는 것, 더하기와 견주기는 같은 종류끼리(종류는 숫자, 글, 목록, 차트, 흐름, 표, 그림). 비율 원 옆의 '='으로 지도가 이어지는 것처럼 엉뚱한 짝은 끼우지 않는다. 이음표가 선 사이는 양쪽 칸이 24px씩 비켜(`LINK_PAD`) 이음표가 혼자 서는 96px을 낸다. 칸의 면이나 가장자리에 걸치면 한쪽 칸에 가려 깨져 보여서다(조합 시험 `checkCombos`가 칸에 걸친 이음표를 찾는다). 위아래 사이에 서면 위아래 부품이 그만큼 낮아져 잘리지 않을 높이에 더한다(`linkRoom`). 옆 사이 이음표가 선 부품은 칸 가운데에 둔다(위에 붙이면 이음표만 아래에 떠 보인다). 모양은 조판 기호처럼 작고 가늘게: 화살표는 선 없는 가는 꺾쇠(›, 전과 후와 두 안 비교의 화살표와 같은 그림), 더하기와 같음은 같은 굵기(2.5)의 가는 획, 견주기는 이름표 크기의 작은 글자(vs). 글자 화살표(→), 가는 꺾쇠, 괘선으로 잇기를 그려 견주고 꺾쇠를 골랐다: 글자 화살표는 쳐 넣은 글처럼, 괘선은 방향을 잃었다. 색은 강조색이 아니라 옅은 글자색(`--ink-3`)이다(답이 아니라 관계라서). 부품 고르기의 '이음표' 묶음에서 끌어 칸 사이에 놓으면 가장 가까운 사이에 붙고, 양쪽 칸이 비켜 나는 모습을 미리 보여 준다. 누르면 고른 부품의 오른쪽(없으면 처음 빈 사이)에 들어간다. 장의 이음표를 누르면 도구 줄에서 모양을 바꾸거나 뺀다(Delete). 부품을 끌어 옮기면 그 부품 오른쪽의 이음표는 두고 간다. 발표할 때는 앞 부품이 나온 뒤에 나온다(화살표는 가리키는 쪽으로 밀려 나오고, 나머지는 튀어나온다). 비교 레이아웃의 화살표도 같은 색이고, 표 모양의 줄 화살표는 같은 그림이다(두 면 모양은 두 면에 붙는 잇는 선, 위 '비교'). 화살표 그림은 하나다(`slides/arrow.tsx`의 `ArrowMark`): 선과 꽉 찬 세모 머리. 선 끝에 꺾쇠를 얹은 흔한 아이콘은 글자 화살표(→)를 쳐 넣은 것처럼 보여서 흐름의 잇는 선과 같은 머리로 바꿨다. 전과 후, 걱정과 대책, 비교 표의 줄 화살표도 같은 그림이고 칸마다 크기만 정한다(굵기를 칸마다 2, 3으로 따로 두어 같은 화살표가 장마다 다른 무게로 보였다). 줄 화살표는 40px 밑으로 줄이지 않는다: 32px에서는 머리가 점처럼 뭉개졌다.
- **글자:** 칸이 좁거나 낮으면 컨테이너 쿼리로 글자를 글자 크기 비율(1.2)의 단계로 줄인다. 반 칸, 3분의 1 칸이나 높이 300px 밑은 한 단계(0.84), 4분의 1 칸은 두 단계(0.7)이고, 높이로는 한 단계까지다. 좁고 낮아도 곱하지 않고 작은 쪽 하나만 쓴다. 곱하면 제목, 숫자, 본문이 모두 바닥(22px, `--fs-min`)까지 내려가 크기 차이가 없어진다. 한 줄에 부품이 둘 이상이면 넓은 칸도 옆 칸과 같은 단계로 둔다(`.is-shared`). 단계가 다르면 나란한 소제목의 크기가 어긋나 줄이 비뚤어 보인다. 같은 줄의 부품은 소제목 윗선을 맞추려고 모두 위에서부터 그린다. 칸 높이를 다 쓰는 차트, 표 옆의 짧은 부품만 묶음째 가운데로 내린다(`--bk-lift`, `fitBlocks.ts`): 차트 옆에서 위에 붙어 있으면 아래 절반이 통째로 빈다. 그런 부품이 없는 줄은 위에 그대로 두고 남는 높이는 장 맨 아래에 모은다(아래 '쌓기'). 글이 시작하는 선은 칸마다가 아니라 줄에 하나다: 옅은 면, 진한 면은 안쪽 여백만큼 글이 아래에서 시작하니, 옆 칸의 글도 그 선에서 시작한다(예전에는 강조 상자 옆의 핵심 한 줄이 칸 위에 붙고 면 안의 글만 내려가 있었다). 가장 낮은 줄에서 칸을 다 쓴 긴 글을 차트처럼 묶음에서 빼면 짧은 쪽만 내려가 소제목 윗선이 어긋났다. 내리지 않는 부품(차트, 표, 그림)은 묶음에 넣지 않고, 그 옆에서는 소제목 없는 짧은 부품(숫자, 강조 상자)만 가운데로 내린다. 차트 옆의 숫자가 칸 위에 붙으면 아래 절반이 비고, 차트 옆의 목록까지 내리면 차트의 소제목과 윗선이 어긋난다. 칸의 80% 넘게 쓰는 목록, 준비 상황, 묻고 답하기 옆에 소제목 없는 짧은 부품이 있을 때도 그 글 칸을 차트처럼 빼고 짧은 부품끼리 가운데로 내린다(짧은 부품이 위 3분의 1에 몰리고 아래가 비었다). 차트 옆의 숫자는 한두 단계 키우지만, 몇 중 몇과 비율 원처럼 자기 큰 숫자가 있는 그림 옆에서는 키우지 않는다(나란한 두 숫자의 크기가 달라진다). 넓고 낮은 칸에서 숫자 옆에 점을 눕힌 몇 중 몇은 스스로 가운데에 서므로 묶음에서 뺀다. 남는 높이는 맨 아래 한곳에 모은다(아래 '쌓기').
- **짜임 바꾸기:** 그보다 작은 자리에서는 글자를 더 줄이지 않고 부품이 짜임을 바꾼다(공개 디자인 시스템의 '흘리기, 쌓기, 모양 바꾸기', [OPEN-SOURCE.md](OPEN-SOURCE.md)). 넓고 낮으면 목록을 여러 단으로 흘리고(개요, 준비 상황, 맡은 사람, 목차, 한 줄을 다 쓰는 지표 흐름표의 넷 이상, 한 줄을 다 쓰는 점 목록. 점 목록은 둘이나 셋이면 나란히, 넷부터 두 단: 한 단으로 두면 짧은 요점이 왼쪽 3분의 1에 몰리고 오른쪽이 통째로 비었다. 다만 단 나누기는 높이가 모자랄 때의 짜임이라, 칸이 넉넉히 높으면 한 단으로 두고 소제목을 왼쪽 반, 목록을 오른쪽 반에 나란히 둔다: 높이가 넉넉한데 다섯을 셋과 둘로 나누면 목록이 장의 왼쪽 위 4분의 1에 몰리고 아래 3분의 1이 비었다. 3분의 2 칸(900~1300px)의 낮은 줄에서는 넷 이상을 두 단으로 흘린다: 한 단이면 글자를 한 단계 줄이고 오른쪽 3분의 2가 비었다) 쌓인 것을 옆으로 눕힌다(큰 숫자는 숫자 오른쪽에 이름과 설명, 전과 후도 두 숫자 오른쪽에 이름과 덧붙임 글. 한 줄을 다 쓰는 넓은 칸(1200px 넘고 높이의 두 배 넘게 넓은)에서는 거꾸로 이름과 설명을 격자의 왼쪽 4칸에, 숫자를 5번째 칸부터 둔다: 숫자 옆에 이름을 붙이면 묶음이 왼쪽에 몰려 오른쪽 절반 넘게 비었고, 격자 선에 맞추면 위아래 줄의 칸 나눔과도 줄이 맞는다. 숫자와 흐름은 숫자 옆에 선, 강점과 약점은 네 칸 한 줄, 2×2 우선순위는 칸마다 이름 옆에 설명). 좁고 높으면 나란한 것을 줄로 쌓는다(핵심 숫자, 하나 크게의 나머지 숫자, 목차 나란히): 나란히 두면 숫자가 칸의 3분의 1 너비에 맞춰 작아지고 칸 높이 가운데에 낮은 띠만 남는다. 줄로 쌓으면 줄이 칸 높이를 나눠 채우고, 줄이 넉넉하면 이름을 숫자 위에 두어 숫자가 칸 너비를 다 쓴다. 다만 그쪽 숫자가 더 클 때만이다: 위아래로 두면 줄마다 이름과 설명의 높이를 숫자가 내주고, 옆에 두면 숫자가 칸 너비의 56%까지만 써서 칸이 넓을수록 더 높아야 위아래 쪽이 이긴다. 너비와 상관없이 정한 높이에서 바꾸던 때는 반 칸(804×624)의 숫자 셋이 옆에 두면 128px인데 62px가 되었다(둘은 154px, 넷은 108px). 핵심 숫자 부품의 숫자는 나란한 것끼리 한 크기이고, 그 크기는 가장 긴 숫자가 들어가는 글자 크기 단계에서 고른다(칸 너비로 그대로 줄이면 단계 밖의 크기가 된다). 두 단으로 바꾸는 높이는 항목 수마다 한 단으로 들어가는 가장 낮은 높이 바로 위로 잡는다. 그보다 낮게 잡으면 그 사이 높이에서는 어느 쪽으로도 들어가지 않는다. 두 값 비교의 막대 한 쌍이 좁으면(150px 밑) 발표할 때 앞 값 숫자를 빼고 뒤 값 숫자를 막대 한 쌍의 너비로 키운다(막대마다 숫자를 둘씩 달면 14px까지 작아졌다). 앞 값끼리, 뒤 값끼리는 가장 긴 숫자에 맞춘 한 크기다. 편집할 때는 앞 값도 고칠 수 있게 그대로 둔다. 줄이 쌓이는 부품(막대, 목차, 비교)은 줄 안에 위아래 여백을 두어, 낮은 칸에서도 숫자와 선이 붙지 않고 잰 높이도 그 여백까지 든다. 2×2 우선순위의 칸 줄도 글보다 낮게 눌리지 않고(`minmax(min-content, 1fr)`), 부품 안에서는 칸 위아래 여백이 칸 높이를 따라 40px에서 20px까지 준다. `minmax(0, 1fr)`이던 때는 낮은 칸(1096×388)에서 칸이 글보다 낮아져 설명이 칸 사이 줄과 아래 축에 걸쳤는데, 글이 칸 밖으로 나가지는 않아 맞추기도 높이 재기도 몰랐다. 기간별 달성의 막대 줄은 124px 밑으로 눌리지 않는다: 그래프 줄이 남는 높이뿐이면 글자 맞추기가 글자를 키운 만큼 막대가 눌려, 가장 긴 막대가 22px였다. 그래도 안 되는 자리는 편집기가 고르지 않는다.
- **면 안의 여백:** 옅은 면(위아래 선 사이), 진한 면, 레이아웃 안의 카드(비교의 두 면 같은)는 내용의 위 여백과 아래 여백이 같아 보여야 한다. 글자가 그려진 선(잉크)에서 면 끝까지를 재어 12px(넓은 여백이면 그 10%) 안이고, 어느 쪽도 16px보다 좁지 않다(`screens/comboChecks.ts`, `checkCombos`). 줄이 쌓이는 부품의 줄은 내용보다 낮게 눌리지 않는다(`minmax(min-content, …)`): 격자 줄을 `minmax(0, 1fr)`로 두면 낮은 칸에서 줄이 내용보다 낮아져, 글이 칸 밖으로는 나가지 않은 채 이름과 설명이 다음 줄의 선 위에 올라탔다. 하나 크게는 나머지 숫자를 줄로 쌓는 높이를 바탕마다 따로 잡는다(옅은 면, 진한 면은 위아래 안쪽 여백 88px만큼 더 높아야 쌓는다). 줄로 쌓는 너비는 큰 숫자를 위에 두는 너비와 같은 1300px까지다: 그 사이(4분의 3 칸)에서 나머지가 한 줄에 나란히 남으면 이름, 숫자, 설명이 세로로 쌓여 더 높아야 해서 글자가 줄었다. 쌓은 줄은 칸 가운데에 모아 두고 마지막 줄 아래 여백을 뺀다. 큰 숫자는 숫자 윗선 위의 빈 키를 잘라 낸다(`text-box`): 그 빈 키만 25px라 면의 위 여백이 아래보다 그만큼 넓어 보였다. 큰 숫자 부품은 위아래를 다 잘라(숫자 윗선과 바닥선) 어느 글꼴이든 숫자 글자가 상자 가운데에 선다: 명조 제목 글꼴은 숫자가 줄 상자 아래로 쏠려 면의 위 여백만 넓었다. 핵심 숫자를 줄로 쌓을 때 이름과 설명 옆 가운데에 두는 숫자도 같다. 나란한 카드의 위아래 여백과 이름, 숫자, 설명 사이는 낮은 칸에서 칸 높이를 따라 준다: 글자 맞추기(`fitBlocks.ts`)는 카드 안쪽 여백으로 내려간 글을 넘침으로 세지 않아, 좁은 카드에서 두 줄 설명이 카드 아래 여백까지 내려갔다. 판의 같은 띠를 나눠 쓰는 칸과 위아래로 쌓은 칸에서도 옅은 면, 진한 면의 내용은 면 가운데에 두고 내리기(`--bk-lift`)에서 뺀다: 면이 곧 묶음이라 옆 칸과 윗선을 맞추는 것보다 면 안의 위아래가 같은 것이 먼저다. 위에서부터 그리던 때는 내용이 짧은 면이 위 44~53px, 아래 90~110px로 아래만 비었다. 면 없는 부품끼리는 그대로 윗선을 맞춰 내린다. 나란히 선 같은 높이의 면(단계 흐름의 단계, 안 비교의 안)은 한 줄을 같이 쓰므로 내용이 가장 긴 면으로 잰다: 짧은 면은 그만큼 아래가 더 비는 것이 맞다(면마다 가운데에 두면 번호와 이름의 윗선이 면마다 어긋난다). 단계 흐름의 칸 모양은 부품 안에서 면이 칸 높이를 다 쓰고, 번호와 이름과 설명을 모든 단계가 같은 줄(subgrid)로 써서 묶음이 면 가운데에 선다(글을 위에 붙이던 때는 높은 칸에서 아래만 182px 비었다). 장에서 아래와 떼려고 둔 마지막 틈(가로 막대의 막대 줄 아래, 사실 목록의 마지막 줄 아래)은 면 위에서는 뺀다: 면의 아래 여백에 그대로 더해졌다. 핵심 포인트도 같다(세로 칸의 묶음 아래 틈, 줄 모양의 맨 아래 줄 선). 면 안의 내용은 넘칠 때도 가운데로 넘친다: 글자 맞추기는 글이 안쪽 여백에 8px까지 들어가도 들어간 것으로 보아, 아래로만 넘치면 아래 여백만 그만큼 좁았다. 줄 선이나 칸이 면 아래 끝까지 서는 부품(준비 상황, 강점과 약점, 시장 크기, 안 견주기, 숫자와 흐름, 늘고 준 것, 기간별 달성)은 맨 위 소제목의 빈 키를 잘라 낸다(`text-box`): 아래는 선이 면 여백에 바로 닿아 위만 그만큼 넓었다.
- **부품끼리의 위계:** 장 제목이 있으면 부품의 글은 제목과 다투지 않는다. 핵심 한 줄은 제목 아래의 답이라 한 단계 작게(44, 제목이 아주 길어 44로 줄면 36) 강조색으로 쓰고, 자리가 남아 모든 칸을 키울 때는 같이 키우되 장 제목의 한 단계 아래까지만(`--msg-cap`: 제목 62면 52, 52면 44). 키우지 않던 때는 좁은 칸에서 줄인 핵심 한 줄(37)이 같이 키운 옆 부품의 소제목(43)보다 작아졌다. 바탕 없는 강조 상자의 글도 44까지만. 인용은 남의 말이라 보통 굵기(500)에 버금 글자색, 장 제목이나 핵심 한 줄이 있으면 36이고(인용 하나가 곧 장의 말일 때만 44), 따옴표는 글 바로 위에 붙이고 말한 사람은 '—'를 앞에 둔 한 줄로 딸린다. 말한 사람 칸은 접어 두지 않는다. 예전에는 제목(52), 핵심 한 줄(52), 인용(44)이 모두 굵은 검정이라 한 장에 제목이 셋으로 읽혔다(예시 발표의 '사업 기회'에 핵심 한 줄과 인용을 더한 장). 장 제목이 없는 장(결론 한 장)에서는 핵심 한 줄이 곧 제목이라 그대로 52다.
- **글의 폭:** 문장을 쓰는 글 칸(핵심 한 줄, 제목과 글, 점 목록, 인용, 강조 상자, 주석, 예상 질문)은 한 줄이 글자 크기의 24배(`--measure`, 한글로 34자 남짓)에서 꺾인다. 칸이 넓어도 줄을 끝까지 늘이지 않고 남는 폭은 오른쪽에 모은다: 한 줄을 다 쓰는 칸에서 인용이 1630px, 다른 줄의 글은 1140px로 줄 길이가 들쭉날쭉했다. 한 줄을 다 쓰는 넓은 칸(1300px 넘게)의 제목과 글은 소제목을 왼쪽 반, 글을 오른쪽 반에 눕히고(글이 판의 가운데 선에서 시작해 위 줄의 반 칸 부품과 같은 선에 선다) 글자는 반 칸의 단계로 둔다. 제목처럼 짧은 글(핵심 한 줄, 인용, 질문과 답)은 줄 길이를 고르게(`text-wrap: balance`), 문단은 `pretty`로 끝 줄에 낱말 하나만 남지 않게 한다.
- **쌓기(사이는 관계로, 남는 높이는 한곳에):** 판은 늘 본문 상자를 빈틈없이 덮어서, 칸이 내용보다 높으면 그 차이가 칸마다 내용 위아래에 흩어져 부품 사이가 들쭉날쭉 벌어졌다(부제 아래 200px, 핵심 한 줄과 인용 사이 130px). 그래서 셋을 한다. ① 판: 위아래로 쌓은 가지에 차트도 면도 없으면 남는 높이를 맨 아래 자식이 다 받는다(`board.ts`의 `share`, pile). 편집 화면에서도 빈 칸은 아래에 모인다. 바탕 없는 글 부품은 혼자 한 줄을 써도 칸 가운데가 아니라 위에서부터 그린다. ② 발표 화면의 쌓기(`fitBlocks.ts`의 `pack`): 칸마다 그려진 범위(글 줄, 그림, 칠한 상자, 면이 있으면 면 전체, `drawn`)를 재어, 바로 위 칸의 그려진 아래에서 줄 사이(`--bk-gap`, 48)만큼 떼어 올려 붙인다(`--bk-shift`, 칸째 옮긴다). 소제목 아래는 그 아래 부품과 한 덩어리라 32, 아래 이음표가 선 사이는 이음표가 설 자리(양쪽 `--lk-pad`)만큼 넓히고 이음표를 그 가운데에 다시 세운다. 같은 줄 선에 서고 위에 있는 칸도 같은 칸들은 같이 옮겨 나란한 칸의 윗선이 그대로다. 장 제목이 없으면(결론 한 장) 모은 묶음째 위아래 가운데에 둔다. 편집 화면은 판의 칸과 선을 그대로 보여야 해서 옮기지 않는다. ③ 면 줄이기(`hug`): 면(옅은 면, 진한 면)은 남는 높이를 받아 한두 줄짜리 강조 상자가 700px 짙은 면이 되었다. 발표 화면에서는 그 줄의 다른 내용이 쓰는 높이까지, 그보다 짧으면 제 내용 높이까지 줄인다(`--bk-trim`). 나란한 면끼리는 같은 높이, 줄인 뒤 넘치면 그대로 둔다. 면은 판이 높이를 주어도 남는 높이를 받아 커지는 자리가 아니다: 사람이 짠 장처럼 면은 제 내용과 위아래가 같은 안쪽 여백만큼(나란한 칸이 더 길면 그 끝까지)이고, 남는 높이는 묶음 사이와 아래(②)로 간다. 그래서 면 안은 줄 사이를 넓혀(`--bk-air`) 채우지 않는다. 채우면 넓힌 내용이 곧 면 높이가 되어 다섯 줄 목록의 면이 본문 바닥까지 닿고, 옆의 두 줄짜리 결정 요청 면도 그 높이를 따라 글이 면 가운데에 떠 있었다. 이음표가 선 줄도 모두 면이면 줄인다(이음표는 줄인 면의 가운데로 옮긴다). 옆에 위아래로 쌓인 바탕 없는 칸이 ②로 올라가면 면의 아래 끝을 쌓은 뒤의 그 끝에 다시 맞춘다(`tail`). 키워서 이득인 것(차트, 표, 그림)만 칸 높이를 다 쓴다. 판의 자리(`at`)는 바꾸지 않으므로 판을 다 덮는 규칙과 저장 형식은 그대로다. 조합 시험(`checkCombos`)은 칸을 판의 자리로(올린 만큼 되돌려) 보고, 그려진 것끼리 겹치는지는 `checkAssembly`가 본다.
- **소제목 묶음:** 소제목 바로 다음에 넣는 부품은 그 소제목 아래에, 소제목 묶음(소제목과 그 아래 부품들) 다음에 넣는 소제목은 그 묶음 옆에 나란히 들어간다(`place.ts`의 `autoPlace`). 판이 알아서 고르면 둘째 소제목이 맨 아래 새 줄에 들어가 다음 부품이 그 아래에 들어갈 높이가 없어, 소제목만 맨 아래에 혼자 남았다.
- **AI:** 부품 장의 모양(부품의 해시 id, 종류, 너비, 모양, 바탕, 움직임, 나오는 때와 빠르기와 쪽, 나오는 차례, 칸이 찼는지)만 본다. 사람처럼 짜임을 바꾸자고 제안할 수 있다: 빈 부품 넣기(`add_block`), 옮기기(`move_block`, 글은 부품과 함께), 빈 부품 빼기(`remove_block`), 모양·바탕·움직임·나오는 때·빠르기·들어오는 쪽·항목 수·강조(`set_block`), 나오는 차례(`set_order`, 부품 해시 id만), 부품의 너비와 높이(`set_size`, 판의 칸 수), 이음표(`set_link`, 오른쪽 `right`과 아래 `below`, 모양 파일의 `link`와 `linkBelow`), 부품 칸의 안내 문구(`set_hint`의 `block`). 장을 부품 장으로 바꾸거나 되돌리는 것(`set_layout`)은 편집기와 같은 규칙(`asCompose`, `unwrapCompose`)이다. 모양 파일은 부품을 읽는 차례로 늘어놓고 부품마다 판의 자리(x, y, w, h)를 준다(`SHAPE_VERSION` 2, 판이 빈틈없이 덮이는지 `checkShape`가 본다). 넣거나 옮길 때는 기준 부품(`beside`)과 쪽(`side`: before, after, above, below), 또는 판의 끝(`edge`: top, bottom)을 준다. 옮기기는 자리 대신 다른 부품과 맞바꿀 수도 있다(`swap`). 예전 판(줄과 칸)의 요청(`REQUEST_VERSION` 1)은 받지 않는다. 놓을 자리와 높이는 편집기에서 끌어다 놓을 때와 같은 규칙(`whyNot`, 부품마다 잰 높이)으로 보고, 장에 들어가지 않으면 `no_room`으로 건너뛴다. 부품 안의 글은 쓰지 못한다. 부품이 있으면 빈 장이 아니라 지우지 않는다.

## 6. 디자인 시스템 (슬라이드)

**콘셉트: 조용한 본문, 분명한 시작, 지면의 말투.** 표지는 결정 요청 칸을 짙은 면으로 강하게. 단락 장과 마지막 장은 본문과 같은 바탕에 큰 번호와 큰 글씨로(색 면은 고르는 모양). 흰 장 사이에 짙은 장이 툭 끼면 장마다 무게가 달라 보인다. 본문 장은 흰 여백, 좌측 정렬, 큰 제목으로 조용하게.

**지면의 말투(괘선).** 잘 짠 연차 보고서나 잡지의 지면처럼, 묶음을 회색 면이 아니라 선과 글자로 보인다. 예전에는 컴포넌트마다 같은 둥근 회색 면, 굵은 파란 숫자, 강조색 점, 알약 꼬리표, 따옴표 그림이 서서 흔한 템플릿이나 AI가 만든 장처럼 보였다(사용자 의견, 2026-10). 시안 둘(괘선, 조용한 면)을 견줘 괘선을 골랐다.
- 머리 괘선: 바탕 없는 컴포넌트는 칸 밖 위(줄 사이 `--bk-gap`의 아래쪽, 칸 위에서 20px)에 글자색 선(`--rule-head`, 3) 하나로 시작한다(`styles/blocks/base.css`의 `.bk::before`, `--head-rule`). 칸 안에 그으면 그만큼 칸이 모자라 글자가 줄었다. 나란한 컴포넌트는 같은 높이의 선에서 시작해 판의 가로 선이 보이고, 선이 줄의 윗선이라 내용은 칸 위에서부터 둔다(차트 옆에서 가운데로 내리지 않는다). 표를 뺀 레이아웃 부품(차트, 핵심 숫자, 두 안 비교, 개요·요점 같은: 그림을 칸 가운데에 두는 것이 많아 선이 떴고, 발표 화면의 쌓기가 그림을 앞 줄 아래로 올리면 칸 위의 선이 앞 줄의 글을 그었다. 제 축과 첫 줄 선을 쓴다), 제 선이 있는 것(소제목, 소제목 없는 줄 컴포넌트, 강점과 약점)과 이미지, 주석, 이음표로 이은 줄, 제목 없는 장의 맨 윗줄은 긋지 않는다. 핵심 한 줄은 짧은 강조색 선(64px), 바탕 없는 강조 상자는 강조색 선. 표는 위 굵은 선, 머리줄 선, 줄 선의 꼴. 발표할 때 선은 왼쪽에서 그어지고 글이 그 아래로 들어온다. 편집 화면의 테두리는 선까지 두른다.
- 면: 옅은 면(card)은 칠하지 않고 위 머리 괘선과 아래 줄 선 사이에 묶는다(안쪽 여백은 그대로라 글 폭과 높이가 같다). 레이아웃의 카드, 타일, 격자(핵심 숫자, 요점, 단계 흐름, 한 장 요약)도 같은 꼴이다. 진한 면만 면으로 남기되 모서리는 각지게. 면과 막대, 띠, 마디의 모서리는 0(`--r-panel`, `--r-mark`).
- 숫자: 큰 숫자는 굵게 칠하지 않고 보통 굵기 안팎의 글자색(`--num-weight`: 프리텐다드·SUIT 400, 함렛 500, 본명조 600. 300은 프로젝터와 뒷자리에서 획이 약했다). 답이라는 위계는 크기로. 단위는 옅은 글자색.
- 이름표: 컴포넌트 맨 위의 작은 이름은 22px(`--t-label`, 컴포넌트 장), 600, 자간 0.06em. 넓은 칸에서도 이름을 키우지 않는다: 키운 장에서 52~62px 굵은 글이 되어 장 제목과 다퉜다.
- 강조색은 답에만: 바뀐 만큼, 고른 항목(is-hl), 지금 단계, 우리 쪽, 핵심 한 줄의 짧은 선, 강조 상자의 선과 이름표. 늘 강조색이던 큰 숫자, 핵심 한 줄의 글, 점 목록의 점은 글자색으로 바꿨다.
- 꼴: 점 목록은 01, 02 차례 숫자(같은 폭, 옅은 글자색)와 항목 사이 옅은 줄 선(사이의 반은 선 위, 반은 아래라 높이는 그대로, 두 단으로 흘리면 선 없이). 인용은 여는 따옴표를 글 밖으로 내단다(걸린 문장부호). 알약 꼬리표(바뀐 만큼, 늘고 준 비율, 상태, 달성률)는 색 글자만.

테마 2종: 바탕은 흰색 아니면 검은색. 크림색처럼 색이 있는 바탕은 낡고 무거워 보여서 쓰지 않는다. 강조색은 고르거나 브랜드 색으로 직접 고를 수 있다. 흰 테마의 짙은 면은 검정이 아니라 강조색을 깊게 가라앉힌 색이다(코발트면 짙은 남색). 새까만 면은 흰 장 사이에서 너무 세고, 아무 색도 없는 표지는 밋밋하다. 흰 바탕, 짙은 남색 면, 강조색 하나는 보고 자료에서 오래 쓰인 짝이다.

| 테마 | 배경 | 글자 | 강조 | 짙은 면 | 제목 서체 |
|---|---|---|---|---|---|
| 화이트 | #FFFFFF | #16171A | #2F55D4 (코발트) | 강조색과 #0A0D16을 반씩 (코발트면 #1D3175) | Pretendard 700 |
| 블랙 (id `navy`) | #000000 | #F4F4F5 | #6B93FF (하늘) | #222327 (한 단계 뜬 검정) | Pretendard 700 |

- 예전의 세리프 테마(id `serif`)는 고르는 목록에서 뺐다. 열면 화이트에 명조 제목(`font: 'serif'`)으로 바꾼다(`plainTheme`). id는 예전 버전과 주고받는 파일 때문에 그대로 둔다.

**색.** 공개된 색 체계의 원칙을 따라 우리 값으로 골랐다(값을 옮겨 오지 않았다).

- 역할을 나눈다: 강조색은 '답'(바뀐 만큼, 고른 막대와 항목, 지금 단계)에만(큰 숫자는 크기로 답이 되므로 글자색), 넓은 면(표지 옆면, 진한 면 부품, 추천안, 색 면 단락 장)은 짙은 면(`--bold-bg`, `themes.ts`의 `deepOf`), 그 위의 강조는 강조색을 밝힌 색(`--bold-accent`, 7:1). 흰 테마의 짙은 면은 강조색 30%를 밤색에 섞은 먹에 가까운 색이다: 반쯤 섞던 때는 면이 쨍한 남색이라 넓은 면이 흔한 파란 상자로 보였고, 그 위의 강조(4.5:1)가 흰 이름표보다 흐려 답이 가라앉았다. 강조는 흰색을 섞지 않고 색상과 채도를 둔 채 밝기만 올린다(흰색을 섞으면 회보라, 회분홍으로 바랜다). 짙은 면 위 글은 흰 글 11.5:1, 옅은 글(`--ink-3`) 5:1, 바뀐 만큼 칩 4.5:1을 넘긴다(`themes.test.ts`). 검은 테마에서 장 전체를 덮는 짙은 면(단락 장, 마지막 장, 색 면 표지)은 바탕과 같은 검정이고, 옆면, 카드처럼 일부만 덮는 면만 한 단계 뜬 검정이다.
- 맥락은 회색, 말하려는 한 곳만 색 (Datawrapper의 차트 색 안내). 작년, 다른 조각, 뺀 요인은 회색 단계.
- 회색은 색을 섞지 않은 중립 회색이다. 강조색을 바꿔도 회색이 따로 놀지 않는다.
- 가장 옅은 글자(`--ink-3`: 단위, 출처, 머리말)도 바탕에서 4.5:1, 카드 면(`--surface`)에서 4:1을 넘긴다. 22px 글자가 프로젝터에서 바래면 3:1로는 읽히지 않는다. 검은 테마의 짙은 면은 카드 면(#141517)보다 한 단계 더 떠서, 카드 모양과 짙은 면 모양이 같은 색으로 보이지 않게 한다.
- 강조색(`ACCENT_COMBOS`) 9개(코발트, 하늘, 청록, 숲, 남보라, 자두, 벽돌, 황토, 먹). 두 바탕과 장의 바탕 셋에서 맞춰 보고 골랐다.
- 강조색은 바탕에서 읽히게 저절로 밝히거나 어둡게 한다: 흰 바탕은 3:1, 검은 바탕은 4.5:1(짙은 색은 검정 위에서 3:1을 넘겨도 가라앉아 흐려 보인다).
- 검은 바탕의 로고 모음은 밝은 판을 깔지 않고 로고를 흑백으로 뒤집어 밝게 한다(`invert` + `screen`). 표지, 사례의 회사 로고 하나는 색을 살려 밝은 판 위에.
- 섞을 때는 sRGB. oklch로 섞으면 색상이 먼 둘 사이에서 주황으로, 회녹색이 분홍으로 틀어진다.

- 서체: 기본은 모두 Pretendard. 테마 메뉴의 '글꼴'에서 맞춰 본 짝 넷 가운데 하나를 고른다(`themes.ts`의 `FONTS`): 프리텐다드(제목과 본문), SUIT(제목과 본문), 명조 제목(Hahmlet 제목 + Pretendard 본문), 본명조 제목(Noto Serif KR 제목 + Pretendard 본문). 모두 SIL OFL 1.1이고 앱과 내보낸 파일에 들어 있어 윈도우에서도 같다. `word-break: keep-all`, 제목 `text-wrap: balance`, 큰 제목은 자간을 좁게.
  - 제목과 본문을 따로 고르게 하지 않는다. 비슷한 고딕 둘을 섞으면 어긋나 보이고, 본문까지 명조면 회의실 화면에서 읽기 어렵다. 짝으로만 고르면 어느 것을 골라도 보기 좋다.
  - 명조는 제목(과 큰 숫자)에만 쓴다. 본문은 획이 고른 고딕이 화면에서 잘 읽힌다.
  - 글꼴마다 굵기의 느낌이 다르다. 장의 굵기(본문 400, 이름표 600, 제목 700)는 Pretendard에 맞춰 정했고, SUIT는 같은 굵기에서 한 단계 가늘어서 굵기마다 한 단계 굵은 파일을 잇는다(`src/fonts/suit.css`).
  - 고른 글꼴에 없는 글자는 Pretendard로 그린다(글꼴 목록 끝에 늘 Pretendard). SUIT에는 자주 쓰는 한글 2,350자 남짓만 있다.
  - 글꼴마다 다른 값(글꼴 높이와 한글 윗선 `box`, `gap`, 숫자 폭 `glyph`, 큰 숫자 줄 높이 `tall`)은 `FONT_LOOK`에 캔버스로 잰 값으로 둔다. 단락 번호의 끝자리 숫자 옆 빈칸은 `styles/section.css`의 `.f-<글꼴> .sc-num`. 새 글꼴을 더하면 갤러리 `&font=<id>`로 `checkFrame()`, `checkCombos()`를 보고, 부품 높이 표를 그 글꼴로도 재어 높은 쪽을 쓴다(`blockHeights.ts`).
- 타입 스케일(1920 기준): 한 비율(1.2)의 단계 22 · 26 · 30 · 36 · 44 · 52 · 62 · 74 · 90 · 108 · 128 · 154 · 184 · 220 · 264에서만 고른다. 장 제목 62(31pt), 부제 36, 칸 제목 36, 본문 30(15pt), 보조 26, 출처 22. 표지와 한 문장 메시지 90, 큰 숫자 108~264. 단계 밖의 크기를 섞으면 비슷한 글끼리 몇 px씩 달라 위계가 흐려진다. 예전에는 40가지 넘는 크기를 썼고 제목 72, 본문 34로 보고 자료치고 커서 장이 꽉 차 보였다. 22는 회의실 뒷자리에서 읽히는 바닥이라 작은 글은 거의 줄이지 않고 큰 글을 더 줄였다. 보내는 자료(`d-read`)는 한 단계씩 작게(제목 52, 본문 26).
- 틀: 모든 장은 같은 틀 안에 그린다. 좌우 120(`--pad-x`), 위아래 72(`--pad-y`)로 왼쪽과 오른쪽, 위와 아래가 각각 같다. 제목(과 부제) 아래에서 본문 상자까지는 72(`--body-gap`)로 레이아웃 장과 부품 장이 같아서, 장을 넘겨도 본문 윗선이 움직이지 않는다. 줄 선은 한 굵기(`--rule`, 2)라 레이아웃 부품과 다른 부품을 한 장에 놓아도 선이 섞이지 않는다. 위아래는 글자가 실제로 그려진 선으로 맞춘다: 위는 제목 글자의 윗선, 아래는 아래 띠(출처와 하단 표시 한 줄)의 글자 아랫선이 틀선에 닿는다. 줄 높이의 빈 위아래까지 상자로 맞추면 큰 제목이 있는 위는 넓고 작은 하단 표시가 있는 아래는 좁아 보인다(예전에는 위 111, 아래 35로 보였다). 글꼴마다 글자 위 빈칸이 달라서 테마가 글꼴 높이와 한글 윗선의 자리(`--head-box`, `--head-gap`, `themes.ts`)를 넘기고, 틀선에 닿는 글(제목, 표지의 결정 요청과 발표자, 마지막 장의 제목과 연락처, 단락 목록)은 그만큼 당긴다. 단락 번호처럼 큰 숫자는 숫자마다 글자 옆 빈칸이 달라 끝자리 숫자마다 당긴다. 장 끝까지 깐 바탕과 옆면(표지의 결정 요청 면, 사례의 결과 면, 그림 면)은 틀이 아니지만, 그 안의 글과 그림은 틀 안에 있다. 하단 표시는 단락 지도가 없는 장(요약, 순서)에서도 같은 자리에 있어서, 넘길 때 아래 줄이 움직이지 않는다. 아래 띠는 한 줄이다: 왼쪽에 숫자 장의 출처·기준, 오른쪽에 단락 지도(지금 단락은 글자색과 굵기)와 쪽 번호. 본문 상자와는 제목 아래와 같은 72(`--body-gap`)라 본문 상자의 위아래가 같은 꼴로 떨어진다. 예전에는 출처를 단락 지도 바로 위에 얹고 지금 단락 아래에 강조색 밑줄을 그어서, 왼쪽 아래에 작은 회색 글 두 줄이 쌓이고 화면의 탭처럼 보였다(본문과는 38뿐이었다). 코드에서 본문 상자를 어림할 때는 `deck/frame.ts`(CSS와 같은지 `frame.test.ts`가 본다). 틀을 벗어난 장이 없는지는 갤러리 콘솔의 `checkFrame()`으로 잰다(글자와 그림이 그려진 선으로).
- 본문 장 아래 띠의 오른쪽에 섹션 이름과 쪽 번호, 왼쪽에 출처. 장을 넘길 때 오른쪽은 제자리에 있고 출처는 장과 함께 넘어간다.
- 면(패널)과 차트 표시의 모서리는 0(`--r-panel`, `--r-mark`). 칠한 면은 진한 면에만 쓰고, 기본은 괘선과 줄과 여백으로 나눈다(위 '지면의 말투').

**숫자의 꼴.** 공개된 조판과 데이터 시각화 안내(시카고 매뉴얼의 빼기 기호 문답, Butterick의 Practical Typography, 세계은행 데이터 시각화 스타일 안내, 대시보드 디자인 시스템의 '큰 값 작은 단위' 패턴)의 원칙을 따라 정했다(글을 옮겨 오지 않았다). 모두 그릴 때만 바꾸고 저장한 글은 그대로다(`slides/fields.tsx`의 `Shown`, `paint`).

- 나란한 숫자는 한 크기: 핵심 숫자처럼 같은 줄에 놓인 숫자는 가장 긴 값에 맞춘 크기 하나를 같이 쓴다(`useSharedUnits`). 칸마다 따로 맞추면 '40%'는 크고 '1,200시간'은 작아져 숫자의 크기가 값의 크기처럼 읽힌다. 칸의 너비도 모두 같아야 해서, 칸 사이 나누는 줄은 칸 안쪽 여백이 아니라 칸 사이 틈 가운데에 그린다. '하나 크게'의 첫 숫자만 따로 크다. 컴포넌트 '전과 후'도 전과 후를 같은 크기로 두고 전은 옅게, 후는 글자색으로 가르고, 바뀐 만큼만 강조색 글자다. 바뀐 만큼(▼ 2.1%p)은 결과인 후 바로 아래에 붙는다. 칸이 좁아 숫자가 줄어들 때도 전과 후는 같은 폭의 칸에서 같이 줄고, 화살표는 줄어든 숫자 크기를 따라 숫자 글자의 가운데에 선다(줄이기 전 크기를 따르던 때는 화살표만 커서 숫자 위에 떴다).
- 숫자와 단위: 큰 숫자(핵심 숫자, 사례의 성과, 안 비교의 비용)는 뒤의 단위('%', '시간', '억 원')를 두 단계(1/1.44) 작게, 같은 바탕선에 둔다(`.slide .u`, `UNIT_K`). 한글 단위는 숫자만큼 넓고 무거워서 같은 크기면 답보다 단위가 먼저 읽힌다. 숫자 하나와 짧은 단위의 꼴('3.6시간', '−3%', '2~3배')만 나누고, '3년 6개월'처럼 그 꼴이 아니면 그대로 그린다. 숫자 앞에 띄어 쓴 세 글자까지의 덧말('약 30억 원', '하루 10분', '월 1.2억 원')도 단위와 같은 작은 글자로 뗀다. 덧말을 숫자 크기로 두면 나란한 '80%' 옆에서 '하루 10분'만 글자가 두 배로 무거워 보였다. 편집할 때도 같은 꼴로 보이지만 칸의 글자는 하나도 바뀌지 않는다.
- 빼기 기호: 숫자 앞의 붙임표(-)와 줄표(–)는 빼기 기호(−, U+2212)로 그린다. 붙임표는 소문자 높이에 맞춘 짧은 선이라 숫자 옆에서 낮고 짧다. 날짜('2026-10-25'), 번호('A-1'), 범위('3-4월')의 붙임표는 그대로다(`minusSigns`).
- 숫자 폭: 혼자 크게 서는 숫자(핵심 숫자, 사례 성과, 비용)는 비례폭 숫자로 글자 사이를 고르게, 위아래로 쌓여 자리를 맞춰 읽는 숫자(표, 지표표, 막대 값, 비중, 진행률, 일정의 시기)는 고정폭 숫자(`tabular-nums`)로.

**계산할 때의 숫자 읽기.** 값 둘 이상으로 계산하는 곳(전과 후의 바뀐 만큼, 목표 대비 실적과 목표 대비의 달성률, 몇 중 몇, 증감 요인의 끝 값, 구성비의 비중과 합계, 깔때기 전환율, 두 값 비교의 차이, 기간별 달성, 원인 순위, 쌓은 막대, 색 표, 지표 흐름표)은 모두 `slides/numbers.ts`의 해석기(`readAmount`, `amountPair`, `changeOf`, `seriesIn`)로 읽는다. 예전에는 글에서 숫자만 뽑아서 '6분 → 40초'가 ▲ 567%로, '1.2억 원 → 8,000만 원'이 크게 는 것으로 나왔다. 틀린 숫자는 듣는 사람이 그대로 믿는다.

- 큰 수의 자리(조, 억, 만, 천, '3천만', '1억 2,000만 원')와 시간(초, 분, 시간, 일, 주, 개월, 년, '1시간 30분'), 무게, 길이, 용량은 같은 바탕 값으로 바꿔 견준다. '이상', '이내', '정도' 같은 덧말은 떼고 읽는다.
- 견줄 수 없는 두 값('3건 → 40%', '2명 → 5대', '6분 → 40')은 계산한 숫자와 화살표를 보이지 않는다. 틀린 것을 보여 주느니 안 보여 주는 게 낫다. 단위가 %인 두 값의 차이는 %p로 적는다.
- 한 그림의 값은 보통 같은 단위로 적고 몇 개에만 단위를 붙인다. 그래서 숫자만 적은 값은 단위를 적은 값이나 단위 칸의 단위로 읽는다('117억, +9, −2'). 서로 다른 단위 무리가 섞이면 막대는 적은 숫자대로 그리되 계산한 숫자(달성률, 전환율, 합계, 끝 값)는 보이지 않는다.
- 숫자가 둘 이상인 글('3~5일', '2024년 120억')은 값으로 읽지 않는다. 진행률, 비율 원, 위치 비교의 점수처럼 칸 하나로 그리는 값은 단위와 상관없이 적은 숫자 그대로다.

**나란한 칸은 한 틀, 본문은 끝까지.** 칸이 나란한 레이아웃(핵심 숫자, 단계 흐름, 일정, 세로 칸 요점)은 이름, 숫자, 설명 줄을 모든 칸이 같이 쓴다(CSS subgrid). 한 칸의 이름이 두 줄이 되어도 옆 칸의 설명이 따라 내려가 줄이 맞는다. 장 한 장을 다 쓸 때는 작은 띠가 본문 가운데에 뜨지 않게 짠다.

- 단계 흐름: 단계는 같은 너비의 칸이고, 위의 선은 칸 왼쪽 끝에서 글의 틈 앞까지 긋는다(선 사이의 틈이 단계 사이). 선 줄은 본문 윗선에, 담당과 시간은 칸마다 선을 하나 두고 본문 아래 끝 줄에 둔다. 설명은 이름 바로 아래 한 덩이. 담당과 시간이 하나도 없으면 띠를 가운데에 둔다. 칸 모양은 칸을 본문 높이만큼 세운다. 단계 수(3, 4, 5–6)마다 글자를 한 단계씩.
- 핵심 숫자: 나누는 줄은 본문 위아래 끝까지, 이름과 숫자와 설명은 칸 안의 눈높이(가운데보다 조금 위)에.
- 일정(가로)과 세로 칸 요점: 내용이 적어도 띠가 낮지 않게 글자를 한 단계씩 키운다(일정은 시기를 가장 크게).
- 핵심 포인트: 장 한 장에 포인트가 서넛뿐이면 이름과 설명을 한 단계씩 키운다(줄마다 높이의 반 넘게 비어 글이 작아 보였다). 타일은 이름을 면의 위에 크게, 설명을 면의 아래 끝에 둔다(포스터처럼). 이름이 작으면 면 가운데가 비어 빈 상자처럼 보였고, 한 면 안이라 둘이 떨어져 있어도 한 덩이로 읽힌다. 보내는 자료는 한 단계 작게.
- 단락 번호: 두 모양 모두 오른쪽 아래에 아주 크게(600px), 획은 가늘게(200) 둔다. 바탕 모양은 옅은 글자색(`--ink-3`, 반복 표시라 강조색이 아니다), 색 면은 밝힌 강조색. 굵은 강조색 번호를 제목 위에 얹은 꼴은 흔한 단락 장 서식처럼 보였다. 숫자의 오른쪽 끝을 틀선에 맞추는 빈칸 값은 굵기 200에서 다시 쟀다(SUIT는 400부터라 400).
- 마지막 장의 요청 번호: 요청 제목과 같은 크기, 같은 글자선에 가늘고 옅게(`--ink-3`) 왼쪽에 둔다. 강조색 동그라미에 넣은 번호는 흔한 서식처럼 보였다. 요청은 제목과 설명 두 줄이라 번호를 앞에 둔다(한 줄짜리 목차는 오른쪽 끝).
- 목차: 항목 몇 개뿐인 장이라 글이 곧 장의 그림이다. 목록은 줄이 본문 높이를 고르게 나눠 채우고, 이름은 항목 수(2–3, 4, 5, 6)마다 한 단계씩 크게(90–52px) 왼쪽에, 번호는 같은 크기로 가늘고 옅게(글자색 `--ink-3`) 줄 오른쪽 끝에 둔다. 번호를 이름 앞에 작은 강조색으로 두면 흔한 서식 목록으로 보였고, 이름만 왼쪽에 있으면 줄 오른쪽이 비었다. 나란히는 제목을 단락 장처럼 크게(108px) 두고, 칸마다 위에 굵은 선을 그은 띠(번호, 이름)를 본문 바닥에 앉힌다. 띠를 가운데에 두면 짧은 이름 몇 개가 낮게 떠 보였다. 발표할 때는 선을 왼쪽부터 긋고(나란히는 칸마다 이어서) 이름이 올라온 뒤 번호가 뜬다. 부품 칸의 나란히는 좁은 칸에서 다섯, 여섯이면 셋씩 두 줄로, 좁고 높으면 목록처럼 줄로 쌓는다.
- 이 짜임은 `.l-<레이아웃>` 규칙에만 있다. 부품 장의 레이아웃 부품은 기본 규칙을 그대로 써서 잰 높이 표(`blockHeights.ts`)가 바뀌지 않는다.

**사용자가 고르는 것.** 글상자를 끌어 옮기는 대신, 아래를 고르면 시스템이 배치한다. AI도 같은 선택지 안에서만 제안한다.

| 어디서 | 고르는 것 |
|---|---|
| 테마 메뉴 (발표 전체) | 테마(화이트/블랙), 강조색(또는 직접), 글꼴(프리텐다드/SUIT/명조 제목/본명조 제목), 글자 크기(작게/보통/크게: 크게는 글자 크기 단계를 하나 올린 1.2배), 아래 표시(섹션만/섹션과 쪽 번호/쪽 번호만/숨기기), 움직임, 장 넘기기 |
| 이 장 설정 (장마다) | 레이아웃, 모양, 강조할 항목, 바탕(바탕/반대 색/강조색), 이 장의 움직임, 두 판으로 나뉜 장이면 옆 판의 자리(왼쪽/오른쪽)와 너비 |
| 장 위에서 끌기 | 항목의 순서(손잡이), 옆 판의 자리와 너비(판의 이름표, 판 사이), 부품 장의 부품(5-1) |

- 바탕 '반대 색'은 밝은 테마에서 어둡게, 어두운 테마에서 밝게 바꾼다. 강조색은 그 바탕에서 읽히도록(3:1 이상) 저절로 밝히거나 어둡게 한다.
- 표지, 섹션, 결정 요청은 모양(표지: 옆 면/아래 띠/색 면, 섹션과 결정 요청: 바탕/색 면)으로 면을 고르므로 장의 바탕은 바꾸지 않는다.
- 색 면(`--bold-bg`)은 쨍한 강조색이 아니라 강조색을 깊게 한 색이다(위 '색'). 쨍한 강조색은 차트의 강조 막대, 점, '추천' 글자처럼 작은 곳에만 쓴다. 안 비교의 추천안, 단계 흐름의 강조 단계, 진한 면 부품처럼 넓은 면도 짙은 면으로 칠한다(검은 테마는 한 단계 뜬 검정에 강조색 테두리).
- 번호는 실제 순서가 있는 곳(목차, 일정, 섹션, 다음 단계)에만 쓴다.

**장 모음 (`#/system`).** 디자인 시스템을 한 화면에서 본다. 색 견본(짙은 면처럼 섞어 만든 색도 실제 장과 같은 조건에서 읽는다), 글자 크기, 장의 바탕 세 가지, 그리고 모든 레이아웃의 모든 모양을 쓰임 묶음(`LAYOUT_GROUPS`)대로 늘어놓는다. 테마, 강조색, 예시 내용/빈 칸을 바꾸면 모두 함께 바뀐다. 홈의 '장 모음 보기'와 장 추가의 '장 모음 보기'(새 탭)에서 연다. 예시 내용은 `src/deck/showcase.ts`의 지어낸 값이고, 저장된 발표는 읽지 않는다. 새 레이아웃을 넣으면 묶음 하나에 넣고 예시 장을 채운다(테스트가 확인한다).

## 7. 편집기 UX

```
┌───────────────────────────────────────────────────────────────────────┐
│ ‹ [발표 제목]   저장됨                         AI  테마  내보내기  [발표하기] │
├──────────┬───────────────────────────────────────────┬────────────────┤
│ 1 표지    │     [⠿ 숫자 2 | ‹ › | ★강조 | ⧉ 🗑]          │설정 | 움직임 | 컴포넌트│
│ 2 핵심요약 │   ┌─────────────────────────────────┐   │ [그림] 레이아웃    │
│ 3 …      │   │  슬라이드 (바로 눌러서 입력)        │   │        바꾸기 ›  │
│          │   └─────────────────────────────────┘   │ ● 빈칸 3곳 다음 빈칸│
│ + 장 추가 │  [AI로 다듬기][모양][+항목]  [미리 보기][▶][⧉][숨김][🗑] │ 모양 / 꾸미기     │
│          │  발표자 노트                                │                │
└──────────┴───────────────────────────────────────────┴────────────────┘
```

- **앱 화면의 디자인 시스템:** 슬라이드의 디자인 시스템(6장, `#/system`)과 따로, 편집 도구 화면은 조용한 회색 바탕에 선택만 파란색(`--sel`)을 쓴다. 값은 `src/styles/base.css` 맨 위의 변수(`--app-bg`, `--panel`, `--line`, `--ink`~`--ink-3`, `--sel`, `--sel-soft`, 마우스를 올린 것의 `--hover`/`--hover-2`, 누르는 동안의 `--press`, 빈칸 점의 `--blank`, `--r-sm`/`--r`/`--r-lg`, `--shadow-pop`)만 쓴다(앱 화면의 CSS는 `app.css`가 `src/styles/`의 화면별 파일을 정한 차례로 가져온다). 부품은 같은 것을 같은 모양으로: 단추(`.btn`, `.btn-ghost`, `.btn-sm`, 그림만 있는 `.icon-btn`), 고르기(`.seg`, 칸을 다 쓰면 `.seg-fill`. 고르는 단추는 줄을 바꾸지 않는다), 말풍선(모든 `title`, `screens/tooltip.ts`), 접어 둔 설명((i) `Info`), 팝오버(`Popover`), 켜고 끄기(`Toggle`). 화면의 움직임은 한 Framo로: 곡선은 끝에서 천천히 멈추는 `--ease-out` 하나(넘쳤다 돌아오는 튕김, 크기를 키우며 튀어나오는 것은 쓰지 않는다), 색이 바뀌는 것은 `--t-fast`, 창이 열리거나 자리를 옮기는 것은 `--t`. 메뉴와 팝오버는 연 단추 쪽에서 4px 미끄러지며 옅게 나타나고, 알림은 아래에서 떠오르고, 오른쪽 칸의 탭은 밑줄이 번지며 내용이 옅게 바뀐다. 움직임을 줄이기로 한 사용자에게는 움직이지 않는다. 그림으로 고르는 것(장 목록, 레이아웃, 모양, 테마)은 올리면 테가 한 단계 짙고, 고르면 파란 테, 키보드로 오면 그림 둘레에 초점 테다. AI 단추는 이웃 단추와 같은 모양에 말풍선 그림(안에 Framo의 물결 한 줄)이고, 공유 중인 것은 점 하나로만 알린다(반짝이 그림과 파란 면은 흔한 AI 제품처럼 혼자 들떠 보였다). 설명 글은 화면에 늘어놓지 않는다: 필요한 설명은 (i)나 말풍선에, 그림만 있는 단추는 `title`에 하는 일을 적는다(끝에 괄호로 단축키를 붙이면 옅게 따로 보인다).
- **이 장 설정(오른쪽 칸):** 늘 보는 것만 한 화면에 둔다. 지금 레이아웃(그림, 이름, '바꾸기'), 빈칸 줄('빈칸 N곳', '다음 빈칸'을 누를 때마다 빈 칸으로 차례로, 목록은 펼쳐야), 모양(그 레이아웃의 모양 그림, 강조할 항목, 옆 판의 자리와 너비), 꾸미기(바탕). 레이아웃 목록은 '바꾸기'를 눌러야 따로 열리고(돌아가기 줄, Esc), 그림에 마우스를 올리면 슬라이드 자리에 그 레이아웃으로 미리 보인다(누르면 바뀐다). 장마다 무엇을 쓰면 되는지(`slide.guide`)는 왼쪽 목록의 장 이름 말풍선에 둔다.
- **움직임(오른쪽 칸의 둘째 탭, `editor/MotionPanel.tsx`):** 이 장의 미리 보기, 움직임 정도, 장 넘기기(이어 움직이기 포함), 그리고 부품 장이면 나오는 차례. 차례 목록은 '장이 나올 때', 'N번 누르면'으로 묶어 보이고, 끌어서 차례를 바꾼다. 줄을 누르면 장 위에서도 그 컴포넌트가 골라지고(장 위에서 고르면 목록의 그 줄이 펼쳐진다), 움직임, 언제, 들어오는 쪽, 빠르기를 고르면 그 컴포넌트만 바로 한 번 움직여 보인다. 시간을 손으로 그리는 막대는 두지 않는다: 비개발자가 밀리초를 맞추게 하지 않고, 고른 값으로 엔진이 시간을 정한다([MOTION.md](MOTION.md)). 맨 위의 '움직임 편집'는 같은 값을 크게 보며 고치는 화면이다: 장을 발표 화면처럼 움직이고, 아래 시간표에서 컴포넌트마다 움직이는 동안을 막대로 보이며, 바늘을 끌어 아무 때의 모습이나 본다(막대는 보기만, 차례는 줄을 끌어서). 오른쪽에는 연출(차례로, 한꺼번에, 누를 때마다, 결론 먼저, 결론은 마지막에)과 고른 컴포넌트의 언제, 움직임(작은 그림이 되풀이된다), 쪽, 빠르기, 그리고 이 장의 움직임 정도와 장 넘기기. 편집기 위에 덮는 대화 창이라 Esc로 닫고, 그동안 편집기 단축키는 쉬고 되돌리기만 받는다. 1280×600에서는 시간표를 줄여 장을 지킨다.
- **장 위에서 고른 것의 도구 (`editor/SelectionBar.tsx`):** 레이아웃 장에서 칸을 누르면(키보드로 들어가도) 그 칸이 든 항목이나 옆 판을 파란 테로 두르고 바로 위에(위에 자리가 없으면 안쪽 위에) 도구 막대를 띄운다. 항목: 이름(끌면 순서 바꾸기), 앞뒤로(가로 목록은 왼쪽·오른쪽, 세로 목록은 위·아래), 강조(레이아웃에 강조가 있으면), 복제, 빼기. 옆 판: 이름(끌면 옮기기, 판의 이름표에 넘긴다), 반대쪽으로, 아래로(표지), 좁게·넓게. 제목 덩어리(표지, 섹션의 제목과 부제, `LayoutSpec.place`): 이름을 잡고 위아래로 끌면 덩어리가 놓이는 칸 위에 세 자리(위, 가운데, 아래)가 보이고 손이 있는 자리로 바로 옮겨 가 놓으면 붙는다(`options.place`, Esc는 처음 자리로, 한 번 끈 것은 되돌리기 한 단계). 위·가운데·아래 단추로도 고른다. 표지에서 제목을 위로 올리면 로고는 아래로 비켜 주고, 색 면 섹션은 큰 번호를 아래에 둔 채 제목만 올린다. 글상자를 아무 데나 놓게 하지 않고 세 자리에만 붙이는 것은 줄과 여백, 글자 윗선·아랫선이 틀에 맞게 하려고다. 그 밖의 칸: 무슨 칸인지와 '모양'. 막대가 떠 있으면 항목 모서리의 손잡이와 빼기, 판의 이름표는 숨긴다(같은 일이 두 번 보이지 않게). 부품 장의 부품은 부품마다 자기 도구(이름표와 아래 도구 줄)가 있다.
- **슬라이드 아래 단추:** 'AI로 다듬기'(고르는 부탁), '모양'(그 레이아웃의 모양을 그림으로 보고 고르기. 예전의 '다른 모양'은 누를 때마다 다음 모양으로 넘어가 무엇이 나올지 몰랐다), 항목 추가 / 미리 보기, 지금 장부터 발표, 복제, 발표에서 빼기, 지우기. 자리가 모자라면 오른쪽부터 글자를 숨기고 그림만 남긴다(이름은 말풍선으로).
- **슬라이드 모드:** 슬라이드 위 글자를 바로 클릭해서 고친다. 빈칸에는 회색 안내 문구와 옅은 면이 보이고, 쓰는 중에는 면 대신 파란 실선 하나(`.ed-halo`, 점선 상자는 쓰지 않는다). 면은 글보다 조금 넓게 깔되 이웃한 칸, 항목, 부품 칸 끝을 넘지 않는다(`slides/halos.ts`). 서식은 없다(붙여넣기도 글자만).
- **문서 모드:** 모든 장의 칸을 문서처럼 한 화면에서 이어서 쓴다. 옆의 작은 슬라이드가 실시간으로 바뀐다. 많이 채울 때 빠르다.
- **장 추가(`screens/editor/AddSlide.tsx`):** 레이아웃을 그림으로 고른다. 왼쪽에 묶음(자주 쓰는 장, 결론과 메시지, 숫자와 차트, 진행과 계획, 비교와 선택, 자료와 사례, 시작과 끝), 오른쪽에 그 묶음의 장이 예시 내용을 채운 그림 세 줄로 보인다. 처음에는 자주 쓰는 아홉 가지(컴포넌트로 꾸미기가 맨 앞)만 보이고, 설명은 그림에 마우스를 올리면 나온다. 예전에는 스물일곱 가지의 이름과 설명을 한 줄씩 늘어놓은 긴 목록이라, 어떻게 생긴 장인지 모르고 글만 읽으며 스크롤해야 했다.
- **빈칸 확인:** 장마다 빈칸 표시. 발표 전에 빈칸이 남았으면 알려준다. 그대로 발표하면 칸을 하나도 채우지 않은 항목은 발표 모습(발표, 미리 보기, 내보낸 파일, 부품 안의 항목도)에서 뺀다(`presentable`, 레이아웃의 가장 적은 수까지만): 빈 요청이 번호 '3'과 줄 선만 남거나 빈 숫자 칸이 장 한쪽을 비웠다. 강조는 같은 항목을 따라간다.
- **항목 순서 바꾸기:** 항목(카드, 줄, 단계, 막대)에 손을 올리면 왼쪽 위에 손잡이가 보인다. 끌면 순서가 바로 바뀌어 그려지고(이웃은 미끄러져 비켜 난다, `slides/itemDrag.ts`), 끄는 항목의 가운데가 다른 항목 상자에 들어갔을 때만 자리를 바꾼다(크기가 다른 이웃 사이에서 떨지 않게). Esc는 처음 순서로, 한 번 끈 것은 되돌리기 한 단계. 손잡이에서 화살표 키로도 옮긴다. 가로로 놓인 낮은 항목(추이의 시기, 부품 안의 한 줄 항목처럼 48px보다 낮은 것)은 손잡이와 빼기를 항목 아래 가운데에 둔다: 오른쪽 위에 두면 짧은 칸(시기 이름)을 덮어 그 칸을 누를 수 없었다. 손잡이와 빼기는 보이지 않는 동안 누름을 받지 않는다(투명한 단추가 아래 칸의 누름을 가로채지 않게). 사람이 고른 강조는 그 항목을 따라가고(`followIndex`), 고르지 않은 강조(마지막 항목 같은 자리로 정한 것)는 자리에 남는다. 자리로 그리는 장(포지셔닝)은 끌지 않는다.
- **옆 판 옮기기 (`slides/panes.tsx`):** 두 판으로 나뉜 장(표지의 옆 면, 사례의 결과, 이미지와 설명의 이미지, 결정 요청의 요청 목록, `LayoutSpec.panes`)은 판 위쪽 가운데의 이름표를 끌어 반대쪽으로 옮기고(`options.flip`), 판 사이를 끌어 너비를 고른다(`options.pane`, 장 너비를 12로 나눈 칸 수 가운데 레이아웃이 정한 값; 끄는 동안 고를 수 있는 너비마다 점선과 이름이 보이고 놓으면 가장 가까운 값에 붙는다. 두 번 누르면 기본 너비). 표지는 아래쪽으로 끌면 아래 띠 모양이 된다. 글상자를 마음대로 놓게 하지 않는 것은 그러면 줄과 여백이 어긋나고 글이 잘려서다. 끄는 판은 손을 따라오고, 놓으면 다른 칸이 새 자리로 미끄러진다. 오른쪽 칸(이 장 설정)에서도 같은 값을 고른다.
- **되돌리기:** Ctrl/⌘+Z, 타이핑은 묶어서 한 단계.
- **자동 저장:** 고칠 때마다 저장된다. 따로 누를 저장 단추는 없고, Ctrl/⌘+S는 기다리지 않고 바로 저장한다(알림으로 알린다). 위쪽의 저장 상태(폴더에 저장됨 / 이 브라우저에만 저장됨 / 폴더 저장 멈춤)에 마우스를 올리면 그 말이, 누르면 어디에 저장되는지와 할 일, 단축키가 나온다.
- **버전 기록:** 시계 버튼. 날짜별 시간 줄, 이름 붙인 버전은 채운 점. 버전마다 앞 버전에서 고친 장을 적는다. 누르면 전체 화면 미리 보기(지금과 다른 장 표시)에서 되돌린다.

## 7-1. 저장과 버전

덱이 사라지지 않게 하는 것이 목표다. 서버는 쓰지 않는다.

- **두 곳 저장:** IndexedDB(늘, 0.4초 뒤)와 보관 폴더(골랐으면, 1.5초 뒤). 화면을 떠나거나 창을 숨길 때 남은 저장을 바로 끝낸다. `navigator.storage.persist()`로 브라우저가 저장 공간을 비우지 않게 요청한다.
- **보관 폴더:** File System Access API(크롬, 엣지). 폴더 핸들은 IndexedDB에 둔다. 권한은 브라우저를 새로 열 때마다 다시 받아야 하므로 '허용하기' 상태를 따로 둔다. 파일 이름은 처음 저장할 때 제목으로 정하고 바꾸지 않는다. 같은 이름이 있으면 `(2)`를 붙이고, 이름을 기억해 둔 파일이 다른 발표 것이면 쓰지 않는다.
- **맞추기:** 홈을 열 때, 편집기를 열 때 폴더와 브라우저 중 `updatedAt`이 큰 쪽을 쓴다. 덮이는 쪽은 내용이 다르면 버전(`파일을 열기 전`)으로 남긴다. 폴더에 없는 발표는 폴더로 옮기되, '지운 발표'에 있으면 다른 PC에서 지운 것이므로 목록에서 뺀다.
- **버전:** 목록(가벼운 정보와 장마다의 비교 값)과 내용(덱 전체)을 다른 저장소에 둔다. 자동 버전은 같은 내용의 버전이 이미 있으면 남기지 않는다. 자동은 30개(폴더는 10개)까지, 이름 붙인 버전은 지울 때까지.
- **작업 파일(.deck):** `{ format: 'html-maker/deck', version: 1, savedAt, deck }` JSON. 노트를 포함한다. 남에게 보내는 HTML과 다르다.
- **내 컴포넌트(`store/saved.ts`):** 발표와 따로 이 브라우저(IndexedDB, 저장소 `html-maker-parts`)와 보관 폴더의 `내 컴포넌트.components` 하나에 둔다. 발표를 지워도 남고 어느 발표에서든 쓴다. 두 곳 가운데 `updatedAt`이 큰 쪽을 쓰고(발표 맞추기와 같게), 컴포넌트 탭을 열 때마다 다시 읽는다(그 사이 폴더를 허용했을 수 있다). 지우면 알림의 '되돌리기'로 그 자리에 돌려놓는다.
- **내 컴포넌트 파일(.components):** `{ format: 'html-maker/components', version: 1, updatedAt, parts }` JSON. 모두 또는 하나를 파일로 저장해 다른 사람과 주고받는다. 읽을 때는 발표 파일과 같은 규칙(`cleanRows`)으로 이 버전이 아는 컴포넌트와 값만 넣고, 뺀 것이 있으면 몇 개인지 알린다(`cleanPart`).

## 8. 발표와 내보내기

- **발표하기:** 전체 화면, 방향키·스페이스·PageUp/PageDown(클리커), Esc로 종료. 숨긴 장은 건너뛴다. B/W로 화면 가리기. '누르면' 나오는 컴포넌트가 남은 장은 다음 키가 장을 넘기지 않고 그 컴포넌트를 보인다(발표자 화면에 남은 수). 움직임은 [MOTION.md](MOTION.md).
- **비워 둔 부품:** 발표, 발표자 화면, 내보내기, 인쇄에서는 글도 그림도 없는 부품을 빼고 그린다(`shownBlocks`). 빈 칸이 회색 안내 문구 없이 빈 상자로만 남아 보이지 않게. 뺀 자리는 옆 부품이 넓혀 덮고, 그 부품에 걸린 이음표도 뺀다. 저장된 발표는 그대로다(편집할 때는 다 보인다).
- **발표자 화면:** '발표하기' 옆 화살표 → '발표자 화면과 함께 발표'(Alt+F5). 큰 화면에는 슬라이드만, 노트북에는 지금 장·다음 장·노트·지난 시간·모든 장이 보인다.
  - 설치 없이 크롬·엣지의 Window Management API로 창을 화면마다 놓는다. 처음 한 번 '창 관리' 허락을 묻는다. 허락하지 않으면 슬라이드만 발표한다.
  - 두 창은 BroadcastChannel로 이어서 어느 창에 키가 가도(클리커) 같이 넘어간다. 한쪽에서 끝내면 둘 다 닫힌다. 발표 내용은 창 사이에서만 오간다.
  - 화면이 '복제'로 연결돼 있으면 발표자 화면에서 Windows 키 + P → '확장'을 안내한다.
  - 창 두 개 방식은 회사 PC 설정에 따라 안 될 수 있어서 기본은 '슬라이드만 발표'이고, 발표자 화면은 직접 고른다.
- **HTML 파일:** 폰트(실제 쓰인 글자 묶음만)와 이미지를 파일 안에 넣는다. 인터넷 없이 열린다. 열면 모든 장이 세로로 보이고, "발표 시작"으로 슬라이드쇼. 발표자 노트는 넣지 않는다(미리 보내도 안전). 이 파일을 다시 열면 편집할 수 있다. CSP로 어떤 주소에도 연결하지 못하게 하고, 스크립트는 들어 있는 뷰어 하나만(해시로) 허용한다.
- **PDF:** 브라우저 인쇄로 장마다 1920×1080 한 쪽.
- **PPT (그림):** 장마다 발표할 때 모습 그대로의 그림(1920×1080 PNG) 한 장을 꽉 채운 .pptx. 글은 그림이라 PowerPoint에서 고칠 수 없고, 발표자 노트는 노트 칸에 글로 들어간다(HTML과 달리 노트가 들어가니 보내기 전에 확인하라고 메뉴에 적는다). 숨긴 장은 뺀다. 서버 없이 화면 안에서 만든다(`export/rasterize.tsx`): 진짜 `SlideCanvas`를 화면 밖 1920×1080 상자에 발표 모드로 그리고, 쓴 글꼴 조각을 받은 뒤 부품 장을 다시 맞추고(`fitBlocks`), 그 DOM을 XML로 옮겨 CSS(slides.css, blocks.css)와 글꼴(data: 주소)과 함께 SVG `foreignObject`에 넣어 캔버스에 그린다. 움직임 엔진은 부르지 않아서 다 보인 끝 모습이다. 파일은 공개 규격 ECMA-376(Office Open XML)의 짜임대로 직접 쓴다(`export/pptx.ts`: 틀 하나, 빈 레이아웃 하나, 테마, 노트 틀, 장마다 그림과 노트). ZIP도 직접 묶는다(`export/zip.ts`, PNG는 그대로, XML은 `CompressionStream`으로 deflate). 의존성을 늘리지 않는다. 장마다 그리므로 장이 많으면 몇 초 걸리고, 그동안 몇 장째인지 알림에 보인다. 편집 화면의 콘솔에서 `await pptPreview()`로 그림만 볼 수 있다.

## 9. 기술

- Vite + React + TypeScript 정적 웹앱.
- **로컬 서버** (`server/serve.ts`, Node 내장만. 빌드하면 `dist-node/serve.mjs`): `127.0.0.1:41580`에만 묶는다. 포트를 고정하는 이유는 IndexedDB와 폴더 권한이 주소(포트 포함)마다 따로라서다. `localhost`로 오면 `127.0.0.1`로 보내고, 다른 Host 헤더는 거절한다(DNS 리바인딩 방어). GET/HEAD만, `dist` 밖 파일은 내주지 않는다. 모든 응답에 CSP(`connect-src 'self'` 등)를 붙이고, 빌드한 `index.html`에도 같은 CSP를 meta로 넣는다.
- **나눠 주기:** `npm run pack`이 `dist`, 서버, 더블클릭 실행 파일(맥 `.command`, 윈도우 `.bat`), 사용법을 묶는다. 받는 사람은 Node.js만 있으면 된다. 빌드 결과에 허락하지 않은 바깥 주소가 있으면 멈춘다(`scripts/offline.mjs`, 검수 CI도 빌드 뒤에 같은 검사를 돌린다).
- **새 버전:** 바깥으로 연결하는 곳은 `server/update.ts` 한 파일이다(`scripts/offline.test.ts`가 소스를 훑어 지킨다). 홈을 열면 화면이 로컬 서버에 묻고(`/__html-maker/update/`, AI 창구처럼 앱 머리글과 같은 Origin만), 서버가 `https://api.github.com/repos/wlsdks/gyeol/releases/latest`에 Accept와 User-Agent(`Framo/버전`)만 붙여 묻는다. 켠 동안 24시간에 한 번까지, ‘다시 확인’은 바로. 답에서는 태그(`vX.Y.Z`), 릴리스 주소, 이 OS의 zip(윈도우 `gyeol-windows.zip`, 맥 `gyeol-mac.zip`)의 주소, 크기(300MB까지), 지문(`sha256:…`)만 고르고, 주소는 태그로 만든 주소와 글자까지 같아야 한다. 지문이 없으면 받지 않고 릴리스 페이지만 알린다. ‘받기’를 누르면 넘겨주기(redirect)를 다섯 번까지 한 단계씩 확인하며 따라간다: https, 기본 포트, 정해 둔 곳(`github.com`, GitHub이 2026년 지금 넘겨주는 `release-assets.githubusercontent.com`, 예전의 `objects.githubusercontent.com`)만. 받는 동안 크기를 넘으면 끊고, 다 받으면 크기와 SHA-256을 맞춘 뒤에만 앱 폴더의 `새 버전/` 안에 고정 이름으로 둔다(네트워크에서 온 이름은 경로에 쓰지 않는다). 그다음 탐색기나 Finder로 그 파일을 보여 줄 뿐, 풀거나 실행하거나 앱 파일을 바꾸지 않는다. 사람은 Framo를 닫고 zip을 풀어 새 ‘Framo 시작’을 켠다. 같은 주소(127.0.0.1:41580)라 이 브라우저의 발표와 보관 폴더 연결이 그대로 이어진다. 실패하면 정해진 말(‘확인하지 못했어요’)만 보이고 오류 글, 주소, 경로는 내보내지 않는다. 개발 서버는 확인만 하고 받지 않는다. 알림은 버전 표시를 눌러 끌 수 있고(이 브라우저의 설정), 끄면 GitHub에 묻지 않는다. 브라우저는 계속 `connect-src 'self'`라 GitHub에 직접 가지 않는다(‘바뀐 점 보기’는 링크로 연다).
- 상태: zustand, 저장: IndexedDB(idb-keyval) + File System Access API, 정렬: dnd-kit.
- 폰트: pretendard(dynamic subset), @sun-typeface/suit(굵기마다 나뉜 파일), @fontsource-variable/hahmlet, @fontsource-variable/noto-serif-kr(둘 다 unicode-range 조각). 앱은 쓴 글자가 든 조각만 받고, 내보낸 HTML에도 그 조각만 넣는다(`export/fonts.ts`).

Claude Code나 Codex가 MCP로 붙어서 발표의 구성과 모양을 다듬을 수 있다. 사람이 적은 글은 AI에게 가지 않는다(MCP 응답은 AI 회사 서버로 간다고 보고 설계했다).

```
브라우저 앱 ──PUT 모양──▶ 로컬 서버 ──▶ AI 공유/decks/<해시>.json ──▶ MCP 서버 ──▶ Claude Code / Codex
     ▲                                                                   │
     └──GET 제안── 로컬 서버 ◀── AI 공유/requests/<id>.json ◀── propose_changes
     └──POST 결과─▶ 로컬 서버 ──▶ AI 공유/results/<id>.json ──▶ get_result
```

- **켜는 법:** 편집기 위쪽 **AI** 버튼에서 발표마다 직접 켠다(`deck.aiShare`). 공유하지 않은 발표에서 부탁을 누르면 그 자리에서 한 번 묻고, 그 단추(‘보여 주고 맡기기’)가 켠다. 가져온 발표, 복제한 발표는 꺼진 채로 시작한다. AI 창은 처음에 고르는 것(부탁)만 보이고, AI에게 보이는 것과 보이는 내용 그대로, Claude Code·Codex 연결 명령, 공유 켜고 끄기는 아래 ‘보이는 것, 직접 연결’의 한 장 뒤에 둔다. 예전에는 설명, 켜고 끄기, 보이는 것 목록, 접은 칸 둘이 부탁과 함께 늘어서서 무엇부터 해야 하는지 몰랐다.
- **모양(`src/ai/share.ts`):** 덱에서 고른 값으로 새로 만든다. 보고 종류, 시간, 장 순서, 레이아웃, 장 역할(카탈로그에 있는 말만), 숨김, 칸마다 `empty | filled | long`, 항목 수, 옵션(장면은 목록에 있고 그 장에 맞을 때만), 테마와 강조색. 장과 덱의 원래 id 대신 해시를 쓴다(가져온 파일의 id에는 아무 글이나 있을 수 있다). 제목, 적은 글, 숫자, 이미지, 노트, 소속·이름·연락처는 넣지 않는다.
- **세 겹 확인:** 앱이 만들고, 로컬 서버가 `checkShape`로 꼴을 확인해서 쓰고, MCP 서버가 읽을 때 다시 `checkShape`, 내보낼 때 `onlyKnownStrings`(모든 글자가 카탈로그·정해진 말·해시인지)로 막는다.
- **MCP 서버(`mcp/server.ts`):** 의존성 없는 stdio JSON-RPC. 스스로를 Node 권한 모델(`--permission --allow-fs-read/write=AI 공유`)로 다시 띄워서 다른 파일을 읽지 못하고 다른 프로그램을 실행하지 못한다. 권한 모델이 심볼릭 링크를 따라가는 문제는 링크·하드 링크를 읽지 않는 것으로 막는다. 오류는 정해진 문구만.
- **도구 여섯 개:** `list_decks`, `get_catalog`, `get_shape`, `check_changes`, `propose_changes`, `get_result`. 글을 읽는 도구는 없다.
- **미리 돌려 보기(`check_changes`, `src/ai/check.ts`):** 보내기 전에 같은 제안을 모양으로 세운 대역 발표(찬 칸은 지어낸 글자, 판의 자리와 고른 값은 모양 그대로) 위에서 앱과 같은 `applyOps`로 돌려, op마다 결과 코드와 고칠 것(정해진 말), 까닭이 된 키(`OP_KEYS`에 있는 이름만)를 돌려준다. 아무것도 쓰지 않는다. 예전에는 AI가 장면과 강조를 한 op에 담았다가 강조가 안 되는 장에서 장면까지 통째로 빠지거나, 꼴이 틀린 op 하나로 제안 전체가 거절돼도 어느 op인지 알 수 없었다. 노트처럼 모양에 없는 것 때문에 앱의 결과와 조금 다를 수 있다. `get_result`의 빠진 op에도 같은 풀이가 붙는다.
- **카탈로그를 작게(`get_catalog`):** 카탈로그가 Claude Code가 한 번에 받는 도구 응답(약 2만 5천 토큰)에 가까워져서, 거짓·없음인 값을 빼고, `deck`을 주면 그 발표 종류의 역할만, `blocks: false`면 부품 장의 부품 목록을 뺀다(빼기만 해도 5분의 4쯤, 둘 다 고르면 3분의 1쯤).
- **프롬프트(`prompts/list`, `prompts/get`):** 'AI에게 부탁'의 부탁(`src/ai/asks.ts`)을 MCP 프롬프트로도 내준다. Claude Desktop이나 Claude Code에 Framo를 붙인 사람이 목록에서 골라 바로 쓴다(`/mcp__gyeol__deck_flow`). 받는 값은 발표 id(비우면 가장 최근에 고친 발표)와 장 부탁의 장 번호뿐이고, 꼴이 맞을 때만 정해진 문장(`mcpPrompt`)에 넣는다. 사람이 장의 해시 id를 알 수 없어서 장은 번호로 고른다.
- **제안(`src/ai/ops.ts`):** 장 넣기·빈 장 지우기·옮기기·숨기기, 레이아웃, 항목 수(빈 항목만 줄임), 옵션(장마다 장 넘기기, 장면 포함. 장면은 그 장에 맞는 것만, 아니면 `scene_unfit`으로 건너뛴다), 테마, 장 안내, 칸 안내 문구. 칸의 글을 쓰는 동작은 없다. 꼴이 하나라도 어긋나면 제안 전체를 받지 않는다. 한 발표에 보지 않은 제안은 5개까지.
- **사람이 결정:** 제안이 오면 오른쪽 아래에 알림이 뜨고, 미리 보기에서 바뀌는 것 목록과 적용한 뒤의 장들을 본다. 목록은 바뀌는 것을 먼저, 건너뛰는 것(까닭과 함께)은 아래에 따로 둔다. AI의 설명은 왼쪽 선 하나로 인용처럼 두고 파란 면을 쓰지 않는다. 적용하면 그 전 상태를 버전(‘AI 제안을 적용하기 전’)으로 남기고, 되돌리기 한 번으로 돌아온다. 결과(적용/거절, op마다 코드)는 AI가 `get_result`로 본다.
- **다른 웹사이트 막기:** AI 창구는 `X-HTML-Maker` 머리글이 있어야 하고 Origin이 같아야 한다. 다른 사이트가 머리글을 붙이면 브라우저가 먼저 허락을 묻는데(OPTIONS), 서버는 허락하지 않는다.

### AI에게 부탁 (터미널 없이)

비개발자가 터미널을 열고 MCP를 연결해 말을 거는 대신, 슬라이드 아래 **AI에게 부탁**(이 장)이나 위쪽 **AI** 버튼(발표 전체)에서 부탁을 고른다. 로컬 서버가 이 PC의 Claude Code를 대신 띄워 부탁을 전하고, 제안이 오면 미리 보기가 바로 열린다.

```
[부탁 고르기] ──POST {ask, deck 해시, slide 해시}──▶ 로컬 서버 ──stdin: 정해진 문장──▶ claude -p (도구 없음 + gyeol MCP만)
     ▲                                                                                        │
     └── 진행(도구 이름), 제안 id ◀── 로컬 서버 ◀── AI 공유/requests/<id>.json ◀── propose_changes
```

- **부탁(`src/ai/asks.ts`):** 이 장 넷(더 어울리는 모양으로, 핵심이 눈에 띄게, 칸 안내 다듬기, 앞뒤에 필요한 장)과 컴포넌트 장에만 보이는 컴포넌트 짜임 다듬기(자리, 크기, 면, 이음표, 나오는 차례. 레이아웃이 정해진 부탁은 `layouts`, 로컬 서버도 다시 확인한다), 발표 전체 넷(보고 흐름 점검, 시간에 맞추기, 테마와 움직임, 장면 연출). 장면 연출은 장마다 맞는 장면을 골라 이야기가 쌓이게(여는 장, 결론 먼저, 근거, 가장 중요한 숫자에서 힘주기, 조용한 마무리) 하고 같은 장면이 이어지지 않게 한다. 장 하나만 고르는 부탁은 두지 않았다: 맞는 장면이 한두 개라 움직임 탭에서 누르는 편이 빠르고, 앞뒤를 보는 판단은 발표 전체에서만 선다. 오가는 것은 id와 해시뿐이고, AI에게 갈 문장은 로컬 서버가 `askPrompt`로 정해진 말로 만든다. 사람이 적은 글은 받지 않는다.
- **띄우는 법(`server/agent.ts`):** `claude -p --restricted --tools "" --strict-mcp-config --mcp-config <gyeol만> --allowedTools mcp__gyeol__* --permission-prompts none`. 파일 읽기·쓰기, 명령 실행, 웹 도구가 아예 없고, 사용자의 훅·플러그인·다른 MCP 서버도 읽지 않는다. AI가 볼 수 있는 것은 MCP 서버가 내주는 모양뿐이다. 사람이 Claude Code를 직접 쓸 때보다 좁다. 한 번에 하나, 3분이 넘으면 끈다.
- **연결 상태:** AI 창과 슬라이드 아래 창의 머리에 셋 가운데 하나만 보인다. 준비됨(이 PC에서 Claude Code를 찾았다), 로그인 필요(부탁이 `login`으로 끝났다. 서버가 로그인 여부를 따로 알려 주지 않아서, 부탁해 보기 전에는 준비됨으로 보인다. 다음 부탁이 제안까지 가면 풀린다), 설치 필요(찾지 못했다). 저마다 한 줄과 할 일 하나: 로그인은 `claude`, 설치는 공식 설치 명령(윈도우는 PowerShell의 `irm …install.ps1 | iex`, 맥은 `curl …install.sh | bash`)을 복사하는 단추. 앱이 그 주소에 연결하는 것이 아니라 사람이 자기 터미널에서 실행하는 글이다. 설치 전에는 부탁을 누르면 부탁 문장을 복사한다(Claude Code나 Codex에 붙여 넣기). 창을 열 때마다 다시 확인해서(`recheck`) 설치하고 돌아와 창을 다시 열면 바로 준비됨이 된다. 슬라이드 아래 창은 위로 열려 자리가 좁아 명령 칸 없이 한 줄과 ‘명령 복사’만 둔다.
- **ACP를 쓰지 않은 까닭:** ACP는 편집기와 에이전트를 잇는 표준이지만 Claude Code, Codex 모두 따로 어댑터를 깔아야 하고, 우리는 대화가 아니라 정해진 부탁 하나를 맡기면 된다. 이미 깔린 Claude Code의 비대화 실행이 도구를 더 좁게 막을 수 있다.
- **Codex:** Codex의 비대화 실행(`codex exec`)은 도구를 하나씩 끄는 방식이라 버전이 오르며 새 도구가 생기면 열릴 수 있다. 그래서 바로 띄우지 않고, 부탁 문장을 복사해 붙여 넣게 한다(Claude Code가 없는 PC도 같다).
- **진행과 결과:** 오른쪽 아래 카드(와 다시 연 AI 창)에 단계 ‘켜기 → 살펴보기 → 정리하기 → 미리 보기’와 흐른 시간을 보여 주고 그만둘 수 있다. 제안이 오면 미리 보기가 바로 열리고, 바뀌는 장은 ‘지금 → 적용하면’을 나란히 먼저 보여 준다. 바꿀 게 없으면 AI가 말한 까닭(마크다운을 걷고 280자까지)을 카드에 남긴다. AI → 앱 쪽 글이라 내용이 나가는 길이 아니다.
- **공유:** 부탁을 들어주려면 모양을 봐야 해서, 공유하지 않은 발표에서 부탁을 누르면 그 부탁 아래에 ‘이 발표의 모양만 AI에게 보여 줘요. 적은 글은 보내지 않아요.’와 ‘보여 주고 맡기기’(복사할 때는 ‘보여 주고 복사하기’)를 펴서 한 번 묻는다. 말없이 켜지 않는다. 끄기는 AI 창 아래의 ‘그만 보여 주기’.
